# STM32 Toolkit 0.7–1.0 Vertical Delivery Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver one Agent-driven VS Code STM32 workflow from new-project creation through real-board 1.0 acceptance without rebuilding the recursive Gate structure that delayed 0.6.

**Architecture:** One Agent-neutral CLI/MCP core coordinates CubeMX creation, CubeCLT builds, PyOCD Probe ownership, Cortex-Debug handoff, and the existing Monitor/Test/Diagnostic loop. Work advances through seven sequential software slices and one final physical campaign; each slice gets a just-in-time implementation plan and one Luna/max implementation owner followed by independent Sol review.

**Tech Stack:** CPython `>=3.12,<3.13`, FastMCP, STM32CubeMX 6.18, STM32CubeCLT 1.22.0, ARM GCC 14.3.1, CMake 4.3.1, Ninja 1.13.2, PyOCD, VS Code, Cortex-Debug, pytest, existing Monitor UI and 0.6 contracts.

## Global Constraints

- Current product accepted base is `d09e2343ab970f4ddeaa4c24dbf581c9bbe96f58`; later governance-only commits do not change those product bytes.
- Current governance baseline begins at design commit `fa9a3c4aa349d296f5de9704ecb4300fc420a71f` and remains local until separately authorized.
- GPT-5.6-sol owns specifications, plans, risk decisions, complete-diff review, and acceptance.
- Every product implementation slice uses one GPT-5.6-luna subagent with reasoning effort `max`.
- Python support is exactly `>=3.12,<3.13`; Python 3.10/3.11 are frozen historical scope.
- The 1.0 reference installation and physical acceptance platform is Windows.
- CubeMX creates new projects; CubeCLT supplies GCC/CMake/Ninja and tool facts; PyOCD remains the only production Probe backend.
- Claude Code remains a thin adapter; the core CLI/MCP behavior is Agent-neutral.
- No ST VS Code extension, second project model, second Probe backend, new controller, provider platform, CI, or remote scheduler is added.
- Hardware tests are deferred to the single 1.0 campaign; fake/replay evidence is never relabeled as physical PASS.
- Push, PR mutation, merge, tag, release, close, and remote branch deletion require separate user authorization.

## 2. Delivery sequence

### Slice VS07-A: Creation plan and environment truth

**Outcome:** A caller submits exactly one MCU, board, or `.ioc` source and receives a deterministic read-only `CreationPlan`, or an accurate remediation explaining why the installed CubeMX/CubeCLT/VS Code environment cannot support it.

**Dependencies:** Existing project boundaries and result contracts; CubeCLT 1.22.0 is installed. CubeMX absence is a valid environment result, but the installed CubeMX 6.18 path is required for the positive acceptance.

**Detailed plan:** `2026-08-22-stm32-toolkit-0701-creation-plan-environment-truth.md`.

**Expected cycle:** 2–3 working days, including independent review.

### Slice VS07-B: Authorized creation to buildable firmware

**Outcome:** An exact single-use plan authorization runs CubeMX once in isolated staging, atomically activates a valid project, then reuses existing configure/build behavior to produce Debug/Release firmware identities.

**Dependencies:** VS07-A accepted; STM32CubeMX 6.18 installed and its required device package available offline.

**Failure boundary:** Input/tool/destination drift, nonzero/timeout/partial native output, activation race, or rollback failure never creates a claimed project success.

**Expected cycle:** 2–3 working days.

### Slice VS07-C: Safe regeneration

**Outcome:** A caller previews and authorizes one `.ioc` regeneration while generated, Toolkit-managed, and user-owned files remain distinguishable; user code is never silently overwritten.

**Dependencies:** VS07-B accepted and one generated fixture available.

**Failure boundary:** Unknown ownership, user drift, generator version drift, path escape, or target collision requires explicit remediation and leaves the prior project recoverable.

**Expected cycle:** 2–3 working days.

### Slice VS08-A: Versioned vertical scenario adapter

**Outcome:** Existing 0600 control and Evidence contracts can run and query two software scenarios: one Keil migration and one new CubeMX project, each through build, simulated/replay observation, diagnosis and verification without claiming physical PASS.

**Dependencies:** 0.7 accepted; existing 0.6 public workflows remain unchanged.

**Failure boundary:** The adapter does not become a controller, scheduler, daemon or second Evidence store.

**Expected cycle:** 2–3 working days.

### Slice VS08-B: Resume, isolation and checkpoints

**Outcome:** An interrupted scenario resumes from verified immutable outputs, two workspaces remain isolated, and intrusive operations require explicit human authorization checkpoints.

**Dependencies:** VS08-A accepted.

**Failure boundary:** Stale checkpoints, identity drift, lease loss, partial cleanup or cross-workspace references fail closed without rewriting prior attempts.

**Expected cycle:** 2–3 working days.

### Slice VS09-A: Runtime and Agent adapter convergence

**Outcome:** A clean Windows user can start the same Python 3.12 Toolkit MCP through generic explicit roots or the retained Claude adapter; doctor, package, Monitor, launcher, Skills, README and MCP inventory agree on one version and support profile.

**Dependencies:** 0.8 public inventory frozen.

**Failure boundary:** No system-Python fallback, duplicate runtime, duplicate MCP registration or Agent-specific product logic.

**Expected cycle:** 2–3 working days.

### Slice VS09-B: Installation, upgrade, security and artifacts

**Outcome:** A pinned GitHub-source checkout installs reproducibly in a clean Windows profile, supports safe schema/runtime upgrades, produces checksummed wheel/archive/Monitor assets/SBOM/licenses, and rejects the named malicious-input classes.

**Dependencies:** VS09-A accepted.

**Failure boundary:** Downgrade never destroys incompatible state; report-only defects do not rewrite product verdicts.

**Expected cycle:** 2–3 working days.

### VS10: Unified real-project and physical-board campaign

**Outcome:** One real legacy Keil project and one new CubeMX project complete create/migrate → build → flash → observe → fail → diagnose → authorized fix → rebuild/reflash → Target test → Monitor verification on a named board/Probe.

**Dependencies:** 0.9 software candidate accepted; real projects, board, probe, transport and exact authorizations available.

**Closes:** Historical 0.4 hardware debt, 0.6 physical Scenario C, and both 1.0 release scenarios without duplicate campaigns.

**Expected cycle:** Campaign duration is estimated only after the named assets exist; hardware discovery time is not hidden inside a software slice estimate.

## 3. Just-in-time planning rule

- Only the next slice receives a detailed code plan.
- The successor plan is written after the predecessor has an accepted CodeHead and frozen public interfaces.
- A detailed plan may contain sequential TDD steps for one Luna implementer, but those steps are not separate agents, branches, reports or Gates.
- If a plan needs more than one product state machine or more than three working days, revise the integration design or slice boundary before dispatch.

## 4. Verification budget

| Layer | Required evidence | Runs when |
|---|---|---|
| Slice | target tests, public contract tests, affected regression, complete diff review | every slice |
| Integration | one cross-module scenario, identity/isolation, critical non-functional contract | after a link is formed |
| Release | full Python/UI/package/install/security/license/SBOM and physical campaign | 0.9/1.0 only |

Risk triggers and stop-loss rules are authoritative in the integrated product design. A plan cannot add a broader check without naming the trigger and affected surface.

## 5. Ownership and review ledger template

Every slice return records:

- full product accepted-base SHA;
- specification and plan source SHAs;
- implementation branch/worktree and implementer;
- code head before any report-only commit;
- tracked/untracked, committed/uncommitted and pushed/unpushed state;
- exact slice tests run by the implementer;
- complete-diff findings and checks run independently by the Sol reviewer;
- separate PRODUCT, INFRASTRUCTURE, ENVIRONMENT, PLATFORM, HARDWARE and REPORT blockers;
- exact remote or hardware action authorized, normally none.

## 6. Stop conditions

- The same issue fails two implementation/review rounds.
- A slice exceeds three working days or requires a recursive task tree.
- Verification/reporting exceeds product implementation in two consecutive slices.
- A new backend, runtime, platform, provider or compatibility family appears without an approved product scenario.
- A required real external component cannot be proven against native bytes.

At a stop condition, do not add Gate layers. Return to the relevant public interface or integrated design.
