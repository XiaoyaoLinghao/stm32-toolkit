## Correction contract and ownership

Runnable scenarios: (1) real Windows MCP stdio can start and close an offline worker without timeout or protocol pollution; (2) CLI worker startup and existing IPC calls retain behavior; (3) startup failure/timeout closes only the owned child and handles. Non-goals: hardware retry, reset/flash, larger deadlines, new error-code taxonomy, broad diagnostic framework, changes to lease/firmware identity, or fixing unrelated IDE-generated configuration.

Proposed file scope: `tools/stm32-toolkit/src/stm32_toolkit/probe/worker.py`, one private Windows launcher adapter beside it only if needed, `tests/test_probe_worker.py`, and the existing MCP test module for real stdio startup coverage. The adapter would own only the existing worker launch's Windows standard-handle configuration; it does not introduce a second backend or IPC protocol. Freeze its concrete supported spawn integration seam before implementation; CPython's private Popen integration must not be copied or expanded casually.

Required behavior: child standard streams are explicitly isolated from parent MCP protocol streams; parent streams remain unchanged. Preserve spawn isolation, worker target/config serialization, ready/IPC schema, owned PID, 10-second ready budget, cancellation/abort/reaping, normal connection policy and non-Windows behavior. Do not globally monkeypatch `_winapi.CreateProcess`, temporarily replace parent stdin, or weaken cleanup. Luna/max must return to design if these constraints cannot be met through a bounded launcher seam.
