## Implementation and integration

1. Fixture-only work proceeds independently in `r10/fi` under its own approved
   contract. Main release implementation is in `r10/vi`, branch
   `codex/STM32TK-1.0-release-identity`, owned by one Luna/max agent. Primary creates
   clean worktrees at the exact approved local commit; no master inference.
2. Release owner changes only the version/installer/builder/schema/docs scope:
   `.claude-plugin/plugin.json`; `bin/setup-stm32-env.ps1` and the two launchers;
   both Python pyprojects, Toolkit `__init__.py`; UI package/lock;
   the two exact `.gitattributes` LF rules for the trusted release utility/policy;
   `schemas/stm32-release.schema.json`; existing builder/policy;
   `skills/setup-stm32-env/SKILL.md`, current README/deployment instructions when
   needed; and affected version/packaging/setup/security tests. No Monitor or
   Probe runtime behavior, UI components, dependency updates or legacy 0600
   controller rewrite. The fixture owner's ten modules are disjoint.
3. Release owner runs affected version, manifest, artifact and setup/security
   regressions, records exact retained results and returns a local CodeHead/report.
   A non-implementing reviewer checks the complete base-to-final diff in a clean
   checkout. Correct findings return to the same owner; two nonconverging rounds
   trigger a contract reconsideration. Primary integrates both accepted slices.

4. The offline-confirmed 0.9 project producer blocker is corrected by that same
   release owner in the existing worktree before final integration. Additional
   ownership is limited to `generation/managed_files.py`, `generation/configure.py`,
   `build/runner.py` and the existing generation/build-runner tests. Follow the
   specification's exact producer allowlist and unchanged hardware-provenance
   boundary; run affected public configuration/build and refusal cases using
   existing fixtures. Update current upgrade guidance, then independently review
   this delta. Do not repeat unchanged installer behavior for documentation alone.

## One final release matrix

The integrated final CodeHead is frozen before broad verification. This is the
release layer explicitly required by the original integrated design, so the broad
matrix is justified here and is not repeated for each slice/report change.

- Python: one complete Toolkit+Monitor suite on CPython 3.12 with retained branch
  coverage >=90%; measured performance runs separately without instrumentation.
  Selected runtime dependency versions must match the pinned supported set.
  Run Toolkit and Monitor as separate pytest invocations: their existing test
  modules use bare sibling imports and have overlapping names. Preserve that
  supported layout, use separate coverage files and gate each package >=90%.
  The completed installer/artifact/launcher slice runs may supply those exact
  module results when final tracked inputs and dependency versions are identical;
  record source-byte comparison and enumerate reused nodes. Do not repeat a long
  installer suite solely for a report or README commit. Remaining suite modules
  and package branch coverage still run on the final integrated CodeHead.
- UI: typecheck and E2E typecheck, lint, Vitest coverage (includes accessibility),
  per-file coverage check, build/dist check, production dependency audit with no
  high/critical advisory; Playwright non-performance cases at
  both declared viewport projects. Then each five-minute performance viewport
  runs serially and exclusively with its own evidence root, unchanged durations
  and thresholds. No physical-hardware claim from the browser fake runtime.
- Artifact owner: existing builder twice from the same clean CodeHead and closed
  offline wheelhouse, compare all 13 outputs; verify archive/checksums, licenses,
  SBOM, compatibility/troubleshooting and product/runtime identities.
- Deployment owner: actual fresh 1.0 Bootstrap/Check in an isolated data root;
  0.9-to-1.0 Repair, rollback/refusal/security checks using existing tests and
  bounded install entries. Do not change user project/firmware evidence merely
  to validate installation. Final deployed launcher and asset checks use shipped
  bytes and absolute paths.
- Primary reconciles each required physical debt with the original A/B authority
  and preserved evidence. A missing real required transport/client check remains
  missing until its exact existing-board operation or external condition is met;
  do not infer it from unrelated acceptance. Only affected missing gates may use
  the user's ongoing hardware authorization with fresh action identities.
  Two-workspace isolation is reconciled across Toolkit attempts, Probe lease and
  cross-process lock, Monitor stores/history, browser origin/workspace controls,
  evidence references and export authority. Use the named existing tests within
  the same final release matrix plus accepted component provenance; the historical
  gate says "across" these surfaces and does not require a new combined framework
  or a further physical run. Each surface must have actual valid evidence.

All run roots are under `D:\codex-tmp\v10b-0918\r10` unless primary explicitly
records a shorter child of `D:\codex-tmp` to satisfy an observed Windows path-length
limit. TEMP/TMP/TMPDIR, pytest basetemp/cache/coverage, npm cache, Playwright browser
and evidence paths are set before their children start. Primary owns cleanup and
retains minimum failures and final acceptance artifacts. Existing `fin/e`,
`fin/archive` and canonical physical records stay frozen; the earlier rejected
cleanup is not retried or bypassed.

Applicable engineering lessons: STM32TK-EL-007 controls all Python temp roots;
EL-008 requires actual retained command/output provenance; EL-004 keeps recovery
prepare hardware-free. GL-004 separates this required release matrix from slice
checks. These do not grant new remote authority or turn replay into hardware PASS.

Completion requires every mandatory item to have valid final-byte or explicitly
reused scoped evidence, the actual local 1.0 artifacts and deployment/fault guide,
and primary final acceptance. Known limits and remote synchronization status are
reported separately. Goal remains active until those conditions are met.
