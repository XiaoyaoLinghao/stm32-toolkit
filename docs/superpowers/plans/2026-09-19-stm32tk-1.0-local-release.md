## Narrow backend performance follow-up

The original named Monitor benchmark failed during retention with the sanitized
`MONITOR_STORAGE_BUSY` result; its separate export benchmark passed. A bounded
direct retention probe reused the exact 100000-value snapshot and returned OK
for 3 warmups plus 20 calls, with no StorageFailure. This is nonreproduction,
not an accepted replacement for the original named benchmark or its missing
HTTP phase. Preserve that distinction and all original failures.

The probe also exposed a separate test-fixture lifecycle defect:
`test_performance.py::_seed_fixture` uses sqlite3's transaction context but never
explicitly closes its checkpoint connection. Immediate database restoration can
then fail to delete WAL on Windows with WinError32. One Luna/max owner may change
only that helper's connection lifetime to an explicit finally/close, retaining
all fixture bytes, clocks, counts and performance limits. Accepted integration
base for this correction is `f7f19053649f16ae4ab390a5af6012c451833bea`; use an
isolated `r10/pf` worktree and the existing test module plus a short report.
Product sources and 1.0 packages remain frozen at 15b.

After independent review and completion of ordinary concurrent tests, run only
`test_named_monitor_performance_acceptance` once, uninstrumented and with
exclusive resources. The existing entry is required to retain the original
append/query/export/retention/HTTP ordering; the smaller probe did not reproduce
the failure in that ordering. Do not rerun the already-passed separate export
benchmark or UI performance. A narrow external StorageFailure constructor
observer, reusing the already-reviewed exception capture, may retain the original
throw site if it fails; successful construction paths, budgets and behavior must
not change. No general tracing framework or private synthetic benchmark.

Use short `r10/t/pf` temp/cache roots and `r10/e/performance-followup`; retain the
actual argv, source/test head, environment, JUnit, metrics, stdout/stderr and exit.
First abnormal benchmark result stops the run. A pass is evidence for this new
run, not proof of the old BUSY cause; a repeated failure returns to primary with
its actual exception before any product correction or further execution.
