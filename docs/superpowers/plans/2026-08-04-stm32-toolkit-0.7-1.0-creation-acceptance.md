**Goal:** Add deterministic VS Code-first STM32 project creation and prove the complete AI-assisted migrate/build/flash/debug/monitor/test workflow on real hardware before declaring 1.0.

**Architecture:** Project creation is adapter-driven. STM32CubeMX is the primary source generator for vendor startup/HAL/LL code, while Toolkit owns validated project metadata, reproducible CMake presets, editor/AI configuration, provenance, and generated-file drift checks. A versioned acceptance harness records immutable evidence for both migrated Keil inputs and newly created projects.

**Tech Stack:** Python 3.10+, STM32CubeMX 6.18 command-line interface, CMake/Ninja, GNU Arm Embedded Toolchain, CMSIS/CMSIS-Pack facts, pytest, the shared 0600 gate controller, the 0.4 Probe Service, and the 0.5–0.6 monitor/test/diagnostic packages.

## Global Constraints

- Creation is VS Code/GCC-first. Do not create, update, or synchronize Keil project files.
- Do not hand-maintain an exhaustive MCU database. Obtain target data through versioned adapters and retain source/version provenance.
- Never overwrite user-owned source silently. Generated regions require ownership metadata, manifest hashes, and drift detection.
- Generated `.vscode` files must remain usable by the Claude Code extension and ordinary VS Code tooling; Toolkit distribution remains GitHub-only.
- GitHub-source installation remains the only documented distribution path.
- Any unsupported MCU, CubeMX version, pack, toolchain, debug probe, or transport must fail with a concrete remediation message.
- Hardware-skipped tests cannot satisfy the 1.0 release gate.
- Do not add a parallel controller, CI system, remote scheduler, dynamic provider loader, second
  runtime, or second project/Monitor/test platform. Remote Git mutation remains separately
  authorized and is never implied by an acceptance plan.
- A future remote lab or Renode integration may exist only as an optional, separately proven
  provider behind the same Toolkit contracts. Simulation, replay, fake-engine, and remote-provider
  evidence may exercise software paths but can never be relabeled as the required physical-board
  PASS.
- Releases 0.8--1.0 close and prove the existing vertical workflow; they do not add another
  controller, runtime, product platform, or unplanned feature family.
- Existing Keil-to-GCC projects remain on their accepted path. Project creation never silently
  regenerates, imports, or converts them to CubeMX, CMSIS-Toolbox, csolution, or another model.

## 1.0 Exit Criteria

- [ ] A fresh GitHub-source installation can migrate one legacy Keil project and create one new STM32 project for GCC/VS Code without writing Keil files.
- [ ] Claude Code can use Toolkit's Skills/MCP tools to build, flash, monitor, control a debug session, collect logs/faults/tests, reason from evidence, apply a fix, and verify it on real hardware.
- [ ] All monitor groups are user-created; no project or Toolkit preset appears in a fresh workspace.
- [ ] Hardware ownership and project data remain isolated under concurrent use, with operation-level safety checks and complete audit trails.
- [ ] Compatibility claims, limitations, install/upgrade paths, version migrations, and rollback behavior are documented and backed by archived acceptance evidence.
