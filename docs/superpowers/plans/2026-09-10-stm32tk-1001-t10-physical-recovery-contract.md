# T10 physical recovery contract repair

Status: frozen for offline implementation. Native TestRun/Diagnostic identifier and source snapshot seams have been reconciled below.

## Authority and scope

Primary conversation owns the design and acceptance. One Luna/max owner will implement the complete recovery slice; an independent reviewer checks the complete diff. Accepted slice base is `4b79ad97c51a3bc62f7c57c4637489ac9d5c6da1`; governing requirement is section 7.5 of the approved 2026-08-25 legacy real-board closed-loop design. No remote action, hardware operation, project P3/P4 mutation, deployment or ownership override is authorized by this document.

Task 10 already requires physical failed TestRun -> Diagnostic -> exact source-change authorization -> physical fixed TestRun -> FixVerification. Current replay-only AcceptanceAttempt cannot represent this. Current source action digest also omits the permitted file/content changes. These are product contract gaps, not evidence that current hardware or the accepted 100ms sampler failed.

## User scenarios

1. Existing VS08 replay attempts and AcceptanceRecord retain their schema, digest, accepted scenarios, stage spelling and behavior.
2. A legacy physical repair attempt checkpoints an existing failed physical Target run and matching Diagnostic. Resume returns a reviewable exact source-change intent and its single-use authorization digest.
3. After that authorization, only the declared resulting source snapshot and matching rebuilt firmware can advance. Final completion requires the actual matching physical passed run and completed Diagnostic FixVerification. Completion is not whole VS10-A acceptance.

No new execution engine, evidence store, public tool, automatic source editor, automatic flash or migration of old evidence. No hardcoded Main.c/LED behavior in Toolkit. P3/P4 project changes remain a later separately authorized campaign operation.

## Exact source-change intent

At the physical `diagnosis-completed` checkpoint accept `sourceChangeIntent` alongside the diagnostic session. CLI uses a bounded JSON `--source-change-intent-file`; MCP uses a closed nested object on the existing checkpoint tool. Reject this input for v1 or other stages.

Intent input schema `stm32-source-change-intent/1`: fields `schema`, `changes`. Changes is a lexically ordered, unique, nonempty list of at most 32 existing paths from the model's declared C/assembly source collections, each with exactly `path`, `beforeSha256`, `afterSha256`, `afterSize`. Require portable canonical relative paths, bounded regular files, actual changed hashes and existing source ownership. afterSize is a strict nonnegative integer within the existing eight MiB per-input limit. This slice supports replacement of existing source content only; reject additions, deletion, header-only changes, generated/configuration/manifest changes and path aliases. No guessed source identities or caller-supplied build identity overrides.

At checkpoint, obtain the existing authoritative source InputSnapshot and verify it matches beforeInputSnapshotSha256 and the fresh P3 build. Validate every declared before hash against that snapshot. Compute the expected after-snapshot hash by substituting only the listed content hashes/sizes in the complete canonical snapshot representation; preserve every other entry and semantic field. Persist the validated intent plus derived `beforeInputSnapshotSha256`, `expectedAfterInputSnapshotSha256` and a canonical `intentDigest` in v2's closed snapshot. intentDigest is SHA256 of this expanded closed intent excluding intentDigest itself. This is immutable from revision 4 onward. No new manifest store is needed: the complete before entries exist in memory at checkpoint, are verified against the already published before digest, and are used then to derive the after digest; no later reconstruction from a scalar hash is attempted. Authorization re-reads the unchanged before snapshot and can repeat that derivation.

Action digest includes schema, scenario/policy, current attempt/checkpoint identity, failed physical evidence identity, diagnostic revision/event head and intentDigest. Resume exposes the exact intent for approval. Authorization rechecks current source is still the P3 snapshot and diagnostic head unchanged before its single winner commits. After-build checkpoint requires the actual complete InputSnapshot hash equal expectedAfterInputSnapshotSha256, a new fresh build/ELF, and the matching existing SourceChangeDeclaration with both build, ELF and snapshot identities. This rejects extra source or configuration changes even if the declared file itself matches. It cannot authorize edits by changing the intent on a retry.

## Physical evidence and completion

Native run identifiers must be preserved verbatim. Physical Target v2 IDs are not to be converted into UUIDs. Attempt UUIDs and Diagnostic identifiers retain their own established domains. Existing TestRun publication and Diagnostic authorities, rather than caller-supplied flags, prove physical identity.

For physical failure checkpoint require a loadable, integrity-validated TestRunRepository publication: target mode, failed state, physical source/transport evidence, current project/workspace/target, expected before build/ELF/input snapshot, and the exact published evidence ID. There is no missing-store fallback for the physical branch. Persist the native run ID and evidence ID. Preserve the physical probe/target lineage from this authority for subsequent Diagnostic and after-run comparisons.

For physical final checkpoint accept `testRunId` and `fixVerificationId` on the existing checkpoint operation; reject `acceptanceRecordId`. Reload the actual passed physical after TestRun and the existing Diagnostic verification from the attempt's diagnostic session. Require completed successful verification with exact failed/fixed run/evidence, source declaration, before/after build/ELF/input snapshot, workspace/project/probe/target and expected-state lineage. Reject replay, host, partial, wrong probe, unrelated verification or swapped run. Store fixedAfterTestRunId, fixedAfterEvidenceId and fixVerificationId in the v2 closed outputs; do not create or accept a VS08 record. The existing SourceChangeDeclaration.changed_paths must equal the intent paths exactly. Its aggregate after snapshot must equal the derived expected snapshot; arbitrary diff text is never substituted for that proof.

The v2 stage outputs retain v1's keys except acceptanceRecordId, replacing it with fixedAfterTestRunId, fixedAfterEvidenceId and fixVerificationId, all unavailable until revision 7. failedBeforeTestRunId/fixedAfterTestRunId use the existing native TestRun identifier domain; Diagnostic session input for v2 uses the existing 32-hex Diagnostic ID domain. sourceChangeIntent is a new top-level field null before revision 4. All other field names and revision availability rules remain as described above. The physical model may be separate from the v1 class, but uses the same recovery authority and persistence lifecycle.

The new `legacy-keil-physical-repair` scenario is mailbox-only, matching the current Task 10 campaign. Reject other transports at its physical failure and final checkpoints. Extend only `diagnostic_workflows._validate_pair_execution_policy` for physical pairs: after existing policy validation, require identical envelope metadata probe_id and target_id, equal manifest transport, and equal project/workspace/target scope. Require equal transport_config_digest for mailbox pairs. Do not impose that equality on other transports: testing/target.py `_task8_identity_digest` includes ELF identity for semihosting and the discovered control-block address for RTT, so legitimate before/after firmware can change those digests. Preserve their existing individually validated provenance and source declaration lineage without inventing a normalized transport schema. Preserve `_same_scope` and its EvidenceIdentity.session_id equality: P3/P4 runs and Diagnostic share this identity session, with origin_session_id/import_session_id each matching it as already required by publication. Each publication remains individually validated by TestRunRepository. Do not require equal action_digest, intent_digest, flash_session_id, lease_id, build or ELF: these belong to distinct operations and P3/P4 intentionally differ. Reuse this same pair validator when finalizing the physical attempt rather than implementing a divergent comparison. Existing immutable evidence references suffice; no FixVerification schema change is needed. These fields prove matching published probe/target/transport lineage, not an unrecorded silicon unique ID.

All evidence loads fail closed on corruption or absent authority. A test fixture may exercise these validators offline but its test output must never be labeled physical acceptance.

The new physical scenario's canonical document includes transport=mailbox, so its digest binds this scope. Persisted v2 attempts at revision 4 or later require the expanded intent (all three derived fields, including a validated intentDigest), not the caller's unexpanded input. The model binds intent.beforeInputSnapshotSha256 to stageOutputs.beforeInputSnapshotSha256, and at revision 6 or later binds expectedAfterInputSnapshotSha256 to stageOutputs.afterInputSnapshotSha256. These checks complement workflow validation and prevent accepting self-consistent but cross-bound persisted records. Reuse the existing native TestRun identifier domain including its established size bound; do not introduce a separate 256-character limit.

## First complete-review corrections

The complete `4b79ad97..c028b7c1` review requires four bounded corrections before integration. Existing successful evidence remains valid for unchanged behavior.

- Intent input parsing must reject any schema other than `stm32-source-change-intent/1`, including the unexpanded caller form. Direct/CLI rejection and MCP parity use existing adapters.
- Keep v1 describe/record scenario enums restricted to the v1 registry. Only attempt begin accepts the physical scenario. Do not extend AcceptanceRecord or add public tools.
- For physical build checkpoints, reuse the existing offline `probe.flash.load_fresh_firmware_facts` authority. Its build ID, ELF SHA and input snapshot SHA come from the same validated firmware identity. Bind the separately needed current full snapshot to those facts; never combine a context build ID with an independently read, unbound snapshot. Keep the v1 path and public context schema unchanged. Test mutation between facts validation and the later snapshot read; rev6 must not publish mixed identities.
- Authorization publication must revalidate its current attempt, Diagnostic revision/event head, complete before snapshot/derived intent and current time at the publication boundary. Resolve exact accepted retries before treating them as new mutations. Respect existing lock order: DiagnosticStore lock before EvidenceStore mutation lock, as Diagnostic checkpoint publication already follows that order. Hold the Diagnostic lock through the authorization publication; use its existing locked chain reader without reacquiring the lock. Fully validate Diagnostic references before entering the EvidenceStore lock, then perform final source/intent and time validation under the EvidenceStore lock before writing the new root. Do not call public diagnostic_show while holding the EvidenceStore lock: a Diagnostic load can repair its checkpoint and acquire that same lock. Do not add a lock framework or change either store schema. Authorization records an observed exact source intent; it does not lock an external editor or grant flash authority. Subsequent actual after-snapshot validation remains mandatory.
- Necessary new evidence is deterministic boundary injection for source/Diagnostic change and expiry between initial validation and publication, fresh-build/snapshot mismatch, unknown intent schema, and correct v1 versus v2 MCP enum dispatch. Preserve exact retry and concurrent single publication, and run the existing full persisted chain once after these corrections. No hardware is involved.
- Locked Diagnostic chain validation is not sufficient alone: preserve the existing `diagnostic_show` failed-run authority check through `_load_authoritative_run` / TestRunRepository (manifest, root and physical provenance), under the Diagnostic lock before entering the EvidenceStore lock. An envelope-only reference is insufficient.
- The final source/derived-intent and deadline check runs after `_put_envelope_locked` and immediately before `_publish_root_locked`; a rejected publication may leave an unreferenced envelope, but must not create the next revision root. Apply the firmware-facts/snapshot binding at this root-publication boundary for physical rev6 too. Add boundary injection during envelope publication, not only before acquiring the CAS lock. The final observation authorizes the bound snapshot; it is not a claim that unrelated external editors are locked.

## Publication lifecycle reconsideration after the second implementation review

Primary independently reproduced an expired rev6 root at `215c8c82`: the predecessor deadline was `2026-09-10T00:15:00.000000Z`; advancing the existing clock seam during the valid rev6 envelope write to `2026-09-10T23:59:59.000000Z` still published revision 6. This is the same publication-lifecycle issue left incomplete across the initial and correction reviews. Stop adding checks selected only by the originally reported endpoint; the integration invariant is frozen below before further implementation.

One shared physical pre-root validation boundary owns **every newly published revision with a predecessor**, including ordinary checkpoints and terminal rev7 as well as source authorization. After all envelope writes and relevant potentially slow source/firmware validation, it samples the current clock and checks the actual locked predecessor's deadline immediately before the root write. It must not check the candidate's replacement deadline or skip the check because the candidate is COMPLETED. Initial revision 0 has no predecessor; exact already-published response-loss retries remain read-only and return the same accepted checkpoint before new-mutation validation. Both existing publication paths must use this shared invariant; no new store, framework, public field, error code or v1 behavior change is needed. Keep existing Diagnostic-before-EvidenceStore lock order, full TestRun validation, source-intent guard and rev6 facts binding.

Reuse the full persisted-chain test to inject expiry during rev6 and rev7 envelope writes: no new root may appear, the predecessor stays authoritative, and resetting the injected clock allows the unchanged valid chain to finish. Existing rev5 expiry, source-change, facts/snapshot, CAS and exact-retry checks remain relevant. Review the final correction delta together with the prior complete reviews; do not restart unrelated matrices. Evidence for the concrete counterexample is `rev6-expiry-reproduction.json` in the primary's 215c8c82 verification records. This design reconsideration satisfies the two-round convergence gate; it is not hardware evidence or permission to broaden scope.
