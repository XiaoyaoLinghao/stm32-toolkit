## Public behavior

1. Generated tasks must use process argv (never shell concatenation), explicit `${workspaceFolder}` project binding and cwd. Build Debug/Release use the existing build CLI contract. Generate separate managed Flash Debug, Handoff Begin Debug and Handoff End tasks. No task dependencies, automatic build/flash/debug sequence, auto-run, recovery, reset or retry. Static launch.json remains empty: a live configuration comes only from a successful handoff, and IDE detach precedes original-ticket end.
2. Deterministic generation must not discover host programs, execute probes or freeze the coordinator's machine paths implicitly. Default task command is `${config:stm32-toolkit.executablePath}`, compilerPath is `${config:stm32-toolkit.compilerPath}`. These are explicit user-scope VS Code settings containing verified absolute native executable paths; generation must not override them with empty workspace settings or fall back to bare PATH names. Document exact setup, version verification and the fact that unbound defaults are not ready to run. VS Code variables do not prove runtime/MCP identity.
3. Provide optional paired configure arguments `--vscode-toolkit-path` / `--vscode-gcc-path`, MCP `vscodeToolkitPath` / `vscodeGccPath`, and Python keyword counterparts. Both supplied renders validated absolute native executable paths directly; neither uses the portable settings route. Reject partial/non-string/empty/control-character/relative/variable-containing/nonexistent/directory/symlink/reparse paths; on Windows require .exe, not shell scripts. Accept spaces and Unicode safely. Validation is static, not binary trust/version attestation. Structured `VSCODE_CONFIGURATION_INVALID` explains field/rule/remediation. Do not write machine paths into the project model. Optional immutable plan binding participates in plan identity, serialization, exact replay/revalidation and fresh re-plan; changed/omitted paths at APPLY cannot silently authorize another plan. Preserve existing configuration transaction/rollback and user-owned editor file behavior; user-owned files remain user-owned. New rendering is an intentional output change, not a template ownership bypass.
4. Add a narrow CLI adapter `ide task <flash|handoff-begin|handoff-end>` for generated tasks, not an MCP replacement. It takes required absolute project-root, data-root, session-id, probe; begin/flash take explicit `--confirmation` with `deny` or `authorize` (default deny); end takes the original ticket and explicit confirmation too, since reclaim may attach. Generated prompt defaults deny and names the operation. No stored authorization, prefilled probe, automatic enumeration or ticket persistence. An authorized task is one explicit invocation only. AI callers must already have applicable user authorization; a UI prompt cannot grant authority to the AI.
5. After context/confirmation validation and before calling any hardware workflow, flash/begin use the existing read-only `_load_fresh_firmware` admission to obtain buildId/ELF SHA from the complete current managed arm-debug evidence. Do not just parse two JSON fields. Preserve its original diagnostic code/details, including snapshot provenance refusal and build/input/artifact failures. Forward the exact pins and binding to existing flash/handoff workflows, which retain their own checks. No release fallback, automatic build, import, admission weakening or direct backend calls. End skips an additional adapter-level fresh-build admission and forwards the original ticket/binding to the existing end workflow. The existing end workflow still validates current firmware, flash evidence and ticket; changed source/ELF may be refused, and only its successful result proves reclamation. All action results, errors and handoff configuration/ticket return intact. Public CLI failures remain bounded structured JSON with nonzero exit.
6. Document managed arm-debug versus imported firmware routes, absolute executable verification, PLAN/APPLY with identical binding options, first failure stop, clean guidance, preserved editor files, path relocation/reconfigure, session/probe/ticket continuity, and actual VS Code/IDE validation still pending.
