# Keil readiness and independent probe discovery

User-authorized software slice, 2026-10-23. Accepted base: `89f76ee5551dfdc313f3f37d2d9e760af47daac8`. Primary owns specification, orchestration, independent review and acceptance; implementation and tests run through the existing Claude Code CLI configuration. No remote, runtime installation, or physical-target action is part of this slice.

## Public behavior

1. Add a read-only `keil preflight` CLI operation and `stm32_keil_preflight` MCP tool. Accept the same project-relative `uvprojx` and exact `targetName` selection as inspect/convert. Missing Git, missing HEAD, and dirty/untracked work must not prevent technical analysis. Return deterministic selected-project/target evidence, source hashes and the migration blockers (encoding, assembly, scoped compiler options, scatter/memory and manifest conflicts) using the same rules as the conversion planner. Reuse the existing containment, size and input-drift guards. Do not duplicate or weaken migration rules.
2. A completed preflight may contain blockers: distinguish successful analysis from permission/readiness to apply. Return explicit apply prerequisites and next steps; preflight produces no applicable plan ID, no patch application and no file changes. Invalid/unreadable/ambiguous input remains an error with exact cause. The existing convert plan/apply contract remains Git-bound, digest-checked and authorized; preflight never authorizes it.
3. `stm32_project_context` retains existing keys/booleans for compatibility, and adds structured per-capability explanations distinguishing available, blocked and not-evaluated. In particular, the constant false hardware capabilities mean not evaluated here, not that those tools do not exist. Keil recommendations identify the preflight tool and explain that entry-point availability does not establish migration readiness. Do not scan all source files inside context or enumerate probes there.
4. Hardware admission errors retain stable existing top-level codes where practical and add actionable details: field, rule/cause, relevant project kind/schema, and safe remediation. Do not collapse missing manifest, invalid schema, invalid session, target/backend and pin errors into empty details. Preserve meaningful lower-level error codes as cause metadata without exposing tokens or arbitrary exception text. Guidance must not recommend fabricating identity, changing hashes, deleting files, bypassing Git/authorization, or guessing a target.
5. `probe list` / `stm32_probe_list` enumerate probe descriptors with no requirement for a Toolkit manifest, configured build, debug backend, target or SVD. Keep the existing bound project-root, external-data-root, session, path and MCP client-root validation. Do not create a project manifest, acquire a lease, attach to a target, select a default probe, reset, halt, flash or write project files. Retain timeout/cancellation/cleanup semantics. For valid configured projects preserve the existing workspace identity; when it cannot be established, return `workspaceId: null` and an explicit unbound discovery status, never invent a project ID. Discovery does not imply target identity or flash readiness. Other hardware workflows retain their full project/target/firmware/authorization checks.

## Accurate VS Code / agent guidance

Update public MCP descriptions, existing migration/build/flash skills and user documentation together. An MCP-only consumer must learn the correct route from tool descriptions/context/results without requiring skill installation. Explain: context -> select exact project/target -> inspect/preflight -> address explicit blockers -> Git-backed plan -> review actual diff and current plan ID -> authorized apply -> configure/build. Preserve exact project/target arguments throughout; use only actual returned identifiers. A missing Git repository can still be diagnosed; establishing a Git baseline is an explicit project-owner decision. Non-UTF-8 input must not be silently decoded/re-encoded and ARMCC startup must not be blindly replaced. When a user asks only to see connected probes, call probe list without requiring build/flash. Probe discovery grants no board-modification permission. Build and flash skills must distinguish unavailable, blocked and unevaluated evidence instead of stopping solely on a legacy false hardware boolean.

## Exclusions

No Keil build backend, charset conversion, startup generator, external firmware import, non-Git build identity, VS Code extension execution, multi-RAM layout redesign, version bump, package/release rebuild, deployment or hardware qualification. Existing v1.2.0 release exceptions do not transfer to this change.

## Evidence and acceptance

Read the standard test procedure and current execution records. Use bounded offline pytest suites with temporary roots outside the repository; fake/injected probe backends only. Cover non-Git and unborn/dirty repositories, representative simultaneous blockers, clean eligible input, no mutations, selection/path containment, stale inputs and unchanged apply guards. Cover configured and unconfigured probe discovery, malformed/absent manifests, zero/multiple probes, invalid paths/session, backend failure/cancellation/cleanup and non-discovery hardware rejection. Verify CLI and MCP entry points, inventory, request-root authorization, structured readiness/errors and actionable guidance. Keep existing regression assertions, updating only deliberately changed behavior. Primary reviews the complete base-to-final diff in a clean exact-head worktree and independently runs the selected integration regressions. Do not claim actual VS Code UI, probe, flash or complete release qualification from these offline tests.
