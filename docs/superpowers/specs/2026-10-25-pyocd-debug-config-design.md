# PY-OCD-DEBUG-CONFIG bounded design

Accepted base `7b25b890f02892626c5ba6201bd3dec2712a95e4`; branch `codex/pyocd-debug-config`. Primary Codex owns specification, orchestration, independent complete-diff review and acceptance. Local Claude Code CLI retaining the existing configured provider/model owns implementation, tests and product guidance. The user authorizes offline configuration/diagnostic improvements in synthetic projects only. No original-project access, hardware, remote action, installation, runtime/global-skill or release-asset changes. No ownership exception.

## Public behavior

Extend the existing project configure workflow, CLI and MCP with an optional explicit pair: Python `debug_backend`/`debug_target`, CLI `--debug-backend`/`--debug-target`, MCP `debugBackend`/`debugTarget`. Both omitted retains the existing configure behavior and plan serialization. Both provided select the configuration-edit route. One alone, wrong scalar type, empty/whitespace value or unsupported backend fails with structured input diagnostics before writes. Backend must be exactly `pyocd`; target must match the existing hardware identifier grammar `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` without trimming, case-folding or coercion. Syntax validation is not a claim that a target is installed/supported or matches the physical device. No PyOCD discovery, import-time probe calls, package download, automatic target selection or Keil-device mapping.

The pair sets only `debug.backend` and `debug.target` in an existing valid Schema2/3 manifest. Preserve all other keys and values, including `svd`, `svdDevice`, `readableRegions`, linkerFragment, memory, source layout, identity and testing. Do not mutate migration/conversion evidence. Ordinary migration still emits `debug: {}` and remains valid for build-only use. The new configuration entry is the supported post-migration step; no migration parameters or new MCP tool are added.

PLAN is read-only and shows the explicit requested pair plus the `.stm32-project.json` change (before/after digest, sizes and full unified diff), together with the existing generated-file plan. Use optional `debug_configuration` and `manifest_edit` fields in GenerationPlan JSON; each is absent for the legacy route. `manifest_edit` contains path/status, before_sha256, after_sha256, before_size, after_size and unified_diff; raw bytes remain private. The manifest stays user-owned and must never be inserted into generated managed records. If the pair already equals the source values, preserve exact manifest bytes rather than rewriting formatting. Otherwise deterministic JSON serialization is allowed, with the complete formatting diff visible. PLAN ID binds source bytes, request, candidate bytes/model and generated output.

APPLY requires the same pair, the exact reviewed current planId and real boolean authorized=true, through the existing authorization boundary. Omitted/changed pair or changed inputs yields stale/invalid plan before writes. Replan from current source and validate the effective candidate with normal schema/post-schema checks. Apply the manifest edit, generated outputs and managed manifest in the existing single guarded staging/backup/replace/rollback transaction. Never write the manifest before planning or do an unprotected second configure phase. Preserve file modes, existing lock, input drift, generated-user-drift, containment/reparse and rollback protections. Refuse tampering of the optional fields, inconsistent bytes/hash/diff or any candidate changes beyond the two permitted debug keys. The direct core apply seam must enforce the same plan integrity, not rely only on workflow validation.

Keep observed source manifest bytes in plan.inputs as the **before** evidence; do not pretend candidate bytes exist on disk. The plan.model/model_sha256 and generated manifest describe the validated **after** model. Fresh checks explicitly distinguish source and candidate instead of weakening the ordinary no-edit stale-model comparison. Candidate loading should be a small shared bytes/payload validation seam, not temporary source writes or a general manifest-update framework. Duplicate keys, oversize/nonregular/reparse manifest files must fail closed in the editing route. Preserve the previous linkerFragment exact-byte guards. Old build/firmware identities become stale naturally after a manifest update; guide users to rebuild with --clean when needed, never repair hashes or receipts manually.

## Missing diagnostics

Use a shared pure debug-configuration diagnostic helper. Report both missing fields together; distinguish missing backend/target, unsupported backend and malformed target. Each diagnostic includes a stable code, field, rule and actionable remediation pointing to the real project-configure entry and explicit paired parameters. Preserve existing hardware error code `HARDWARE_INPUT_INVALID` and existing first-field/rule semantics, adding complete diagnostics/missingFields and current entry guidance; no new hardware behavior. Keep SVD-specific checks separate. No SVD or readable-region settings are invented or relaxed.

Expose additive `data.debugConfiguration` in configured project context and Keil preflight. It includes configured backend/target (null for the migration's planned build-only model), status (`configured` or `needs-user-input`), missingFields, diagnostics, targetSupport=`not-checked`, hardwareVerified=false and nextSteps. A valid pair means configuration is present only. For missing/invalid debug settings, affected managed flash/debug/monitor/target capabilityDetails are blocked with complete diagnostic reasons; preserve any existing Git/snapshot identity blockers and imported-route separation. Do not mark hardware capabilities true just because the pair is valid. Configure/build remain available for a valid fully absent debug spec; probe discovery stays independent.

Keil preflight reports the post-migration debug prerequisite as non-blocking readiness guidance, separate from technical migration blockers/planReadiness. No debug absence is converted into a migration failure, no Git dependency is introduced, and no plan ID or authorization is invented. Context/model-load failures keep their existing broader schema contract.
