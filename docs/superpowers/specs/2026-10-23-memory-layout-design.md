# Explicit multi-RAM section placement — approved design

Accepted base: 8d0334462291b84f24822e4dfafc5e575e1d9cd1. STARTUP-GCC is accepted; this is the next authorized local slice. User authorized local multi-RAM support, CLI implementation/tests and primary review; no original project mutation, deployment, remote or hardware. This slice must provide real placement of managed .data/.bss/.heap/.stack, not merely declare extra MEMORY regions.

Add an optional explicit managed memory layout assigning each of data/bss/heap/stack to a named writable memory region, with deterministic selection of a non-writable executable Flash region (or an explicit flash role where ambiguous). Validate all named regions, duplicates/overlaps, bounded 32-bit address arithmetic, writable/readable roles and required fields. Never infer DMA accessibility from writeability or place buffers into CCM automatically. Preserve actual region names/origins/lengths from inspection; no invented external SRAM region.

For new Keil migrations with more than one RAM region and no complete placement decision, preflight and plan return a structured actionable MEMORY_LAYOUT_REQUIRED blocker listing actual candidate names/ranges. Allow the explicit layout to be passed through the existing public CLI/MCP preflight/convert requests (precise same options in preview/plan/apply); include it in plan identity and fresh re-analysis. A caller may explicitly keep all standard sections in one RAM and leave another unused, but this is a displayed choice, not an inferred default. Carry the layout into the proposed project manifest and typed model/schema. Existing native-linker projects continue to own their linker script; do not rewrite or pretend to control their layout. Existing managed single-RAM behavior stays compatible; multi-RAM managed configuration without an explicit plan must fail with a useful field/remediation instead of silently choosing the first RAM.

Render each standard section in its selected region. Keep .data load address in the chosen Flash and its load/start/end symbols consistent; .bss clearing symbols must cover the chosen .bss wherever it resides. Preserve user-selected/original stack/heap sizes and 8-byte stack alignment. Require link-time bounds/overlap diagnostics and actual MAP/ELF verification; preserve all fixed section addresses from reviewed existing migration evidence. Do not reinterpret fixed NOLOAD sections as initialized data or promise they are automatically zeroed; arbitrary extra initialized/zero regions need a separate supported startup table contract and remain explicitly unsupported. Nonliteral ARMCC absolute expressions, unknown scatter placement and external SRAM outside declared regions remain blockers, with exact actionable diagnosis. This implementation must not silently drop those declarations or claim the real project is fully migrated.

Actual original facts: IROM0x08000000+1MiB; IRAM0x20000000+192KiB; IRAM2/CCM0x10000000+64KiB. MALLOC uses fixed CCM addresses and external SRAM0x68000000; some address expressions include macros. These original inputs stay read-only. Safe software verification uses synthetic equivalents with explicit decisions, not a guessed conversion of the entire robot project.

CLI owns tests: no-layout multiRAM preflight/configure blockers; explicit layout round-trip/schema invalid selections; all-main-RAM declared choice; data in main SRAM and bss/stack in another RAM with corresponding startup initialization symbols; heap/stack sizes and alignment; region order must not select executable RAM as Flash; overlaps/overflow/too-small regions fail; fixed addresses preserved or blocked; option/plan/input drift rejected; native linker unchanged; public CLI/MCP arguments and exact VS Code guidance. Use existing ARM GCC to link small generated multiRAM ELF, check section VMAs/LMAs, reset-vector stack pointer, init symbols and MAP usage. This is offline linked-image evidence, not proof that a physical board's CCM/external memory initializes or runs correctly.

Allowed scope after finalization: project model and both current schema copies; migration options/analysis/planner/preflight/apply/public adapters; generation/configure and root/packaged linker templates; required layout bounds validation in build ELF/MAP only if a concrete integration gap exists; targeted tests/synthetic fixtures; relevant skills/user/architecture docs; report. No Monitor/probe protocol rewrite, firmware import, native UV4 backend, automatic install or real hardware. Finish with code and separate report commits; primary independently reviews full diff in clean exact-head worktree and runs selected integration evidence.

Frozen interface decisions for dispatch: public memoryLayout is an optional object; CLI --memory-layout takes its JSON object. The object has exactly five required string keys flash, data, bss, heap, stack, each naming an existing region. Manifest memory.layout stores the same mapping, with a typed immutable representation. Flash must be readable/executable/non-writable; RAM roles must be readable/writable. With no explicit mapping, preserve single-RAM/single-Flash behavior only; return an actionable decision requirement when either role is ambiguous. Reject an explicit layout with generation.nativeLinkerScript rather than pretend to control native-owned sections. Existing native configurations without these options remain unchanged. Keep the previously added memory.stackSize/heapSize and generation.runtimeInitialization semantics. CLI malformed/duplicate JSON keys, unknown keys, bad types and incomplete mappings are rejected before planning with stable details; do not silently fill missing choices.


Additional interface decisions for the implementation dispatch:
- Use one shared layout-validation/selection implementation (a small memory_layout.py module is allowed) across model/configuration and migration, rather than duplicating role rules. The immutable layout representation has exactly five named roles. No arbitrary expressions or linker fragments are accepted as region names.
- Successful preflight adds analysis.memoryLayout with status (implicit, explicit, or requires-selection), layout (the resolved five-role mapping or null), and candidates (flash and ram lists containing actual name/origin/length/attributes). For absent options on ambiguous managed memory, return the ordinary technical blocker MEMORY_LAYOUT_REQUIRED and status requires-selection while still returning the other migration blockers. The PLAN response must also expose the chosen layout or required candidates alongside its existing blockers; do not put the only useful selection information inside a prose error. Explicit malformed input remains a structured input failure. Bind the exact explicit request to plan identity and fresh apply; missing options versus an explicit all-main-RAM choice are distinct reviewed requests.
- MEMORY_LAYOUT_REQUIRED details for configure and analysis evidence name the unresolved roles and actual candidates plus remediation. Logical invalid choices use MEMORY_LAYOUT_INVALID with field/rule/remediation; existing schema-level PROJECT_SCHEMA_INVALID remains valid for malformed manifest JSON/schema. CLI malformed/duplicate-key JSON must be rejected before inspection with structured details, not a raw traceback. Public snakecase internal adapter arguments may differ from the documented memoryLayout MCP field, but registered tool schema/call tests must exercise the camelcase public interface.
- Keep absent layout fields out of legacy model hashes and preserve generated bytes for a single unambiguous flash/RAM manifest with no new options. New startup runtime/size behavior stays exactly as accepted. Native linker configurations with no explicit layout keep their ownership path; do not require the new managed selection there.
- New public options and examples are current-source/candidate behavior. Published v1.2.0 runtime is unchanged and lacks them. VS Code guidance must inspect actual connected tool schemas before sending optional parameters, preserve identical startup/layout choices through preflight/plan/apply, and read concrete blocker details rather than invent region choices.
- Preserve preflight aggregation: structural model validation may accept omitted memory.layout so analysis can return all blockers. Enforce unresolved managed role selection at conversion analysis and configuration, not by throwing from manifest-proposal validation before other diagnostics are returned. Explicit invalid mappings still fail validation.
