## 1. 权威与取代关系

本文是 STM32 Toolkit 0.7–1.0 的单一跨版本产品设计，冻结 Agent、VS Code、CubeMX、CubeCLT、构建、Probe、Monitor、Test、Diagnostic、Acceptance 和 Release 的职责关系。

- CubeMX、CubeCLT、ST VS Code extension、CubeProgrammer、PyOCD 和 Cortex-Debug 可以共享模糊职责。

旧计划保留为历史需求来源；与本文冲突的任务分解、运行时、工具边界和验证层级不再执行。

## 3. 产品定位

STM32 Toolkit 是一个在 VS Code 工作区中由人和 Agent 共同使用的本地 STM32 开发控制面。Agent 通过标准 MCP 或 CLI 调用 Toolkit；Toolkit 安全编排外部生成、构建和调试工具，并提供项目隔离、身份、授权、测试、证据、Monitor 和诊断闭环。

Claude Code 是保留的薄客户端适配器，不是核心产品唯一宿主。其他能够提供项目根并连接 stdio MCP 的 Agent 可以复用同一 Toolkit runtime 和公共接口。不同 Agent 不得拥有不同的 Project、Probe、Monitor、Test 或 Diagnostic 实现。

### 3.1 1.0 用户可见目标

在一个受支持的 Windows VS Code 环境中，用户可以让 Agent：

1. 检查并一次性迁移一个真实 Keil 工程，或从 MCU/`.ioc` 创建一个新的 CubeMX 工程；
2. 使用 CubeCLT 中的 ARM GCC/CMake/Ninja 生成可复现固件身份；
3. 通过 Toolkit Probe Service/PyOCD 安全烧录、观察和运行 Target 测试；
4. 在需要人工交互时把同一 Probe 交接给 VS Code Cortex-Debug；
5. 从失败测试和 Monitor/Fault 证据形成诊断，绑定授权源码修改，重新构建/烧录并验证修复；
6. 保存可审查的项目、固件、板卡、Probe、测试和诊断证据，而不把 replay/fake 冒充物理结果。

### 3.2 非目标

0.7–1.0 不：

- 维护 Keil 与 GCC 双向同步或写回 `.uvprojx`；
- 把 STM32CubeIDE 或 ST VS Code extension 设为产品依赖；
- 同时支持 CubeProgrammer、ST-LINK GDB Server、OpenOCD 和 PyOCD 多个权威硬件后端；
- 建立第二套项目模型、Probe controller、Monitor、Evidence、Test、Diagnostic 或 Release controller；
- 手工维护所有 STM32 MCU、pack、startup、linker、HAL/LL 数据库；
- 承诺所有 Keil 工程、STM32 系列、TrustZone、双核、外部存储或 Probe；
- 恢复 Python 3.10；
- 把 Linux 或 macOS 纳入 1.0 的正式兼容声明；1.0 的参考安装与实体硬件验收环境为 Windows，已有跨平台代码与历史证据继续保留，新增平台支持留给后续版本；
- 把发布、远程 Git 或实体硬件权限隐含在实现批准中。

## 4. 唯一工具职责

| 组件 | 唯一职责 | Toolkit 边界 |
|---|---|---|
| VS Code | 编辑、构建入口和人工调试界面 | Toolkit 生成/验证工作区配置，不控制编辑器私有状态 |
| Agent client | 解释用户意图并调用 MCP/CLI | 只传公共请求，不实现 STM32 业务逻辑 |
| STM32CubeMX 6.18 | 从 MCU/`.ioc` 生成 pin、clock、peripheral、startup、HAL/LL 和原生 CMake 工程 | 只由授权 creation apply 适配器调用 |
| STM32CubeCLT 1.22.0 | 提供 ARM GCC、CMake、Ninja、CubeProgrammer、ST GDB server、target/SVD 事实 | 0.7 使用 GCC/CMake/Ninja/事实；包含某工具不代表它自动成为权威后端 |
| CMake/Ninja/ARM GCC | 配置、增量构建、编译和链接 | 复用现有 managed build 和 FirmwareIdentity |
| PyOCD | 唯一生产 Probe backend | 由 Probe Service 独占会话、烧录、读取和 transport |
| Cortex-Debug | VS Code 人工 GDB UI | 只通过一次性 PyOCD attach handoff 获得 Probe |
| Monitor | 用户与 Agent 共用的观察和比较界面 | 只读消费公共身份与证据，不成为项目真相源 |

CubeProgrammer 和 ST-LINK GDB Server 在 CubeCLT 中保留为环境事实，但 1.0 前不作为产品 backend。增加任一 backend 必须证明它替代 PyOCD 的明确范围，而不是增加平行硬件路径。

## 5. 系统结构与数据流

```text
VS Code / Agent adapter
        |
        v
generic CLI + project-bound MCP
        |
        +--> ProjectCreation service --> CubeMX adapter
        |          |                         |
        |          +--> ownership manifest <-+
        |
        +--> existing Project/Build service --> CubeCLT CMake/Ninja/GCC
        |                                           |
        |                                      FirmwareIdentity
        |
        +--> existing Probe Service --> PyOCD --> selected probe/target
        |          |                     |
        |          |                     +--> flash/read/transport
        |          +--> one-time handoff --> Cortex-Debug
        |
        +--> Test/Evidence --> Diagnostic --> Monitor/FixVerification
```

### 5.1 新工程创建流

```text
MCU/board/.ioc request
-> read-only environment and input discovery
-> canonical CreationPlan + plan/action digests
-> explicit single-use authorization
-> revalidate CubeMX, inputs and destination
-> generate in isolated staging
-> validate CubeMX native output and ownership
-> atomically activate destination
-> reuse existing project configure/build
-> publish ProjectIdentity + FirmwareIdentity
```

### 5.2 用户代码所有权

- CubeMX 拥有它生成的 startup、system、HAL/LL、pin/clock/peripheral 初始化和明确生成区域。
- Toolkit 拥有它声明的 project manifest、managed build/VS Code 文件和生成所有权清单。
- 用户/Agent 拥有应用和测试代码，推荐目录为 `App/` 与 `Tests/`。
- 重新生成前必须比较 generator/version/input/file digests；用户漂移不被静默覆盖。
- 现有 Keil→GCC 工程不被 CubeMX 自动导入、重生或改模。

## 6. 公共模型、权威来源与错误语义

### 6.1 新增公共模型

| 模型 | 权威内容 |
|---|---|
| `ToolSupportProfile` | 明确允许的 CubeMX/CubeCLT/Python/VS Code/extension 路径、版本和摘要 |
| `CreationRequest` | MCU/board/`.ioc`、HAL/LL、目标目录和覆盖策略 |
| `CreationPlan` | 规范化请求、输入/工具摘要、目标库存、预期输出、所有权政策、expiry、plan/action digest |
| `GenerationResult` | 原生输出库存、生成器证据、所有权 manifest、激活/回滚结果 |
| `AcceptanceScenario` | 版本化纵向步骤和所需身份/授权，不是新的 controller |
| `AcceptanceRecord` | 场景执行引用和最终 verdict，不复制底层 Evidence |

`ToolSupportProfile` 是 server/runtime 启动时冻结的机器配置。MCP 产品请求不得携带可执行
文件路径、命令或环境覆盖；CLI 的显式 profile 选择是本机操作员入口，profile 文件必须通过
既有 data-root/path 安全边界。一次会话中工具事实发生变化时，原 plan 失效并要求重新规划。

### 6.2 唯一权威来源

- 项目逻辑身份：`.stm32-project.json`；
- 新工程生成来源与文件所有权：project-local generation ownership manifest；
- 固件身份：现有 FirmwareIdentity；
- 外部工具支持事实：显式 `ToolSupportProfile` 与本次执行捕获的版本/摘要；
- Probe/硬件状态：现有 Probe Service/lease；
- Test、Evidence、Diagnostic、Monitor 与 FixVerification：沿用 0.6 单一权威来源；
- Release qualification：release ledger，不写入产品状态。

### 6.3 失败分类

所有公共失败首先属于以下之一：

- `PRODUCT`：冻结的产品行为被违反；
- `INPUT`：请求、工程或 `.ioc` 无效/不支持；
- `ENVIRONMENT`：CubeMX/CubeCLT/VS Code/Python 缺失或版本不符；
- `PLATFORM`：操作系统或平台专属能力不可用；
- `INFRASTRUCTURE`：测试、验收 runner、归档或报告工具失败；
- `HARDWARE`：命名板卡/Probe/传输实际失败；
- `REPORT`：产品与证据有效，仅报告载体错误。

环境、基础设施和报告失败不得自动改写产品候选结论。

## 7. 版本职责与纵向切片

### 7.1 0.7：从请求到可维护的新 GCC 工程

#### VS07-A：创建计划与环境真相

**用户行为：** Agent 对 MCU/board/`.ioc` 请求执行只读计划，得到明确可执行或可修复的结果。

**包含：** Agent-neutral public request、Python 3.12 边界、CubeCLT 元数据与显式路径发现、CubeMX 独立发现、VS Code/extension 准确诊断、closed `ToolSupportProfile` 与 `CreationPlan`。

**失败：** 工具缺失、版本不符、路径冲突、无效 `.ioc`、目标冲突分别返回可操作错误；不写目标目录、不运行 CubeMX。

**验收：** 当前主机准确识别 CubeCLT 1.22.0 和缺失 CubeMX；安装 CubeMX 后同一请求形成稳定 plan digest；CLI 与 MCP 同行为。

#### VS07-B：授权创建并构建

**用户行为：** 用户授权一个计划后得到可由 VS Code 和 Agent 构建的 GCC 工程。

**包含：** CubeMX 6.18 CLI adapter、single-use authorization、staging、native CMake output validation、ownership manifest、atomic activation、现有 configure/build/FirmwareIdentity 复用。

**失败：** 输入或工具漂移、超时、非零退出、部分输出、目标竞争、激活或回滚失败均 fail closed；失败证据保留，目标不出现半工程。

**验收：** 一个受支持 `.ioc` 和一个 MCU-based 请求各自生成、配置并完成 Debug/Release 构建；重复授权和 direct adapter call 被拒绝。真实硬件不在本切片。

#### VS07-C：安全重新生成

**用户行为：** 用户修改 `.ioc` 后可以预览并授权重新生成，同时保护用户代码。

**包含：** source/generator/manifest drift、generated/user/Toolkit ownership、diff preview、transactional regeneration、rollback 和 Keil-path isolation。

**失败：** 未声明用户漂移、generator major/version 变化、未知生成文件或越界路径要求人工决策；不静默覆盖。

**验收：** 用户 `App/`/`Tests/` 内容保持不变；合法 CubeMX 变更更新生成区域并重新构建；Keil→GCC fixture 字节和能力不变。

### 7.2 0.8：两个纵向场景的可恢复验收

#### VS08-A：统一场景适配器

在现有 0600 控制与 Evidence 生命周期上增加两个版本化 scenario adapter：legacy Keil migration 和 new CubeMX project。软件阶段使用真实本地工具与 fixture/replay 完整运行，但明确标记非物理结果。

#### VS08-B：恢复、隔离与人类检查点

验证中断恢复、每步超时、lease/target 清理、两个 workspace 并发隔离，以及烧录、源码修改等侵入操作前的人类授权。它不是新的 scheduler/controller/provider platform。

0.8 完成标准是两个软件场景可恢复、可查询、无状态串扰；不是硬件 PASS。

### 7.3 0.9：可安装、可升级、可维护的发布候选

#### VS09-A：运行时与 Agent 适配收敛

统一 CPython `>=3.12,<3.13`、通用 `STM32_TOOLKIT_*` runtime、Claude 薄适配器、标准 MCP 配置示例、doctor/tool discovery、package/Monitor/plugin/Skills/MCP inventory 版本。

#### VS09-B：GitHub 安装、升级、安全与发行物

完成干净 Windows profile 的 pinned-source 安装、schema/runtime 升级与安全降级拒绝、恶意输入、路径/命令/token/lease/audit 安全测试，以及 reproducible wheel/archive、Monitor assets、checksums、SBOM、licenses、compatibility 和 troubleshooting。

0.9 不要求发布到远程；发布、tag 和 GitHub Release 仍逐次授权。

### 7.4 1.0：统一实体硬件和真实项目验收

1.0 不增加新产品平台。它使用一套命名资产同时关闭：

- 历史 0.4 Probe、attach/read、flash/readback、handoff/reacquire、typed register/Fault 和 CLI/MCP 硬件债务；
- 0.6 mailbox/RTT/UART/semihosting、Target、Monitor、diagnostic、failed-before/fixed-after 债务；
- 一个真实 legacy Keil→GCC 场景；
- 一个真实 new CubeMX project 场景。

两个真实场景必须执行 create/migrate、build、flash、observe、reproduce failure、collect evidence、diagnose、authorized source fix、rebuild/reflash、Target test 和 Monitor assertion。可以使用同一受支持板卡/Probe，但每个场景必须绑定自己的 project/firmware identity。

## 8. 开发节奏与所有权

1. 任一时刻只有一个共享核心产品切片处于实现状态；0.7 的 A→B→C、0.8 的 A→B 和 0.9 的 A→B 顺序执行。
2. 只读研究、环境盘点和互不写同一状态的审查可以并行；共享 Project/MCP/CLI/Probe 代码的产品实现不并行。
3. 每个切片在单独 clean worktree、精确 accepted-base 上由一名 Luna/max 实现者完成。
4. Luna 只接收一个自包含、1–3 个工作日可完成的产品行为；任务不得包含整个版本或多个状态机重写。
5. Sol 主代理独立审查 accepted-base 到 final-head 的完整 diff，并运行比例适当的切片或集成验证。
6. finding 返回同一分支和同一切片；同一问题两轮不收敛，停止修补并返回接口/整体设计。
7. 规格解决跨模块歧义；实现者不得通过新增模式、fallback、provider 或兼容范围自行补设计。

### 9.3 发布级

- 完整 Python 3.12 suite/coverage；
- UI unit/E2E；
- package/install/upgrade/security/license/SBOM；
- 兼容矩阵；
- 1.0 实体硬件与证据归档。

发布检查只有在以下书面触发器出现时才前移：

| 触发器 | 前移检查 |
|---|---|
| 修改 public schema/protocol/version migration | 受影响兼容与升级测试 |
| 修改 process/path/token/lease/authorization | 对应安全与并发测试 |
| 修改 package/bootstrap/runtime/asset inventory | 干净安装或 wheel smoke |

## 10. 止损规则

- 验证计划规模不得明显超过产品 diff；若确有必要，计划必须说明风险与预计成本。
- 一个切片不得拥有类似完整发布流程的多级 Gate。
- 报告格式问题不自动使产品候选失效。
- 环境、平台、基础设施、硬件和产品失败分别记录。
- 只重跑受影响验证层级；未受影响 PASS 保留。
- 同一问题连续两轮不收敛，回到接口或设计。
- 切片超过三个工作日或需要递归任务树，暂停实现并重划边界。
- 连续两个切片中验证/报告时间超过产品实现时间，暂停产品工作做治理复盘。
- 新依赖、新 backend、新 provider 或新兼容范围必须说明它替代什么以及真实用户触发。
