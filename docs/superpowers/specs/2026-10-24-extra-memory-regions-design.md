## Public behavior

Add optional `memory.extraRegions` to Schema 2/3 manifests. Every entry explicitly supplies exactly `name`, `origin`, `length`, `attributes`; no default origin, size, name or access is inferred from a device, address, source expression or board. This slice supports external SRAM: `attributes` is `rw-` or `rwx`, never a new programmable Flash region. Bound the list to 32 entries and its JSON option to 64 KiB. Names are linker-safe ASCII identifiers, at most 64 characters. Origin and length are exact JSON integers, never booleans, strings or fractional numbers; origin is 0..0xffffffff, length is 1..0x100000000 and the half-open end must not exceed 0x100000000. Reject unknown/missing fields, repeated/case-colliding region names, overlap with declared base or other extra regions, and unsafe linker names. Adjacency is allowed. Explicit zero capacity is not an omission.

Use one shared validation/composition implementation for the manifest and migration path. The persisted manifest keeps Keil/base `memory.regions` and explicit `memory.extraRegions` separately. On loading, normalize once so `ProjectModel.memory.regions` is the full validated ordered base-plus-extra region tuple; existing configure, fixedSections, linker, ELF/MAP, build identity and downstream consumers use this same tuple, without ad-hoc append lists or separately inferred memory maps. If additional typed metadata is needed it must not create a second independent region interpretation. Omitted/empty extras keep all historical bytes and identity payloads. Nonempty extras participate in model/configuration/build identity through the normalized map and original manifest input; changes require normal reconfiguration and stale-output guards, never edited managed hashes.

Expose the same explicit input for Keil preflight and conversion PLAN/APPLY: MCP `extraRegions` as a real list of objects, CLI `--extra-regions` as a JSON list string, core `extra_regions` as an immutable normalized value. Bound parsing, reject duplicate JSON object keys, malformed/oversized/nested JSON and repeated CLI option use. Never coerce types through the MCP schema: choose an annotation/schema that preserves raw scalar values for shared validation (for example list[dict[str, Any]]), and document framework-level rejection versus Toolkit errors. No new MCP tool or inventory count. Invalid options produce structured `EXTRA_REGIONS_INVALID` with portable field/rule/remediation; manifest validation uses its established structured error family. Cross-region validation happens against the actual inspected/model base regions, before any write. No original `.uvprojx` or inspection evidence is changed to pretend the external region came from Keil.

Bind the normalized nonempty extra-region request into immutable migration plan identity, validate its shape in apply, retain it for fresh replan, and expose it in preflight `analysis.extraRegions`, PLAN `extra_regions`, and conversion report `extraRegions`. Omitted/empty values are the same no-extra request and preserve historical plan bytes. A changed or omitted nonempty request invalidates the approved plan; tampered typed plans are rejected before writes. Carry exact options in next-step guidance. Propose the entries under `memory.extraRegions`, not by modifying the inspected base region list. Preflight stays Git-free/read-only; PLAN/APPLY retain their Git, explicit authorization, digest, fresh-input and transactional guards.

Use the combined map for migration fixed-address admission and layout candidates as well as configure fixedSections and artifact validation. Missing extras leave `MIGRATION_FIXED_SECTION_OUTSIDE_MEMORY` actionable: request the owner-supplied exact map, never suggest a guessed length. Combined extra RAM creates additional RAM candidates; the existing `memoryLayout` selection requirement remains, with actual base and extra candidates. Do not implicitly place `.data`, `.bss`, heap or stack in new RAM. An explicit mapping may name a valid extra RAM, with unchanged startup initialization semantics. Native-linker ownership is unchanged: model validation/artifact bounds include extras, but the user's native linker is not rewritten and cannot also claim managed `memoryLayout`.

Managed linker generation emits every normalized region once and places fixed NOLOAD sections through the existing template. Keep fixed sections NOLOAD; do not invent copy/zero tables, controller initialization, reset sequences or board timing. The owner must arrange external-memory initialization before access; external stack use can require earlier bootstrap than SystemInit, and NOLOAD buffers are not promised initialized. Runtime correctness is not proven by offline linking. The model declaration does not authorize hardware access, add a Flash algorithm or bypass chip Flash-map/provenance checks. Writable extras must not become Flash candidates or allow programming external SRAM as Flash.
