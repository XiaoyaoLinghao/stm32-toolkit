## Contract

1. A valid managed GCC/CMake project can build from an exported/non-Git directory, an unborn repository, or when Git is missing/unavailable. Exact input snapshots, model/managed-file validation, authorization, locks, compiler timeout/cleanup, ELF/MAP validation, before/during/after input-drift detection and stale-output defenses remain mandatory. Git failure alone is not a build failure. Never initialize/commit/change Git state or invent a commit hash.
2. Preserve the current schema-1 identity/record bytes and build-ID semantics when full Git evidence is available. Keep the strict `git_evidence` API for existing consumers; add a build-specific optional collector which maps only Git availability errors to bounded diagnostics. Unknown provenance is not `gitDirty=false`; represent unavailable head/dirty as JSON null, never `str(None)` or zero/fake hashes.
3. For unavailable Git, emit a distinct schema-2 firmware identity and successful build record. The identity explicitly names `sourceBaseline: "input-snapshot-v1"`, retains inputSnapshotSha256 and all existing project/target/toolchain/artifact fields, and includes bounded gitEvidence with unavailable status, stable code and rule. Both gitHead and gitDirty must be null. Hash the mode/diagnostics into the identity normally; validate both schema copies with strict conditional contracts. Existing schema-1 acceptance must not be widened to nullable/fabricated Git fields. Make typed FirmwareIdentity serialization round-trip faithfully.
4. Context recognizes valid schema-2 build/result evidence as fresh only when identity digest, record fields, current exact input snapshot, target/preset/model, ELF/MAP hashes and safe regular contained paths all agree. Schema-2 freshness does not require a Git subprocess. Preserve schema-1 Git freshness behavior. Report baseline/provenance explicitly to callers; Git unavailable must not be interpreted as clean.
5. Incremental/no-op output reuse must prove a compatible current prior success record, matching identity/source baseline and inputs/artifacts. Unknown/tampered/cross-schema records, changed sources, stale artifacts and failures remain rejected. Changing provenance mode cannot silently reuse an incompatible prior identity. Test repeated non-Git builds as well as failed/stale/tampered paths.
6. This slice enables build and build freshness only. Existing flash/debug/Monitor/acceptance protocols require Git-shaped provenance. Do not fabricate a Git commit to admit a snapshot identity. At the shared firmware admission boundary reject valid snapshot identities with a stable actionable `FIRMWARE_PROVENANCE_UNSUPPORTED` result before probe/lease/attach and explain the supported build-only scope. Keep all current Git-backed hardware behavior. Expose this limitation in context capabilityDetails and public MCP/VS Code guidance instead of falsely suggesting flash readiness. Broader hardware protocol versioning is a separate future slice; do not modify Monitor/acceptance wire schemas here.
7. Migration planning/apply still require their committed Git baseline. Non-Git build support does not authorize migration writes or imply automatic migration. Update build/flash guidance, MCP descriptions, architecture and user guide with the exact new fields and source-only runtime limitation. No new tool names, version bump, release/install/remote actions or physical operations.
