# STM32 Toolkit 1.0 local release

Status: authorized by the user's persistent goal: finish VS10-B and continue to
1.0 local release readiness without repeated approval; retry only after a stated
recovery condition or correction. VS10-B is accepted at
`1df30a0f4070805488687a67f907dbaa1867d681`. The full product accepted base for this
release slice is that commit; subsequent fixture-portability work is separately

Luna/max agent, with independent review. No remote operation is authorized here.

## Three user scenarios

1. A Windows x86_64 / CPython 3.12 user installs a pinned 1.0.0 offline bundle in a
   fresh data root, obtains healthy CLI/MCP/Monitor/launcher checks, and can follow
   the deployed-IDE troubleshooting instructions without relying on the author's
   old temporary files or machine-specific paths.
2. An existing single 0.9.0 runtime is explicitly upgraded by Repair to 1.0.0.
   Bootstrap refuses existing installations; failed promotion/check/state write
   restores the original runtime and exact state bytes. Multiple legacy runtimes,
   downgrade and same-version different-source replacement remain refused.
3. The release owner builds twice from the same clean committed source and pinned
   wheelhouse, verifies identical 13-file artifacts, complete checksums, licenses,
   SBOM, assets and compatibility, and binds the final release to actual A/B
   physical acceptance without inventing a new physical run.

Non-goals: new features, hardware, backends, supported platforms/Python versions,
sampling-frequency upgrades, generic release frameworks or remote publication.
Existing hardware authorization applies only when a necessary named release gate
requires it; first reuse valid evidence with explicit source/contract mapping.
No Option Bytes, mass erase, probe-owner stealing or unrelated process termination.

## Version and trust contract

Product SemVer becomes `1.0.0` across runtime `__version__`, Toolkit/Monitor wheel
metadata/dependency, UI package/lock, plugin, setup and both launchers. Monitor and
protocol product-version values continue to derive from the canonical runtime
version. Evidence/project/protocol schema numbers are format contracts; do not
renumber unchanged schemas merely for the product version change. Project-schema
current/previous support remains unchanged.

Keep the existing bounded builder and policy filenames
`tools/release/build_0900_artifacts.py` and `release_0900_policy.json` as stable
entry paths, updating their current product identity to 1.0.0. The historical
filename is documented, not a claim that produced packages remain 0.9.0. Do not
copy the engine or add an importing wrapper: setup executes verified utility and
policy bytes in memory, so an unpinned imported engine would expand that trust
boundary. Historical 0.9 reproducibility belongs to its historical commit and
artifacts; the current 1.0 source need not rebuild old product metadata.

The manifest remains `stm32-toolkit-release/1`, now closed to productVersion
1.0.0; runtime state remains `stm32-toolkit-runtime-state/1`. The existing builder
constant, policy.version and release JSON schema must agree; add a bounded
consistency check/test rather than a new version registry. Selected third-party
pins, Python range, PyOCD 0.45.1, 48 MCP operations, 8 Skills, license policy,
13-file inventory, deterministic ZIP rules and no-network builder behavior remain
unchanged. Output filenames/prefixes use 1.0.0. Setup's two trust hashes must match
the exact shipped utility/policy bytes from Git archive (LF), not an accidentally
different Windows checkout representation. Preserve in-memory verification and
changed-after-read protection.

Active runtime becomes `DATA_ROOT/runtime/1.0.0`; recognized legacy versions are
0.9.0, 0.5.0 and 0.3.0. The existing Repair transaction owns staging, quarantine,
promotion and rollback; no parallel installer. Old state with active/highest 0.9
is repairable to 1.0, successful generation increments once, higher installed
versions refuse downgrade, and a different manifest/source at active 1.0 remains
source-conflict. Old evidence stores, project files and firmware are not migrated
or rewritten by this version change.

## Verified legacy-producer compatibility correction

Offline reproduction in `r10/e/legacy-producer-reproduction.json` calls existing
`load_project_model` and `plan_project_configuration` on an isolated v2 fixture
whose producer is 0.9.0. Schema loading succeeds; the plan refuses it with
`GENERATION_MODEL_INVALID`, `generation.version/value`. The same exact-version
gate exists in build admission and managed-manifest parsing. Installer Repair
does not change these project files, so runtime-only promotion would strand an
otherwise supported existing project. This is a product compatibility gap, not
new hardware evidence or permission to relax hardware provenance.

Three bounded scenarios supplement the release contract:

1. Existing schema v2/v3 projects with exact producer 0.9.0 and generation template
   1 can be planned read-only, applied only through the existing guarded configure
   transaction, and built through the existing public build workflow under 1.0.
   Project producer metadata remains truthful and unchanged; newly generated
   managed manifests and newly published firmware identities name 1.0.0.
2. User-edited managed files, malformed prior manifests, unexpected template/schema
   versions, unknown producers, and stale plan/input hashes retain their current
   refusal and rollback behavior. The exact generation-reader allowlist is current
   1.0.0 plus prior 0.9.0, not an arbitrary SemVer range. Non-string version input
   must produce the existing structured refusal rather than a Python type error.
3. Old firmware identities, Probe endpoints, handoff state and Monitor provenance
   retain their exact-current-version checks. A new explicit build supplies current
   identity; this correction never relabels old physical evidence or connects a
   probe. Installer still never rewrites a project or firmware.

One shared bounded producer predicate belongs to the existing
`generation/managed_files.py` and is reused by `generation/configure.py` and
`build/runner.py` at their three admission checks. Existing generation templates,
schema numbers, ownership/hash validation, public API, mutation locks and build
publication are unchanged. Current accepted 0.9 generation/template/build logic
and this identity candidate have no other differences in these modules; the
compatibility grant is specifically for that unchanged template-1 contract.
Do not add a migration framework, silently edit generatedBy, widen endpoint or
firmware acceptance, or change cache/freshness logic without separate evidence.

The same Luna/max release owner additionally owns those three product modules and
their existing `test_generation.py` / `test_build_runner.py` tests. Reuse current
fixtures and public functions: prove v2/v3 0.9 plan/apply/build, current identity
publication, retained user-edit/unknown/future/type/hash refusals, and the existing
old firmware-identity rejection without hardware. Current release docs must give
the explicit configure/build/new-session sequence and preserve the runtime-only
Repair boundary. Independent review covers this final delta before the release
matrix; unchanged installer behavior retains its valid prior evidence.

## Ownership and verification

One implementation owner covers the existing version declarations, builder/policy,
manifest schema, setup/launchers, current setup documentation, and only affected
current-version assertions/fixtures. Historical parser values and explicit legacy
0.3/0.5/0.9 migration states are retained as such. Tests may move current-candidate
expectations from 0.9 to 1.0; they must not weaken hostile-input, rollback, version
conflict or security assertions. The ten fixture-portability modules have a
different owner and are excluded from this implementation's write scope.

Before release, all required checks apply to the final committed code and actual
1.0 artifacts: complete Python 3.12 tests/branch coverage >=90%, UI unit/per-file
branch coverage >=90% and Windows browser tests, deterministic packaging, clean
install/Repair/rollback/refusal/security, asset/license/SBOM/compatibility and A/B
physical archive reconciliation. Performance measurements run without coverage
instrumentation and with exclusive resources. Fixtures and browser fake runtime
are software evidence only. Record exact command, source, interpreter, stdout,
stderr and exit; an old hardcoded printed command is not execution provenance.

The finalization native Windows lock-contention classification limitation remains
explicitly known. This release slice does not redesign DiagnosticStore locking;
if an actual mandatory release gate demonstrates it blocks the supported scenario,
return to primary for a separately bounded correction. Passing one package test
or the completed B record cannot substitute for the release matrix.
