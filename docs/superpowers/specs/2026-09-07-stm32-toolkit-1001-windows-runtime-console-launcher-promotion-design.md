## 2. Observed defect and classification

The accepted setup helper creates one CPython 3.12 virtual environment at
`DATA_ROOT/runtime/.staging/0.9.0-<nonce>`, installs only verified
release-manifest wheels with the staging interpreter, validates the packages,
and then moves the directory to `DATA_ROOT/runtime/0.9.0`.

On Windows, wheel console launchers generated by pip/distlib embed the absolute
`sys.executable` that existed at installation time. Moving the virtual
environment does not rewrite those launchers. The real accepted-head runtime
therefore has this split behavior:

```text
runtime/0.9.0/Scripts/python.exe -I -m stm32_toolkit.cli version -> 0.9.0
runtime/0.9.0/Scripts/stm32-toolkit.exe version                -> exit 1
```

The failed executable contains the retired `.staging/.../Scripts/python.exe`
path. `stm32-toolkit.exe`, `stm32-toolkit-mcp.exe`, and `stm32-monitor.exe`
are declared public product console entry points. The repository-level MCP and
Monitor `.cmd` launchers happen to remain usable because they directly execute
the final runtime Python, but that does not satisfy the README's generic
`stm32-toolkit ...` CLI contract.

Classification: `PRODUCT / Windows install transaction`. It is not a hardware,
VS Code, PyOCD, project, or Agent-adapter failure.

## 3. Runnable scenarios

### Scenario R1: fresh Bootstrap publishes usable final-path product launchers

Given a verified 0.9.0 Windows bundle, one supported CPython `>=3.12,<3.13`, an
explicit project root, and a new data root (including roots containing spaces),
authorized Bootstrap must:

1. retain the existing verified-wheel staging and pre-promotion validation;
2. move the one staged runtime to `DATA_ROOT/runtime/0.9.0`;
3. before writing `runtime-state.json`, use only the final runtime interpreter
   and the already copied, manifest-verified product wheels to regenerate the
   `stm32-toolkit`, `stm32-toolkit-mcp`, and `stm32-monitor` console launchers;
4. validate the final-path launchers and existing runtime/doctor inventory; and
5. only then publish the runtime-state generation.

The final `Scripts/stm32-toolkit.exe version` and
`Scripts/stm32-monitor.exe version` must both exit zero and return exactly
`0.9.0`. Each of the three public product launcher records must bind the final
`DATA_ROOT/runtime/0.9.0/Scripts/python.exe`, not any `.staging` path.

### Scenario R2: Check detects a relocated-but-unrepaired public CLI

CHECK remains read-only. If module invocation and doctor pass but any required
public product launcher is absent, redirected, bound outside the exact final
runtime interpreter, contains a staging binding, or its bounded version smoke
fails, CHECK reports the existing structured runtime status `broken`, sets
`authorizationRequired=true`, and recommends `Repair`. It does not rewrite the
launcher, state, project, or data.

The current accepted-head installed runtime is therefore expected to change
from a false `healthy` report to `broken` until an authorized Repair installs
corrected bytes.

### Scenario R3: Repair is one rollback-safe runtime transaction

Repair retains the existing quarantine model. It validates a fresh staging
runtime, quarantines the old runtime, promotes the candidate, regenerates and
validates final-path public launchers, and writes the next runtime-state
generation only after all final checks pass.

Any failure after promotion but before state publication removes only the new
candidate, restores the exact quarantined runtime and prior runtime-state bytes,
and returns failure. It never leaves a falsely matching state record or a
partially accepted second runtime.

### Scenario R4: preserve all Agent-neutral entry paths

The generic CLI, generic MCP `.cmd`, Monitor `.cmd`, package console entry
points, and Claude thin adapter continue to target the same single managed
runtime and the same public CLI/MCP behavior. No caller acquires an implicit
project root, system-Python fallback, second registration, or Agent-specific
product path.

## 4. Frozen implementation contract

### 4.1 Source and destination ownership

`bin/setup-stm32-env.ps1` remains the sole owner of managed-runtime installation
and promotion. The release manifest remains the only wheel inventory source.
The final runtime remains exactly `DATA_ROOT/runtime/0.9.0` and
`runtime/runtime-state.json` remains the only installed-version/source state.

Only the two manifest entries for distributions `stm32-toolkit==0.9.0` and
`stm32-monitor==0.9.0` may be used for public-launcher regeneration. Their
copied final-runtime wheel files must be regular, non-redirected, bounded by the
existing safe runtime path, and rechecked against the manifest size and SHA-256
before invocation. No index, dependency resolution, source build, host wheel,
PATH lookup, or network access is permitted.

The finalization command uses the final runtime Python and retains the existing
closed pip flags, adding only the reinstall semantics required to recreate the
product entry points from those two exact wheels. Dependency packages are not
reinstalled and the package versions do not change.

### 4.2 Final-path validation

Before state publication, and during every CHECK, the helper validates:

- exact regular/non-redirected files for final Python and the three public
  product console launchers;
- `stm32-toolkit.exe version == 0.9.0`;
- `stm32-monitor.exe version == 0.9.0`;
- bounded launcher metadata/bytes proving all three console launchers reference
  the exact final runtime Python and no `runtime/.staging/` interpreter;
- existing `python -I -m pip check`, Toolkit version, PyOCD import, Monitor UI,
  doctor runtime facts, 48 MCP tools, and eight Skills.

No MCP server process is started merely to validate its executable. Its
interpreter binding is checked without opening stdio, a socket, a service, or a
persistent process.

### 4.3 Error and lifecycle semantics

No new public error code or schema is added. Existing setup behavior remains:

- CHECK returns structured `missing`, `healthy`, or `broken` evidence and does
  not mutate;
- Bootstrap/Repair return nonzero with bounded stderr on any finalization or
  validation failure;
- `runtime-state.json` is never written before the final runtime is fully
  valid;
- Repair restores prior runtime and prior state on a post-promotion failure;
- Bootstrap removes its failed final candidate and leaves no matching state;
- staging/quarantine cleanup stays within the existing exact-path guards.

### 4.4 Allowed tracked changes

Product and implementation tests may change only:

```text
bin/setup-stm32-env.ps1
tools/stm32-toolkit/tests/test_setup_runtime.py
```

This specification, its plan, and a later report are governance files, not
product exceptions. If implementation requires another product/test path, the
owner must stop and return to Sol; it may not widen scope locally.

## 6. Risks and required evidence

The principal risks are accepting a launcher that still names staging,
mutating the final runtime after state publication, reinstalling unverified
wheels, weakening rollback, missing paths with spaces, or falsely marking an
old relocated runtime healthy.

Slice evidence must include, on Windows CPython 3.12:

1. RED from the accepted base showing a real fresh Bootstrap with product
   entry-point wheels yields a broken final `stm32-toolkit.exe` due to the
   staging binding.
2. GREEN fresh Bootstrap under paths containing spaces: both bounded version
   smokes pass; all three public launchers bind the exact final Python; no public
   launcher contains the staging interpreter; CHECK returns healthy.
3. CHECK-only regression against a deliberately staging-bound launcher returns
   broken and leaves a byte-for-byte project/data mutation audit unchanged.
4. Repair regression proves quarantine, incremented state generation, working
   final launchers, and preserved project bytes.
5. A post-promotion finalization/validation failure path proves no new matching
   state and restoration of the prior runtime/state when present. If the
   existing test harness cannot deterministically inject this phase without a
   product test hook, the implementer must stop and report the test-design
   blocker rather than add a test-only product switch or weaken the assertion.
6. Existing setup security, downgrade/source-conflict, bundle-integrity,
   MCP/Monitor `.cmd` launcher, doctor inventory, and complete
   `test_setup_runtime.py` regressions chosen only where the changed transaction
   creates direct risk.
7. `git diff --check`, exact changed-path audit, cleanup of run-owned temporary
   artifacts, and a clean implementation worktree.

Acceptance requires the independent Sol reviewer to inspect the complete
`387e59067cb066d5bb9ccf5d0e2253644a9710f5..final-code-head` diff and reproduce
the focused Windows evidence. A passing install test does not accept the
