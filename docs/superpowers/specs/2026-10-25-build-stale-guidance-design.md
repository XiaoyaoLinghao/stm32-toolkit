Primary owns specification, orchestration, independent complete-diff review and acceptance; local Claude Code CLI using existing provider/model owns implementation, tests and product guidance. ## Problem and public contract

After successful CMake commands, unchanged ELF/MAP outputs may fail the existing prior-evidence comparison. Today `BUILD_OUTPUT_STALE` only reports `path` and `rule=unverifiable`; callers cannot distinguish changed input evidence from missing/invalid receipts or other identity mismatches. Missing outputs also use this error. `--clean` already means CMake `--clean-first`, not directory/cache deletion.

Preserve the error code, legacy `path`/`rule`, every freshness admission check, success identity/result schemas and bytes, managed-file drift guards, Git/snapshot provenance boundaries, authorization and locking. Add bounded, JSON-safe diagnostics on this error only. Do not widen admission, retry automatically, remove directories, edit receipts or managed hashes, or attribute a specific changed file when only a digest mismatch is known.

The first existing failed comparison supplies a stable `reason` and, where useful, a fixed-field `evidenceField`/`evidenceSource`. Distinguish output unavailable, prior evidence unavailable (missing/unreadable/malformed is intentionally combined by the existing bounded reader), previous build not successful, input snapshot mismatch, and other prior evidence mismatches. Within the latter retain a fixed discriminator for preset/target, invalid identity/build ID, discovery policy, artifact paths/hashes, schema/provenance, project/version and invalid snapshot result. Derive diagnostics from the same predicate used for acceptance; do not maintain a second divergent validation algorithm. Prior recorded values are untrusted and must not be echoed. Digest mismatch means recorded evidence differs, not proof of a particular source edit or malicious change.

Include actual validated `preset`, `cleanRequested`, and portable log/result/identity paths. For unchanged unverifiable outputs with `clean=false`, provide `remediation.action=clean-rebuild`, explain that current inputs/evidence do not establish freshness, and offer exact CLI arguments and MCP tool/arguments preserving preset and timeout. CLI arguments are a token array, relative to the same project root and a caller-verified executable; no shell string or absolute root. MCP parameters omit `authorized=true` and explicitly require applicable authorization before execution. Advice never executes itself. For missing outputs, or stale output after `clean=true`, use `inspect-build-log`, explain the observation, and omit rebuild invocation fields: no repeated clean loop or claim that clean guarantees a fix.

Keep successful result/identity and failure receipt schemas unchanged. The returned OperationResult carries full diagnostics; build.log can retain the improved bounded message. Documentation must say to retain the failed response before another operation overwrites current evidence.

Review clarification: the CLI requires an explicit absolute project root even when cwd is the project directory. Portable advice must therefore identify a required binding, e.g. `cli.projectRoot={"option":"--project-root","valueFrom":"same-bound-project-root","required":true}`, in addition to its argument tokens and workingDirectory. The caller supplies the already verified bound absolute root; do not echo it into the portable error or weaken the parser to accept cwd/relative roots. State that `arguments` are the command tail, not a standalone invocation. Verify that omitting this binding is rejected without starting CMake and that constructing the invocation from the binding metadata succeeds.

## Calling guidance

Update build-firmware Skill, MCP build description, CLI clean help and user-guide VS Code workflow. Read the complete failure envelope and structured fields. Choose the proposed clean build only within applicable user authorization, using identical project binding/preset/timeout; a diagnostic suggestion is not authorization. Existing explicit authorization remains usable within its scope. Stop if clean was already requested or required output is unavailable; inspect logs/configuration before another plan. BUILD_PROJECT_INVALID/managed drift needs supported configure/fragment repair, not clean or hash editing. Do not switch to imported firmware or hardware after a failure. This is current-source behavior, absent from frozen/installed 1.3.0 until a later authorized install. Product remains 1.3.0; integration target is v1.3.1 after all agreed work.

## Boundaries and evidence

Allowed product scope: build/runner.py (a small adjacent diagnostics helper only if justified), cli.py help, mcp_server.py build docstring, focused build/CLI/MCP tests, skills/build-firmware/SKILL.md and docs/user-guide.md. No original project reads/writes needed; no hardware, runtime/global installation, network publication, packaging, version bump, new automation or dependency.

Tests use synthetic managed projects and fake CMake with real workflow/CLI/MCP boundaries. Cover Git and snapshot builds; unchanged accepted no-op; input/source/header/model or linker evidence changes where supported; unavailable/malformed prior evidence; non-success prior record; identity/preset/policy/provenance mismatch; missing ELF/MAP; release preset and nondefault timeout; clean already requested; exact existing clean argv; failed-result publication/no fresh identity; preserved authorization/root guards and managed drift refusal. Owner-specific execution records include exact source, command and JUnit. Primary independently reviews all changes and reruns the applicable focused suite in a separate clean tree at exact CodeHead. A small independent read-only CLI scenario checks guidance decisions. Skill structure validation is separate from behavioral evidence. No full release or hardware qualification is claimed.
