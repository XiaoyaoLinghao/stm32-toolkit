## Runnable scenarios and boundaries

1. An existing physical repair reached authorized source change and a valid after build; recovery produced a passed Target run in a different session. Explicit continuation binds both original physical runs and permits the missing Monitor analysis and Diagnostic verification without rewriting either origin identity.
2. A continuation attempt expires while verification is incomplete. Its roots remain immutable. Another fresh timed attempt can reference the same immutable association, retaining any valid Monitor/Diagnostic evidence. No source or hardware authorization is renewed.
3. Existing same-session physical and replay paths retain their canonical bytes and behavior. Cross-session requests without the exact verified association, or with swapped/corrupt/incompatible evidence, fail closed.

Only the existing Keil/mailbox physical repair scenario is supported. No hardware calls, firmware edits/builds, probe changes, identity aliases, evidence migration, replay-to-physical conversion, generic workflow engine or new public tool inventory. The successful P4 run is historical physical evidence; readiness for later sampling still needs the actual then-current preflight.

## One authority for association

Introduce one closed `stm32-physical-continuation/1` record, persisted as a canonical JSON artifact/envelope in the existing EvidenceStore. It is an immutable association proof, **not an action authorization or acceptance result**. Its envelope identity is the unchanged failed-before identity. The envelope has operation/artifact kind/root type `physical-continuation`; the root ID is the canonical payload SHA256, and the published evidence ID is the consumer handle. The envelope's produced time is its actual publication time. An existing identical content root is reused, not rewritten with a new time.

The exact payload fields are: `schema`, `predecessorAttemptId`, `predecessorCheckpointId`, `predecessorEvidenceId`, `diagnosticSessionId`, `diagnosticRevision`, `diagnosticEventHead`, `diagnosticEvidenceId`, `sourceChangeDeclarationId`, `sourceChangeIntent`, `failedBeforeTestRunId`, `failedBeforeEvidenceId`, `fixedAfterTestRunId`, `fixedAfterEvidenceId`. `sourceChangeIntent` is the existing fully expanded canonical SourceChangeIntent; do not create another snapshot format. Other facts are obtained from these authoritative parents rather than accepted as caller overrides. Envelope parents are exactly predecessor evidence, pinned Diagnostic evidence, before evidence, after evidence, and source-diff evidence, in that order, without duplicates.

Creation requires a fully validated original v2 physical attempt at revision6 / firmware-built-after, including its valid historical source authorization, exact intent, declaration, build and snapshot bindings. The caller names the exact predecessor checkpoint and evidence; it must still be the latest immutable predecessor revision. An expired predecessor is allowed as **historical input**; it is never mutated or used as a live authorization. Completed predecessors, replay/host/non-mailbox evidence, missing stores and synthetic caller flags are rejected.

The original Diagnostic is pinned by its real revision/event head and existing checkpoint evidence. Creation validates the original failed authority and the matching single SourceChangeDeclaration. Each TestRun is loaded through TestRunRepository under its own original identity; require target/physical/transport-evidence true, before failed, after passed. Require identical workspace, logical project, target, published probe/target IDs and mailbox transport digest; require the two distinct sessions to match their respective original manifests/envelopes. Do not infer silicon UID. Each original publication's origin/import/flash/lease contract remains intact. Distinct actions, flash sessions, leases, builds and ELFs remain legitimate. Before/after build/ELF/input snapshots and declared paths must exactly match the predecessor intent and declaration. No rewriting of source intent or authorizations is permitted.

Keep one shared association model/authenticated-reader below workflow adapters. It must validate the immutable Evidence graph, original roots/manifests/artifacts and pinned historical prefix, not trust just an association JSON or evidence ID. It must not import Diagnostic or recovery **workflow** modules, call mutable high-level DiagnosticStore loading from inside its own reference validation, or import Monitor. Reuse/extract the smallest existing pure chain reader as needed. Dependency direction: models/EvidenceStore/TestRun authority → shared continuation proof → recovery, Diagnostic and Monitor adapters. Creation owns mutable-head/Diagnostic checks; all consumers own exact contextual matching using the same authenticated proof.

Diagnostic is permanently in the before session. The pinned historical revision may acquire legitimate later verification events; readers verify the pinned ancestor rather than requiring the current Diagnostic revision to remain forever equal. They must still reject a non-descendant, substituted declaration/run or unrelated active verification. Reference graph traversal remains acyclic: the proof refers only to the pre-verification Diagnostic checkpoint; subsequent plans/events refer to the proof.

## Public entry and timed attempt

Extend existing `scenario attempt begin` with optional CLI `--continuation-file`, and the existing MCP begin tool with a corresponding closed `continuation` object. No new command family/tool. Absent input preserves v1/v2 behavior.

The file/object is `stm32-physical-continuation-request/1`, with exactly one form:

- `kind=bind`: `schema`, `kind`, `predecessorAttemptId`, `predecessorCheckpointId`, `predecessorEvidenceId`, `fixedAfterTestRunId`, `fixedAfterEvidenceId`, `diagnosticRevision`, `diagnosticEventHead`.
- `kind=reuse`: `schema`, `kind`, `continuationEvidenceId`.

Use existing UUID/native-run/hash/revision domains and bounded safe JSON reading. These inputs apply only to `legacy-keil-physical-repair`, version1, with a fresh caller-specified attempt UUID and the original before session context. Reject other scenarios, unknown keys or mixed forms. Bind returns the authoritative continuation evidence ID; reuse fully reloads it. Exact retries preserve the original accepted publication even if time has advanced; conflicting reuse of an attempt UUID is rejected.

Create `stm32-acceptance-attempt/3` only for this continuation. Reuse existing immutable attempt roots and envelopes, with a closed dedicated model/policy and two revisions: rev0 `IN_PROGRESS` / `verification-pending`; rev1 `COMPLETED` / `target-fix-verified`. The model carries the existing identity/time/checkpoint/scenario fields, a required `continuationEvidenceId`, and `fixVerificationId` null at rev0 and a real digest at rev1; it carries no new source action digest or authorization state. Freeze a separate `stm32-physical-continuation-policy/1` with a 900-second completion window from rev0 publication and no intrusive actions. Do not alter v1/v2 policy digests or stages. Existing show/resume dispatch recognizes v3 and reports expiry without changing roots. Authorize-source-change is invalid for v3.

The v3 JSON fields are exactly `schema`, `attemptId`, `revision`, `checkpointId`, `previousCheckpointId`, `scenarioId`, `scenarioVersion`, `scenarioDigest`, `recoveryPolicyDigest`, `workspaceId`, `logicalProjectId`, `sessionId`, `projectOrigin`, `executionSource`, `physicalTransportEvidence`, `status`, `stage`, `continuationEvidenceId`, `fixedAfterTestRunId`, `fixedAfterEvidenceId`, `fixVerificationId`, `openedAtUtc`, `updatedAtUtc`, `deadlineAtUtc`. Session is the before session, projectOrigin=keil, executionSource=physical and transport evidence=true only after verified binding. Both revisions retain the original rev0 deadline; completed reads do not become timed out later. The fixed-after IDs are immutable copies of the proof. Checkpoint hashing follows the existing exclusion of checkpointId. Rev1 points to rev0, preserves its immutable fields, has an in-window updated time and the verified completion ID. The separate scenario digest binds the v3 attempt schema, existing scenario ID/version, keil/mailbox/physical profile and the two named stages; the policy digest binds that scenario digest, v3 schema, 900 seconds and no intrusive actions. These definitions have one owner in the new model module.

Existing checkpoint accepts only `target-fix-verified`, exact after run ID and actual FixVerification ID. Require the original Diagnostic's completed PASSED FixVerification, plan digest and all analysis/declaration/before/after evidence to match this proof. Completion uses a fresh current time check immediately before the new root publication; expiry creates no completed root. An already accepted exact retry remains readable. A new timed attempt may reuse the same association after expiry, so a correct pre-existing VerificationPlan and FixVerification do not need new identities solely for bookkeeping.

Use existing Diagnostic-before-EvidenceStore lock order, CAS and immutable root publication. Revalidate mutable inputs at association publication; do not load a public Diagnostic workflow while holding the EvidenceStore mutation lock. Shared readers must be safe when called from existing locked paths. A failed publication can leave unreferenced artifacts, but cannot expose an accepted association/attempt root. Races must produce one valid winner or a typed conflict, never a partially trusted proof.

## Monitor and Diagnostic consumption

Monitor `analysis compare` and `analysis bundle` accept optional `--continuation-evidence-id` / corresponding existing Python argument. With no ID, preserve all current checks. With an ID, fully authenticate the proof, require the original Diagnostic and exact declaration, and match the before/after TestRuns and physical Monitor refs to the proof. Load each physical ref/history under its own original session; keep physical publication/transcript/reference rules unchanged. The caller context remains the before session. No projection or republishing into a false physical identity.

For explicit continuation only, add `stm32-monitor-analysis-lineage/2`: retain all existing lineage fields and add `before_session_id`, `after_session_id`, `continuation_evidence_id`. Publish `stm32-monitor-analysis/2` with the same outer field meanings and the v2 lineage. Existing computation and request/selector/statistics contracts remain unchanged. Analysis ID and evidence bind the v2 lineage and proof; operation retry/conflict keys must include the association context. Analysis envelope identity remains the actual after identity; parents are the existing before transcript, after transcript and source-diff evidence, followed by continuation evidence. Versioned metadata includes the continuation evidence ID. Existing v1 bytes, analysis evidence refs, marker refs and statistics are preserved.

Add `stm32-verification-plan/2`: exactly the old fields plus required `continuation_evidence_id`. Its canonical plan digest includes the ID. Use the existing source declaration's `validation_plan_id`; do not replace the declaration. FixVerification retains its existing schema because the exact versioned plan digest and analysis IDs already bind the proof; require that transitive binding on every reader/finalization path.

Update all actual consumers together: Diagnostic plan/start/complete, per-side Target/transcript validation, Analysis/marker loading, DiagnosticStore event/reference replay and complete reload, Monitor comparison/publication/bundle/readback, and final attempt checkpoint. Do not globally relax `_same_scope`, physical provenance or TestRun publication. A shared proof permits only the exact pair's session difference; every other identity/declaration/state/quality predicate remains required. Include the proof in existing event/evidence reference collection so GC keeps its parents. No fallback for missing/corrupt association, no acceptance based only on passed flags.

Use existing input/identity/integrity/conflict/timeout error families for each public adapter. A malformed/unknown/mixed continuation request is input-invalid; a valid proof for the wrong context/pair is identity-incompatible; corrupt or missing authoritative evidence is integrity failure. An expired timed attempt is still the existing attempt-timeout result. No new hardware safety code is needed.

The adapter mapping is explicit below. After the error-category finding persisted through two review rounds, local patching stopped to audit all consumers together. The ambiguity was the distinction between external consumer context and contradictions inside a persisted graph; this table freezes that distinction without expanding the approved behavior. `ContinuationIdentityError` applies only after authenticating a proof, when external expected context or a supplied verification plan does not match it. Ordinary `ContinuationValidationError` means malformed/corrupt authoritative graph data; a stored analysis claiming this proof while contradicting its own bound lineage is graph corruption. Pure analysis retains its existing single error code and typed cause; workflow adapters translate that cause.

| Boundary | Malformed request | Valid proof, wrong consumer context | Missing/corrupt proof or bound graph |
| --- | --- | --- | --- |
| Recovery public workflow | `ACCEPTANCE_ATTEMPT_INPUT_INVALID` | `ACCEPTANCE_ATTEMPT_IDENTITY_MISMATCH` | `ACCEPTANCE_ATTEMPT_EVIDENCE_INTEGRITY_FAILED` |
| Monitor public workflow | `ANALYSIS_WORKFLOW_INVALID` | `INCOMPATIBLE_IDENTITY` | `EVIDENCE_INTEGRITY_FAILURE` |
| Diagnostic public workflow | Existing plan/event input validation | `INCOMPATIBLE_IDENTITY` | `EVIDENCE_INTEGRITY_FAILURE` |
| DiagnosticStore append/replay | Existing event validation | `DIAGNOSTIC_IDENTITY_MISMATCH` | `DIAGNOSTIC_EVIDENCE_MISSING` for unavailable direct references/provider reads; `DIAGNOSTIC_CHAIN_CORRUPT` for invalid authenticated graphs or stored reference contradictions |

No adapter may catch the shared validation base class and unconditionally label it identity mismatch. Context checks are not moved ahead of proof authentication. The shared reader remains independent from workflow modules and does not create a generic diagnostic framework.
