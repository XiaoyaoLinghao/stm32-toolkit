## Public contract

2026-10-29 follow-up: the [100 kHz default design](2026-10-29-flash-default-100khz-design.md)
supersedes the former ordinary default. Omission still preserves the selected worker
configuration, but production worker/backend defaults are now 100000 Hz. Explicit
faster values remain optional; 1 MHz is not a physical acceptance requirement.

1. Add optional `frequency_hz: object = None` at the END of both FlashWorkflowRequest and FlashImportedWorkflowRequest. Existing positional constructors remain compatible. Add CLI `--frequency` (decimal integer Hz) to `flash` and `flash-imported`, rejecting duplicate options with the existing parser machinery. Add optional `frequencyHz` (StrictInt, inclusive100000..50000000, or null) to the two existing MCP tools and wrappers. No new MCP tool. Root binding and authorization checks keep their existing precedence. Booleans/floats/strings are rejected in Python/MCP; CLI rejects malformed, fractional, out-of-range and duplicate values. Workflow invalid frequency returns HARDWARE_INPUT_INVALID with field=frequencyHz, rule=type/range/conflict and actionable guidance; reject before creating directories/lease/supervisor/backend or invoking flash. No model/default PATH/settings changes.
2. Omitted frequency preserves the selected worker config (production normal default100000Hz, updated by the 2026-10-29 follow-up); explicit normal frequency selects that value. Managed recovery retains the existing for_under_reset_recovery() policy at100000Hz. Explicit100000 with recovery is accepted; any other explicit value conflicts and fails before effects. Preserve target profile, transport provider and connection policy invariants. Do NOT call dataclasses.replace on ProbeWorkerConfig: it has init=False and target_profile_json is not a constructor parameter. If constructing a copy, use the public constructor with base.target_profile()/transport_provider/connection_policy, then the existing recovery method as appropriate. _seams is immutable/shared and must not be modified. No worker wire, receipts, identity, firmware admission or hardware-control change is required. The follow-up changes only the shared default, not these invariants.
3. Imported flash gains normal frequency ONLY. Its existing contract does not offer under-reset; do not add recovery arguments, an imported recovery route or a suggestion for an unsupported command. Managed no-Git refusal and imported separate admission/receipt boundaries remain unchanged. Existing IDE generated tasks and adapter keep their defaults; custom frequency/recovery uses explicit CLI/MCP with the documented actual binding/pins. No generated template/IDE adapter expansion in this slice.
4. After selecting config and running _one_shot, merge `details.flashOptions` into returned success/failure while preserving every existing code/message/data/details field and cleanup precedence. Shape: requestedFrequencyHz (null if omitted), configuredFrequencyHz (int), connectionPolicy (existing config string), automaticRetry=false. These are selected CONFIGURATION, not measured/effective hardware frequency or proof that attach/programming happened. Managed success keeps postFlash unknown/runVerified=false. Imported success keeps receipt publication and all post-cleanup integrity checks before success; annotate also the subsequent revalidation/receipt failures once config is selected. Do not change receipt or firmware identity schemas. Early input/auth/admission failures may omit flashOptions.
5. Add a bounded `details.recoverySuggestion` ONLY for a managed NORMAL flash failure returned after owned cleanup with code PROBE_PROGRAM_FAILED, or PROBE_ATTACH_FAILED with a valid closed attachDiagnostic whose primary.stage is session-open or halt-verify AND reason in {probe-disconnected,probe-io,transport-timeout,transport-fault,transport-error,target-response,target-register,debug-command,debug-operation,postcondition-failed,backend-code}. No suggestion for cleanup failure, identity/stale/provenance/input/authorization/readback/receipt failure, success, already-recovery, imported routes, cancellation or arbitrary errors. The suggestion is informational: kind=under-reset, frequencyHz=100000, cliOption=--recovery-under-reset, mcpArgument=recoveryUnderReset, requiresNewAuthorization=true, automaticRetry=false, guidance explaining stop, retain diagnostics, verify target/reset wiring and cleanup, then consider a separately authorized one-shot recovery. Recovery may leave halted and does not prove running. No fabricated full commands, IDs, credentials or guarantee of success. Preserve existing attach/programDiagnostic and general guidance. Eligibility does not grant authority.
6. No automatic lower-frequency retry, reconnect, reset/resume, fallback, route switch, fresh enumeration or new hardware call. Existing owned cleanup remains unchanged, including its established internal behavior. Failure output is pure enrichment after the current workflow terminates.
