# 大型项目开发错题本：STM32 Toolkit 首个大型项目复盘

**形成日期：** 2026-08-22

**适用范围：** 后续由 Codex 主代理规划、子代理实现并由主代理独立审查的中大型软件项目

**性质：** 跨项目治理记忆的完整证据版；用户级 `C:\Users\ZhangYang\.codex\AGENTS.md` 只保留本文件的简明执行规则

## 1. 复盘目的

STM32 Toolkit 是本协作流程开发的第一个大型项目。项目交付了大量真实产品能力，但也暴露出一种危险的替代行为：当整体设计、跨模块契约或真实产品闭环尚未收敛时，继续拆任务、增加 Gate、扩大报告和重复验证，能够制造“工作持续推进”的表象，却不能缩短从需求到可集成产品行为的周期。

本错题本不是追责记录，也不把所有复杂性归咎于验证。它的目的，是区分必要的嵌入式工程复杂性与可以避免的开发复杂性，并把纠正措施变成后续项目默认执行的规则。

## 2. 事实基线

复盘所依据的当前事实如下：

- 当前治理 HEAD：`1f28cf4bba310210f4658dfc06590bed3646bfb8`。
- 当前 0.6 产品 CodeHead：`d09e2343ab970f4ddeaa4c24dbf581c9bbe96f58`。
- 当前状态：0.6 软件闭环完成，0.4/0.6/1.0 实体硬件活动统一后置；没有远程、PR、合并、tag 或硬件授权。
- 从首个 0.3 接受提交之前到当前 0.6 产品候选，一方历史包含 306 个提交：50 个 `feat`、136 个 `fix`、75 个 `docs`、27 个 `test`、4 个 `refactor`、1 个 `chore`，没有正式 `release` 提交。
- 当前 Toolkit 约有 46,095 行产品 Python 和 71,743 行测试；其中 release Gate 测试约 9,565 行，Testing/Diagnostics/Evidence 产品层约 17,781 行，而 Project/Keil/Migration/Build 约 8,649 行。
- 0.6 在治理切换前形成了多层计划和补充文档：0600–0603 模块计划之外，Task 10、VS03、VS04 又产生多份 replacement、authority、wire-contract、adapter、completion 和 amendment 文件。
- 真实硬件与真实 Keil 固件工程一直未具备，因此大量软件验证只能证明模型、适配器和 replay 行为，不能证明最终物理闭环。

这些数字不自动证明代码质量低；它们证明产品实现、修复、报告和验证之间的投入比例已经需要治理干预。

## 3. 没有走错的技术路线

以下外部工具组合不是弯路，后续项目不得因为“组件数量多”就错误地重新实现成熟基础设施：

- CubeMX 负责 MCU、pin、clock、peripheral、startup 和 HAL/LL 生成；
- ARM GCC 负责编译和链接；
- CMake/Ninja 负责可复现构建；
- PyOCD 负责统一 Probe 会话、烧录、观察和调试后端；
- Cortex-Debug 负责 VS Code 人工交互调试；
- MCP/CLI 负责让 Agent 调用同一产品控制面。

真正的产品价值是安全编排这些成熟工具，而不是重新发明编译器、工程生成器、调试协议或图表系统。

## 4. 错题与根因

### 4.1 总体目标正确，但最初缺少可执行的跨模块闭环

**现象：** 初始架构描述了迁移、构建、烧录、Monitor、测试和诊断，但没有在同一设计层冻结 TestRun、Evidence、DiagnosticSession、MonitorRun、SourceChange 和 FixVerification 的端到端关系。

**结果：** 模块各自合理，直到集中验收才发现身份、引用、生命周期和失败语义不兼容。Target origin workspace 与 import workspace 的桥接就是典型例子：局部模块都能工作，跨工作区 diagnostic begin 却因为把两个 workspace identity 直接等同而失败。

**根因：** A 整体设计缺失，叠加 B 公共接口未冻结。

**改正：** 大型项目在模块实现前必须先写一个可执行集成设计，至少包含端到端数据流、公共模型、唯一权威来源、错误分类、生命周期和三个真实调用场景。局部规格只能细化，不得自行决定跨模块语义。

### 4.2 按层、文件、异常和证据类型拆任务，代替纵向产品切片

**现象：** 任务从模块继续拆成 Task、Gate、replacement、amendment 和 adapter 子树；部分任务的输出是新的契约、报告或验证器，而不是调用方可消费的产品行为。

**结果：** 完成大量局部工作后仍无法演示用户闭环；实现者上下文频繁切换；所有权账本、分支、工作树和报告成本随任务数量增长。

**根因：** A 整体设计缺失和 B 接口未冻结被错误处理为“继续细分”。

**改正：** 每个实现任务必须产生一个可演示或可由调用方消费的纵向行为，通常 1–3 个工作日完成。一个切片不得递归拆成多层任务树；如果边界仍不清楚，退回设计层，不继续分解。

### 4.3 把发布级 Gate 前移到每个实现切片

**现象：** 覆盖率、双运行时、双平台、打包、浏览器、证据归档和发布报告要求多次进入局部实现任务。

**结果：** 验证计划规模明显超过产品变更规模；Gate controller 和 verifier 自身成为大型子产品，并产生新的 race、路径、格式和恢复缺陷。

**根因：** 验证基础设施缺陷 D 被继续增加验证基础设施来修复。

**改正：** 固定三层验证：切片级、集成级、发布级。只有书面风险触发器才能把某项发布检查前移；风险触发器必须指向实际变更，例如协议/schema 兼容、进程/锁、凭据边界、安装包或硬件控制，不能用“更稳妥”作为理由。

### 4.4 报告格式与产品正确性耦合

**现象：** 报告自身的 SHA、计数、路径、命名、归属或摘要差异可能使正确的产品候选失效；已通过且产品字节未变的证据被要求重跑。

**结果：** 报告修正演变为候选修正，验证时间侵占产品开发时间，且证据归属更难理解。

**根因：** F 纯报告问题被错误分类成 C 实现缺陷。

**改正：** 产品候选、验证证据和报告载体三者分离。报告格式错误只修报告，除非它证明证据本身不可定位、不可归属或被篡改。未受产品字节、依赖、环境或契约影响的 PASS 不作废。

### 4.5 环境失败、平台失败和产品失败没有始终分离

**现象：** 一次审计从错误工作树导入 `stm32_toolkit`；并发审计污染性能样本；缺少 `code` PATH 被等同于 VS Code 缺失；真实硬件不可用被混入产品实现状态。

**结果：** 正确代码可能收到失败结论，或者环境阻断推动新的产品修补和 Gate。

**根因：** E 环境/平台问题与 C 实现缺陷混淆。

**改正：** 每个失败先分类为 PRODUCT、ENVIRONMENT、PLATFORM、INFRASTRUCTURE 或 REPORT。验证必须绑定精确 CodeHead、解释器和依赖来源；性能测试独占执行；PATH 只是发现来源之一，不是安装事实；硬件缺失只能是命名的后置阻断。

### 4.6 真实产品锚点过晚

**现象：** Keil 转换、Probe、Target transport 和物理诊断已经完成大量 fixture/replay 验证，但没有真实 Keil 工程和可独占板卡形成早期锚点。

**结果：** 工程结构、身份桥接、Probe 组合和实际传输风险积累到集中验收；随后又试图为硬件活动收集大量参数，而用户当时并没有真实固件项目。

**根因：** E 环境条件缺失，但计划没有及时重排；部分风险又被误解为需要更多软件 Gate。

**改正：** 项目开始时明确真实锚点何时具备。若暂时没有真实资产，软件切片只能声明 software-complete，硬件证据统一后置，不能伪造兼容范围。真实资产一旦具备，用同一纵向场景同时关闭历史硬件债务，避免多轮重复活动。

### 4.7 外部工具职责和产品边界描述不够清晰

**现象：** CubeMX、CubeCLT、ST VS Code extension、CubeProgrammer、PyOCD 和 Cortex-Debug 的职责在文档中并存，但没有一张唯一权威映射；用户自然产生“CLT 是否就是 VS 插件”“烧录究竟由谁负责”的疑问。

**结果：** 安装判断和 0.7 方案可能走向重复后端或第二套控制面。

**根因：** B 接口/所有权未冻结和 F 产品描述问题。

**改正：** 每个外部工具只能有一个明确职责和一个产品适配边界。新依赖必须说明它替代什么；如果不替代任何现有组件，默认不增加。用户安装清单、doctor 输出、架构图和实施计划使用同一术语。

### 4.8 核心 Agent 接口较通用，但交付层过度绑定单一宿主

**现象：** CLI/FastMCP 核心可以由通用调用方使用，安装器、环境变量、Skills 和 manifest 却绑定 Claude Code。

**结果：** 产品被描述为“VS Code + Agent”，实际交付却像单一 Agent 插件；后续接入其他 MCP Agent 时容易复制业务逻辑或运行时。

**根因：** A 产品边界不完整。

**改正：** 核心只认显式 project/data/session 参数和通用 `STM32_TOOLKIT_*` 环境；不同 Agent 是薄适配器。不得为新 Agent 复制 Project、Probe、Monitor、Test 或 Diagnostic 实现。

### 4.9 兼容范围扩张早于真实需求

**现象：** Python 3.10/3.12 双版本、平台矩阵和多类工具输出在产品闭环尚未完成时就进入常规开发节奏。

**结果：** 维护和报告成本提高，实际用户价值没有同比增加。

**根因：** A 非目标不够坚决，叠加 D 验证基础设施扩大。

**改正：** 首个稳定版本只支持一个明确运行时和一组真实证明的工具版本。STM32 Toolkit 当前冻结为 CPython `>=3.12,<3.13`。任何新增兼容范围必须由真实用户场景驱动，并在独立版本中验证。

### 4.10 版本、README 和实现状态没有同步收敛

**现象：** 当前产品代码已进入 0.6 候选，但 package、launcher、README 和工具清单仍显示 0.5.0/旧接口。

**结果：** 用户无法仅通过产品入口判断实际能力；环境诊断和安装说明也可能给出过期结论。

**根因：** F 报告/发布问题长期后置。

**改正：** 版本元数据作为独立的发布纵向切片处理。代码、runtime、Monitor、manifest、README、Skills、MCP inventory 和兼容矩阵必须在同一候选中原子收敛，但不得混入无关功能实现 diff。

### 4.11 进度百分比掩盖了未打通的链路

**现象：** 历史百分比可以随着任务、测试和文档完成而上升，即使用户场景仍不可运行。

**结果：** 项目看起来接近完成，却仍缺真实输入、公共入口或跨模块身份桥接。

**根因：** F 进度报告模型错误。

**改正：** 只报告已完成用户场景、已打通跨模块链路、已冻结公共契约、未解除产品阻断、切片周期，以及产品开发时间与验证/报告时间比例。

### 4.12 代码和测试单元增长过大，增加了审查与修复成本

**现象：** 部分控制器、测试文件和领域模块达到数千行；单次改动需要同时理解状态、路径、锁、证据和报告语义。

**结果：** Luna 实现任务容易超出一次上下文可控范围，Sol 完整 diff 审查成本升高，修复更容易触发邻接回归。

**根因：** A/B 边界不清后在同一文件持续叠加行为。

**改正：** 文件大小不是独立重构指标，但当一个单元不能用一个清晰接口解释，或一个切片需要同时修改多个无关状态机时，必须在设计中拆清职责。不得为“清理代码”做无关重构；只在纵向切片触达的边界上改进。

## 5. 根因分类与正确响应

| 类别 | 识别问题 | 正确响应 | 禁止的默认响应 |
|---|---|---|---|
| A 整体设计缺失 | 多个模块对同一用户行为各自解释 | 回到集成设计，冻结端到端闭环 | 增加子任务或 Gate |
| B 公共接口未冻结 | identity、状态、错误、所有权有两种解释 | 冻结唯一权威来源和公共契约 | 让实现者自行选择 |
| C 实现缺陷 | 已冻结行为被代码违反 | 同一切片修复并跑受影响回归 | 扩大成完整发布审计 |
| D 验证基础设施缺陷 | runner/verifier/report 工具错误 | 修验证工具并保留产品证据 | 宣布产品候选自动失效 |
| E 环境/平台问题 | 工具、硬件、PATH、权限、并发污染 | 记录环境阻断或修复环境 | 修改产品迎合偶发现象 |
| F 报告问题 | 文字、格式、计数、链接不一致 | 修报告和索引 | 重跑未受影响验证 |

## 6. 后续大型项目的强制开发规则

1. 先定义 2–4 个可运行用户场景，再定义模块和文件。
2. 在模块并行开发前冻结公共数据模型、错误语义、状态转换和唯一权威来源。
3. 每个实现任务是 1–3 个工作日的纵向产品切片；不能保持边界就回到设计。
4. 一个切片只有一名实现所有者和一名独立最终审查者；实现者不得接受自己的 diff。
5. 主代理审查 accepted-base 到 final-head 的完整 diff，不以摘要、报告或局部 patch 代替。
6. 切片验证只包含目标测试、契约测试、受影响回归和 diff 审查。
7. 集成验证只在跨模块链路形成后运行；发布矩阵只在候选发布时运行。
8. 发布 Gate 前移必须有书面风险触发器和明确受影响范围。
9. 同一问题两轮不收敛，停止局部修补，回到接口或整体设计。
10. 验证/报告规模不得明显超过产品改动；连续两个切片超过时暂停开发并治理复盘。
11. 先分类 PRODUCT、INFRASTRUCTURE、ENVIRONMENT、PLATFORM、REPORT，再决定是否改产品。
12. 已通过且未受产品字节、依赖、环境或契约变化影响的证据不得无理由作废。
13. 报告格式错误不自动使正确候选失效。
14. 外部工具优先复用成熟能力；每个新工具必须替代或承担唯一职责。
15. Agent 宿主是薄适配器，核心产品不绑定单一 Agent。
16. 没有真实项目或硬件时明确声明 deferred，不用 replay/fake 冒充物理 PASS。
17. 兼容范围从最小真实支持集开始；新增运行时、平台、MCU 或后端需要真实需求。
18. 远程 push、PR、merge、tag、close 和分支删除逐次授权，不能由“继续开发”推导。
19. 用用户场景、跨模块链路、冻结契约、产品阻断和周期衡量进度，不使用历史百分比。
20. 规格、计划和代码各自有边界：规格解决歧义，计划安排实现，代码不得补写未决产品设计。

## 7. 每个新项目启动检查表

在第一个产品实现提交前，主代理必须能够回答：

- 用户最终要完成哪三个真实场景？
- 明确非目标是什么？
- 哪些能力由外部工具承担？
- 公共模型和唯一权威来源是什么？
- 失败如何区分产品、环境、平台、基础设施和报告？
- 第一个纵向切片的输入、输出、失败行为和验收是什么？
- 哪些验证属于切片、集成和发布？
- 哪些真实资产现在缺失，何时补齐？
- 实现者、审查者、accepted-base 和远程权限是什么？
- 如果两轮不收敛，回到哪一层重新设计？

任何一项无法回答，都不应通过增加任务数量来掩盖。

## 8. 记忆维护规则

- 用户级 `AGENTS.md` 保存第 6 节的精简规则，使后续项目自动继承。
- 本文件保存事实、反例和完整解释，是 STM32 Toolkit 的可审计来源。
- 后续项目只有发现新的、可复现的反模式时才追加错题；不得把临时偏好写成全局规则。
- 全局规则修改必须说明它来自哪个项目事实，并避免加入单一仓库路径、版本号或临时实现细节。
