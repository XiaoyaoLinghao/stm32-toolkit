# Flash Firmware

## Select one route before any context or model gate

- If the user only asks which probes are connected, use the discovery-only route first. Do not call `stm32_project_context` and do not require a model.
- If the user asks to flash the current managed build, use the managed flash route. Its stop rules are for that route only.
- If the user explicitly selects an external or snapshot firmware file, use the separate imported route. A managed blocker, stale evidence, failed managed flash, or context model error never switches the route automatically. A context model error also does not prove the imported endpoint is absent: preserve that error, then, only after the user selects the imported route, validate that route's own declared inputs. Invalid project roots, invalid bindings, and errors from that endpoint itself still stop the operation.

1. **Discovery-only request.** Call `stm32_probe_list` and report its evidence. Probe discovery requires no manifest, build, target, or SVD, is read-only, and grants no board-modification permission. The firmware provenance form never blocks this discovery-only request. Do not call `stm32_project_context`, require or discuss a build, or flash. If `workspaceId` is null and `discovery.status` is `unbound`, say so and never invent a workspace ID. Finish here.
2. **Managed flash request.** Call `stm32_project_context` with no arguments and read/retain the complete result; check `ok` before reading `data`. If it is a failure, preserve its code/message/details and stop this route. Read `data.project.root`, `data.firmwareRoutes`, and `data.capabilityDetails`; never flatten them to legacy booleans. `data.firmwareRoutes.managed` mirrors `capabilityDetails.flash`; `data.firmwareRoutes.imported` is always `not-evaluated` in context. `not-evaluated` means context did not examine hardware; it is not a refusal. Stop this route only on a known `blocked` status or a missing/stale current managed build identity, never merely because a legacy capability boolean is false. Require a current successful managed build identity. Read `data.build.buildId` and `data.build.elfSha256` (the ELF SHA-256); if the build evidence is blocked or stale, report that and stop this route. In published v1.3.3, a schema-2 identity (null `gitHead`/`gitDirty`, `sourceBaseline="input-snapshot-v1"`) is accepted by the shared firmware admission exactly like schema 1: the declared inputs, model/debug target, exact ELF/MAP bytes and successful build record must still match. Git is optional traceability for project creation, migration, build and this normal managed route; never `git init`, commit or fabricate a commit, and never treat null as clean. A no-Git or migrated `keil convert` output flashes normally after binding its `outputRoot`, configuring and building. Do not substitute an imported image. The project model remains the authority for target and optional SVD selection.
3. **Verify the binding.** A launcher or CLI version does not prove the bound MCP server's version. Compare `stm32_doctor` `data.runtime.toolkitVersion` and `data.publicInventory` (as returned by the actual MCP client) with the actual tool list and input schemas the client exposes, and keep `data.project.root` authoritative. Doctor inventory counts are not proof that the client registered those tools. After an upgrade restart VS Code once, then verify again. If expected tools or fields are missing, or the root differs, preserve the full result and stop the dependent operation; do not work around a binding error.
4. Call `stm32_probe_list` and show its returned evidence. Require the user to choose one exact `probeId`; zero or multiple probes never imply a default.
5. Restate the exact probe, `expectedBuildId`, `expectedElfSha256`, project target, and that flash modifies the selected board.
6. Obtain explicit authorization for that exact operation, including any frequency or recovery option you will select next. State that a normal confirmed flash includes one pre-program `SYSRESETREQ` reset-and-halt with a halt verification before programming, while a selected under-reset recovery reuses its connection-time reset and only re-verifies that the target is halted; either way the reset is part of the single authorized flash operation rather than a separate grant. An existing explicit authorization for this exact operation can cover a requested option; do not ask again solely because the option exists. Without authorization, call nothing intrusive and stop.
7. Select the request before the one call. Omit `frequencyHz` unless the user requested a non-default debug frequency; an explicit value must be an exact integer from 100000 to 50000000, and omission uses the ordinary production default (100000 Hz / 100 kHz in this unpublished v1.3.5 local candidate). A faster value is an optional explicit choice, never a required 1 MHz gate; on an older runtime that still carries the former default, pass exactly 100000 to select 100 kHz. Under-reset recovery is a separate managed policy: only when the user explicitly selects it, pass `recoveryUnderReset=true` and omit `frequencyHz` or pass exactly 100000; never infer it. Under-reset recovery reuses its connection-time reset and only re-verifies that the target is halted; it never adds a second reset. Then call `stm32_flash` once with the selected `probeId`, `expectedBuildId`, `expectedElfSha256`, `authorized=true`, and those selected options. Do not issue a second implicit operation.
8. Report the complete operation result, including any stable failure code and flash-result evidence. A successful result carries `details.postFlash` with `targetState=unknown` and `runVerified=false` and `details.flashOptions` with `requestedFrequencyHz`, `configuredFrequencyHz`, `connectionPolicy`, `preProgramReset` (`sysresetreq` for a normal flash, `under-reset-connect` for recovery), `preProgramHaltRequired=true`, and `automaticRetry=false`; some early failure results omit these, so report the actual returned fields. `preProgramReset`/`preProgramHaltRequired` describe the selected policy only: they are not proof that the reset, attach, or halt happened, and they can appear on a failure that never reached them. A successful flash proves only the existing programming and readback checks; target state is unknown and program execution is unverified. Frequency options are selected configuration, not a measured clock.
9. If a managed normal flash fails with `PROBE_PROGRAM_FAILED`, read `details.programDiagnostic.stage`. `pre-program-reset` and `pre-program-halt` mean the pre-program preparation failed: no readback, no success receipt and no further programming followed, and the existing owned cleanup still ran. Report that stage verbatim, stop, and do not retry, reset again, repair the target state or open a new connection on your own. Programmer creation and the programming call are later, separate stages (`programmer-create`, `program-call`; `driver-acquire` precedes preparation).
10. If a managed normal flash fails, report any returned `details.recoverySuggestion` exactly as informational: stop, retain the complete diagnostics, and require a new reviewed authorization for any separate recovery attempt. It is never an automatic retry or a second call, and it does not switch routes. Terminal-failure recovery authorization is separate; imported flash has no recovery and receives no such suggestion.

## Explicit external/snapshot import route

Use this route only when the user explicitly selects it and the bound server actually exposes `stm32_firmware_import`, `stm32_firmware_admit`, and `stm32_flash_imported` with input schemas matching this workflow; the published v1.2.0 runtime (48 tools) does not. Before promising the route, call `stm32_doctor` through the actual MCP client, check `ok`, and compare `data.runtime.toolkitVersion`/`data.publicInventory` and the real tool input schemas with the actual client tool list. A separately started launcher/CLI version or `doctor --json` is supporting evidence only, not proof of the live MCP binding. This route adds no context/model prerequisite, and this Skill runs no shell command. It needs no managed `.stm32-project.json`, Git baseline, build receipt, or SVD. `capabilityDetails.flash` and the managed route describe only the managed path and do not block this route. Context not having evaluated an import does not make the route ready or admitted.

1. Ask for the original project-relative firmware path, its exact lowercase SHA-256, the format (`elf`; AXF is parsed as ELF, `hex`, or `bin`), the exact supported pyOCD target, and the reviewed internal-Flash regions. BIN also requires an explicit uint32 base address and carries no debug symbols.
2. Call `stm32_firmware_import` with no `planId` to obtain the read-only PLAN. Show `data.planId`, `data.importId`, `data.source.sha256` (original file) and `data.image.sha256` (normalized programming image, with segments and entry). Admission and flash results report flat `sourceSha256` and `imageSha256` fields. Never conflate the two hashes.
3. Obtain explicit authorization for the offline import copy, then repeat the exact request with that `data.planId` and `authorized=true`. Import authorization covers only the immutable copy and never authorizes hardware.
4. Call `stm32_firmware_admit` with the exact `importId` and original source SHA-256. Report `offlineReady`, `hardwareVerified=false`, and the remaining requirements. Admission success is not a flash success, not a current build, and not a reusable token. Never fabricate a manifest, `buildId`, or Git state to replace it.
5. Only if the user then asks to flash: call `stm32_probe_list`, require one exact `probeId`, restate the exact import, probe, and target, and obtain a new explicit authorization for this exact hardware operation. An existing authorization for this exact operation can cover a requested frequency option; do not ask again solely for it.
6. Before the one call, include `frequencyHz` only if the user explicitly requested a non-default debug frequency (100000..50000000); omit it for the ordinary 100000 Hz (100 kHz) production default in this candidate, and treat a faster value as an optional explicit choice rather than a required 1 MHz gate. On an older runtime with the former default, pass exactly 100000 to select 100 kHz. This route shares the same pre-program preparation: after map admission and identity/authorization checks, it performs one `SYSRESETREQ` reset-and-halt and requires HALTED before programming. State that this reset is part of the same authorized flash operation. Then call `stm32_flash_imported` once with that `probeId`, `importId`, original source SHA-256, `authorized=true`, and the selected frequency. Report the complete result. A successful result includes the external-flash receipt path, `details.postFlash` (`targetState=unknown`, `runVerified=false`), and `details.flashOptions` reporting selected configuration rather than measured frequency, including `preProgramReset=sysresetreq` and `preProgramHaltRequired=true`; some early failure results do not contain these. A `pre-program-reset`/`pre-program-halt` failure means no readback, no receipt and no second programming attempt occurred. This route has no under-reset recovery and must not receive a recovery suggestion, and its `preProgramReset` is never `under-reset-connect`. Report the actual returned fields.

An imported receipt proves only the programming/readback checks for that immutable snapshot. It does not unlock debug, Monitor, Target tests, legacy flash evidence, reset/recovery, or a managed build identity, and it grants no later independent reset authority beyond the one authorized flash operation that produced it. Never present it as a remedy for those workflows or for a failed managed flash.

## Boundaries

- **Managed route only:** never accept a caller-selected target, SVD, ELF path, workspace, endpoint, token, or memory location. Never weaken stale-build, identity, lease, or authorization failures. Missing Git or null Git fields is not a stop for this route, and never a reason to fabricate a commit or change routes.
- **Explicit imported route:** the caller may declare only `firmwarePath`, original SHA-256, `format`, `target`, reviewed internal-Flash `flashRegions`, and the BIN `baseAddress` accepted by the import schema. Do not accept any other override, reuse a receipt as an identity, or let a managed failure select this route.
- Never invoke PyOCD, a compiler, or a process directly. Call only the named MCP tools above.
- Never treat unavailable Git (`gitHead=null`, `gitDirty=null`) as a clean repository.
- Never fabricate physical success. A skipped, simulated, deferred, or failed hardware gate is not a board PASS.
- Under-reset recovery is a separately selected, explicitly authorized policy for the managed route and is not available to the imported flash path. Do not select it automatically after a failure. Recovery flash may leave the target halted; do not claim that it reset or ran. A `recoverySuggestion` is informational only: stop, retain diagnostics, and require fresh authorization before any recovery attempt. It appears only for the exact managed gates in the tool description, never for cleanup, identity, stale, provenance, input, authorization, readback, receipt, success, cancellation, already-recovery, or imported results.
- The confirmed normal flash includes one pre-program `SYSRESETREQ` reset-and-halt plus a HALTED check before programming. Under-reset recovery does not add that reset: it reuses its connection-time reset and only re-verifies that the target is halted. Either reset belongs to this authorized operation and grants no later independent reset, resume, Monitor, handoff or Target-test authority. `preProgramReset`/`preProgramHaltRequired` state selected policy, not execution evidence, and can appear on a failure that never reached the reset. A `pre-program-reset`/`pre-program-halt` diagnostic means the operation stopped there: no readback, no success receipt, no retry or state-repair halt. A successful flash performs no post-flash reset and proves nothing about target execution (`details.postFlash` remains `targetState=unknown`, `runVerified=false`); any later reset, resume or recovery remains separately authorized. Never invent a physical fix or claim the reset cured a hardware fault; physical efficacy needs its own separately authorized hardware acceptance.
- A frequency is configuration, not a measurement. Do not describe `configuredFrequencyHz` or `frequencyHz` as the observed debug clock, and do not edit generated IDE task templates or template digests to set it. `--frequency` and `frequencyHz` exist in published v1.3.3 and in the published v1.3.2 and v1.3.1 packages; the earlier frozen/installed 1.3.0 lacks them. The ordinary 100000 Hz (100 kHz) default is the v1.3.5 local candidate default and is not in the published v1.3.4 or earlier bytes; a VS Code restart does not install it, so ask for an explicit 100000 on an older runtime when 100 kHz is required. The pre-program reset itself is a v1.3.5 local-candidate change and is not in the published v1.3.4 bytes, so do not attribute it to an installed v1.3.4 build. An existing v1.3.2 process does not acquire v1.3.3 behavior by restarting VS Code alone; install or upgrade to v1.3.3 first, then restart once to verify.
- Diagnose a failed attach from its returned stage and last verified state. Do not retry, reset, resume, or add a second hardware operation without fresh authorization.
- Probe enumeration is discovery only; it does not verify target identity, current firmware, or flash readiness. A full Fault analysis requires its own controlled halt authorization; running observation does not grant it.
