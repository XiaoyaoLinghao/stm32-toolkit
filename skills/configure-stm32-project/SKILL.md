# Configure STM32 Project

## New-project routing (before this workflow)

This skill configures an existing, validated project model; it is not a project-creation entry. If the user asks for a **new** STM32 project, or `stm32_project_context` reports no usable model for that request, do not only report "blocked" and stop: explain the separate creation sequence and point them to [the new-project section of the user guide](../../docs/user-guide.md) — read-only `stm32_project_create_plan`, then same-input `stm32_project_create_prepare` (writes only an expiring, single-use authorization under the Toolkit data root; never launches CubeMX or changes the destination), then explicitly authorized `stm32_project_create_apply` with the returned `authorizationDigest`, which stages via CubeMX, configures, builds debug/release and activates the project-relative destination. That flow is published v1.3.3 behavior and needs actual STM32CubeMX plus a matching offline firmware package; Git is never required, and a missing vendor prerequisite is reported with the actual diagnostic rather than replaced by a synthetic fixture. An existing v1.3.2 process does not gain it from a restart alone; install or upgrade to v1.3.3 and restart once before verifying the binding. After a successful apply, bind the applied destination as workspace/MCP project root and return to the workflow below.

## Workflow

1. **Context first.** Call `stm32_project_context` (no arguments). Read `capabilityDetails.configure`: `available` means a valid supported project model is loaded; `blocked` means a named prerequisite is missing; `not-evaluated` means context did not check it. If it is `blocked`, report the context evidence and next step and stop. The legacy `capabilities.configure` boolean remains for compatibility. For a project delivered by `keil convert`, first bind the apply result's `data.outputRoot` as the VS Code workspace and MCP project root, then run context there; configure at that root and never against or inside the read-only Keil source. Git is optional for both new and delivered projects.
2. **Read-only plan.** Call `stm32_project_configure` with no `planId` and no `authorized` — this returns the deterministic `project-configuration-plan` (a PLAN response). Show its `data.plan_id`, every blocker, and each file's status and available diff from `files` (create, unchanged, update-managed, user-drift, unowned-collision, preserved-unowned). Also read and report `data.vscodeGuidance` (`bindingMode`, `requiredUserSettings`, `userSettingsChecked=false`, `preservedPaths`, `diagnostics`), which is explained below. A `preserved-unowned` editor file has no original-content diff because Toolkit does not read it. When the manifest's managed memory has multiple Flash/RAM candidates and no `memory.layout`, the plan fails with `MEMORY_LAYOUT_REQUIRED` and actual `candidates`/`unresolvedRoles`/`remediation`; an explicit layout must be written as the reviewed five-role `memory.layout` object (the migration `memoryLayout` choice) rather than guessed in the configure call. An ambiguous managed project never selects the first RAM automatically.
3. **Stop on blockers.** If `blockers` is non-empty, or any target is `user-drift` or `unowned-collision`, report them and stop; never overwrite user changes. The five fixed `.vscode` JSON targets may be `preserved-unowned` when they are regular files without prior managed records. They are safe to leave in place, but the user must align their IDE configuration with the generated build.
4. **Authorize.** An explicit user instruction that covers this intended mutation and scope (for example "plan and apply only these changes; after reviewing the exact plan, proceed without asking again") remains reusable after you review the actual plan, provided every reviewed change stays inside that instruction. The user does not need to have quoted the not-yet-existing `data.plan_id`; the APPLY request carries the concrete reviewed `plan_id`. Re-review a changed plan, input or scope; ask only when the newly reviewed change exceeds or conflicts with the existing authorization, not merely because a fresh plan ID exists within the already authorized task. Never infer mutation authority from the earlier read-only call; keep the exact plan/input replay and `authorized=true` guards.
5. **Apply.** Only when the user's authorization covers the reviewed mutation (an existing instruction reused within its scope, or newly given), call `stm32_project_configure(planId="<exact data.plan_id>", authorized=true)`. The PLAN response field is `data.plan_id`; the APPLY request argument is `planId`. The core replans and rechecks the model, inputs, and drift guards before its first write.
6. **Return the result.** Report the `project-configuration-apply` result: the managed manifest path, created/updated paths, `preservedPaths`, warnings, and `vscodeGuidance` (including an unchanged/idempotent apply). The preserved paths are outside the managed manifest and must not be counted as generated or unchanged files. If the result is a failure (`AUTHORIZATION_REQUIRED`, `PLAN_CHANGED`, `GENERATION_*`), report the exact code and details and stop.

## Optional explicit debug pair (post-migration)

The ordinary call above omits `debugBackend`/`debugTarget` and keeps the historical plan shape. To record exactly `debug.backend` and `debug.target` in an existing valid Schema v2/v3 manifest, pass **both** values — MCP `stm32_project_configure(debugBackend="pyocd", debugTarget="<pyocd-target>")`, CLI `stm32-toolkit project configure --project <abs> --debug-backend pyocd --debug-target <pyocd-target> --dry-run --json`. The same project and the same pair must be used for PLAN and APPLY; `pyocd` is the only supported backend and the target is syntax-checked only (never discovered, installed, trimmed, case-folded, coerced or mapped from a Keil device).

1. PLAN is read-only. Besides `data.plan_id`, `data.inputs[]`, `data.files[]` and `data.blockers[]`, read `data.debug_configuration` and `data.manifest_edit`: `path`, `status` (`update`/`unchanged`), `before_sha256`/`after_sha256`, `before_size`/`after_size`, and the full `unified_diff`. Confirm the diff changes only those two debug keys and preserves `svd`, `svdDevice`, `readableRegions`, `memory`, `generation` (including `linkerFragment`) and all other fields. `status=unchanged` means the exact manifest bytes stay untouched. If `blockers` is non-empty, stop.
2. One value alone, a non-string, an empty/whitespace value or an unsupported backend returns `DEBUG_CONFIGURATION_INVALID` before any write, with `details.field`/`rule`, complete `details.diagnostics[]` (`code`, `field`, `rule`, `message`, `remediation`) and `details.missingFields[]`. Report every diagnostic; the remediation names the real `project configure` / `stm32_project_configure` entries and the paired parameters.
3. Apply step 4's authorization rule to this exact reviewed plan, then APPLY with the same pair and project: `stm32_project_configure(debugBackend="pyocd", debugTarget="<same>", planId="<exact data.plan_id>", authorized=true)` or CLI `stm32-toolkit project configure --project <same abs> --debug-backend pyocd --debug-target <same> --apply --json --plan-id <data.plan_id> --authorized`. An omitted or changed pair, or changed inputs, is refused with `PLAN_CHANGED`/a structured failure and writes nothing.
4. A successful manifest edit naturally invalidates earlier build/firmware identity. Rebuild with `clean` when required (`stm32_build` with `clean=true`); never repair hashes or receipts by hand. A configured pair is metadata only: it does not create a debug session, `launch.json` stays empty, and a real debug handoff remains a separate authorized step. `data.debugConfiguration` in `stm32_project_context` has the shared shape: `backend`/`target` (null when absent), `status` (`configured` or `needs-user-input`), `missingFields`, `diagnostics` (each with `code`/`field`/`rule`/`message`/`remediation`), `targetSupport` always `not-checked`, `hardwareVerified` always false, and `nextSteps`. When missing/invalid, the affected `capabilityDetails.flash`/`targetTest`/`monitor`/`breakpointDebug` are `blocked` with all reasons, while build/configure availability is unchanged; a valid pair never turns hardware booleans true.

This pair option was introduced in v1.3.2: the earlier frozen/installed 1.3.0 runtime lacks it. The published v1.3.2 package contains it, and v1.3.3 keeps it unchanged; an installed v1.3.1 package may predate later fields. No new MCP tool was added. Installation or upgrade requires separate authorization. `data.vscodeGuidance` below was likewise introduced in v1.3.2 and may legitimately be absent from a v1.3.1 implementation.

## PLAN/APPLY guidance (`data.vscodeGuidance`)

Every successful PLAN and every successful APPLY result, including an unchanged/idempotent apply, carries `data.vscodeGuidance`; report it as received. `bindingMode` is `user-settings` for the portable default route and `explicit-paths` only after the existing paired validation. `requiredUserSettings` lists `stm32-toolkit.executablePath` and `stm32-toolkit.compilerPath` for the default route and is empty for explicit bindings. `userSettingsChecked=false` means this offline call did not evaluate your effective VS Code settings to determine whether these bindings exist, so it makes no claim that the settings are absent or complete; workspace configuration may also define them. This does not mean no managed editor bytes are ever read: `preserved-unowned` editor contents are never read, and their bytes remain unchanged. `preservedPaths` is exactly the plan's `preserved-unowned` paths.

`VSCODE_EXECUTABLE_SETTINGS_REQUIRED` (`severity="info"`) on the default route means this generator's supported default guidance is to put both reviewed absolute native executable paths in User Settings, or to re-run PLAN and APPLY with the same paired CLI/MCP options; never imply that PATH installation is required. An explicit pair must not receive this diagnostic. When `.vscode/tasks.json` is `preserved-unowned`, `VSCODE_TASKS_PRESERVED` (`severity="warning"`, `path=".vscode/tasks.json"`) means the existing tasks were retained and the requested bindings/new tasks were not applied to that file, whose contents were not inspected; old bare commands may remain. Do not claim a bare command was found. Ask the user to review that file manually against the absolute managed runtime executable or the documented User Settings, and to inspect PLAN `data.files[].status`/`unified_diff` plus APPLY `data.preservedPaths`. Guidance is advisory: it never authorizes a write, never changes generated bytes or plan identity, and is not proof of installation or IDE use.

## Optional VS Code executable binding

The ordinary call above renders the portable user-setting defaults. To render reviewed absolute native executables instead, pass **both** `vscodeToolkitPath` and `vscodeGccPath` (CLI `--vscode-toolkit-path`/`--vscode-gcc-path`) on PLAN and on APPLY with the same plan ID. Both values are validated static absolute native files; read the [VS Code executable-binding section of the user guide](../../docs/user-guide.md) for the exact field schema and validation rules. The pair is invocation-scoped and is never written into `.stm32-project.json`: repeat it on every later configure PLAN/APPLY that should preserve the binding. A new PLAN that omits both deliberately returns `.vscode/tasks.json` and `.vscode/c_cpp_properties.json` to the `${config:...}` portable defaults; show that diff and review it before APPLY. Do not supply only one value, persist machine paths in the project model, or repair managed hashes/digests by hand. This option was introduced in v1.3.2: the earlier frozen/installed 1.3.0 runtime lacks it, and an installed v1.3.1 package may predate the v1.3.2 guidance. The published v1.3.2 package contains it, and v1.3.3 keeps it unchanged; no new MCP tool was added. Installation or upgrade requires separate authorization.

## Rules

- The plan call is read-only; show it before any mutation.
- The apply call is the only mutation. Pass exactly the plan ID shown to the user.
- Do not edit generated files, run CMake, or invoke compilers yourself.
- Configure preserving an editor file does not make CubeMX regeneration ready: regeneration has its own closed inventory and can still reject an unknown editor path. Without `memory.stackSize`/`memory.heapSize`, the generated linker template reserves the historical default 4 KiB heap and 1 KiB stack. A migration-generated manifest from the reviewed `startupStrategy="generate-cmsis-gcc"` route instead records the exact source-derived byte counts and emits them as exact linker values (`_Min_Heap_Size`/`_Min_Stack_Size`); do not replace them with 4K/1K. Memory usage reports linker allocation/reservation, not runtime peak use.
- `memory.layout` has exactly `flash`, `data`, `bss`, `heap` and `stack`, each naming an existing region; Flash must be readable, executable and non-writable, and the other four readable and writable. The generated linker places each section in its selected region and keeps the `.data` load address in Flash. An explicit all-main-RAM mapping is valid and leaves other RAM unused. A writable executable RAM is never inferred as Flash, and CCM/external SRAM is never selected automatically. An omitted layout is accepted only for an unambiguous single non-writable Flash plus single readable/writable RAM. `memory.layout` is rejected, never ignored, with `generation.nativeLinkerScript`; the native linker remains user-owned. Fixed absolute sections stay `NOLOAD` placements in their address region; Toolkit does not add an implicit copy/zero table for them.
- `generation.runtimeInitialization` has exactly one supported value, `cmsis-gcc-v1`. It is valid only with the managed linker template and adds `.preinit_array`/`.init_array`/`.fini_array` sections plus `__initial_sp`/`__heap_base`/`__heap_limit` compatibility aliases required by the generated startup. It is rejected, never silently ignored, when `generation.nativeLinkerScript` is present. A native linker script remains user-owned.
- The generated `Startup/stm32tk_startup_gcc.S` is project input, not a managed generation target. Do not edit it, delete the original ARMCC startup, or claim the GCC runtime is ARMCC, ABI or Microlib equivalent. Review the generated reset/vector/RAM assumptions and build the result through the authorized build entry.
- Never claim success; report the returned `OperationResult` exactly as received and finish immediately.
