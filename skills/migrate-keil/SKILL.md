# Migrate Keil Project

## Workflow

1. **Context and binding first.** Call `stm32_project_context` (no arguments). Read `capabilityDetails`, not only the legacy booleans: `status=available` means the entry point applies to this project, `blocked` means a named prerequisite is missing, and `not-evaluated` means context did not check it. `hardwareDiscovery=not-performed` means no probe was queried. Context never scans all sources or proves migration readiness. Keep `data.project.root` authoritative. If this workflow needs v1.3.1-only options, compare `stm32_doctor` `data.runtime.toolkitVersion` and `data.publicInventory` with the actual tool list/input schemas the client exposes; a CLI/launcher version does not prove the bound server's version. After an upgrade restart VS Code once and verify again. Missing tools/fields or a different root means preserve the full result and stop the dependent operation.
2. **Select and inspect.** Use `data.project.files` to identify the project-root-relative `.uvprojx` (context does not list target names). For multiple project candidates, ask the user to choose one. If the exact target is unknown, call `stm32_keil_inspect(uvprojx="<selected relative path>", includeBaseline=true)` and omit `targetName`; on `KEIL_TARGET_SELECTION_REQUIRED`, present `details.targets` and let the user choose, then inspect again with that exact `targetName`. A successful result carries `data.inspection.target_name`; preserve that exact value, plus the same `uvprojx`, for every later call. Never guess a target. `baseline.available` only means a historical AXF or MAP was found and parsed; it does not prove a current build, toolchain, source identity, or authorized baseline.
3. **Preflight without Git.** Call `stm32_keil_preflight(uvprojx="<same path>", targetName="<same target>")`. Preflight is read-only, requires no Git, and returns typed `analysis.blockers` separately from `planReadiness` (prerequisites for an applicable plan and progression to APPLY; Git/root prerequisites can still prevent any PLAN) and `applyReadiness` (always false pending a reviewed, authorized plan). A successful call means analysis completed; it does **not** mean the project is ready to apply and never returns an applicable plan ID. A read-only PLAN can still be requested for diagnostics when Git/root prerequisites permit even while blockers exist; it contains those blockers and its planId is not applicable, so do not claim a blanket inability to generate a diagnostic plan. Report every blocker and every unmet prerequisite, including whether the repository, committed HEAD, toplevel, or clean worktree is missing. Each blocker adds `remediation` with `category` (`needs-user-input` or `unsupported`), a concise `summary`, an optional `tool` naming a real MCP tool, an optional `skill` naming a companion Skill (the two are never conflated), and `requiredInputs`; `blockerSummary.byRemediation` counts the same classifications while the original code/rule_id/path/line/column/evidence/message fields stay unchanged. When supported source rewrites are proposed, `analysis.sourceChanges` is an additive concise list of `{path, ruleIds, beforeSha256, afterSha256}` from the same patch evidence; PLAN still carries the full `data.patches[].unified_diff`. Use it only to distinguish proposed supported changes from blockers — it grants no authorization. Supported common syntax is narrow, and its new function/declaration rules apply only to C sources (the historical numeric `__at` placement form remains for C++), while the exact standalone no-semihosting pragma is supported for both C and C++: an exact `__asm void` wrapper (zero-argument WFI/CPSID I/CPSIE I, or a known 32-bit/`unsigned int`/`unsigned long` MSP setter) whose body is exactly the instruction plus `BX LR`/`BX R14`, rewritten to a GNU `naked` basic-asm function; bounded `__align(n)` (positive power of two at most 4096) on one plain object, composable with a supported fixed address only when that resolved address is a multiple of `n`; a single uninitialized scalar/array absolute placement whose bounded expression resolves from target defines and contained quoted guarded headers; and only the exact standalone `#pragma import(__use_no_semihosting)` (removed, with an explicit `build.newlibSpecs=["nosys.specs"]` in the manifest proposal). Unknown/conditional/redefined/`#undef`/function-like macros, extra instructions or prototypes, pointers, initializers, `extern`/`typedef`, zero-length arrays, mixed/unknown attributes, C++ new function/declaration forms, and unsupported ARMCC pragmas retain blockers; other generic pragmas keep their existing behavior. Only inputs the current preflight actually accepts may be recommended: `memoryLayout` and `extraRegions` here, and the separate `startupStrategy`/`startupSource` opt-in below. There is no framework, FPU, or ABI override parameter, no blocker is auto-fixable, and unknown codes remain unsupported. Read `analysis.floatAbi` on every preflight (PLAN returns the same object as `data.floatAbi`; the conversion report uses `floatAbi`): numeric `uFloatingPoint` values are not ABI evidence, literal `soft`/`softfp`/`hard` is a project declaration only, and default hard linkage is inferred only for ARMCC + Cortex-M4 + FPU2 when the selected target's `ArmAdsMisc/RvdsVP` is absent/empty or the historical value `2`. Any other nonempty selector, compiler/CPU/FPU tuple, or unknown numeric value stays blocked, even when a literal ABI is declared. `baselineVerified` is always false: inspect the actual compiler command lines, objects and libraries, and never edit evidence, selectors, or digests to clear a blocker. Blocked float-ABI or hardware-selection evidence stops progression toward APPLY, not diagnostic planning: when Git/root prerequisites permit, a read-only PLAN may still be returned with blockers, and that planId is never applicable. When a group or file scope carries only `IncludePath` and the analysis produced merge evidence, preflight also returns additive `analysis.includeMerges`: one entry per scope/owner and normalized directory with `decision` `added` or `already-present` (added entries also carry `inventorySha256`/`inventoryFiles`; the PLAN `include_merges` entries use the same fields in snake_case, `inventory_sha256`/`inventory_files`). Only scopes whose compiled sources are included C/C++ contribute; listed headers and precompiled libraries do not execute a compiler and are ignored for this decision (so a C/C++ group that also lists headers still merges), an excluded file scope, a header/library-only group or file, or a group with no included source is ignored, while a scope that also has defines, misc controls, included assembly, or an unknown compiled language stays a single `ARMCC_OPTION_UNSUPPORTED` blocker without a partial merge. Any `MIGRATION_INCLUDE_*` blocker (missing, not-directory, escaping, unreadable, unsupported redirect, aggregate traversal/hash limit, or one case-insensitive include-relative key resolving to different files in two search roots) rejects the whole include analysis, so no partial merge is reported and the proposal keeps the original target include list. Overlapping search roots are allowed when they expose the same physical files (for example a target `USER` directory plus a scoped `USER/IWDG` directory); only a key that resolves to distinct files is ambiguous.
4. **Optional CMSIS startup review.** A conventional ST/CMSIS Cortex-M ARMCC startup is supported only through the explicit opt-in `startupStrategy="generate-cmsis-gcc"` (CLI `--startup-strategy generate-cmsis-gcc`). Add `startupSource="<exact project-relative included ARMCC .s path>"` (CLI `--startup-source`) whenever more than one included non-empty assembly source exists; omitting it then returns `MIGRATION_STARTUP_SELECTION_REQUIRED` with `details.candidates`. Omit both options to retain the existing `ARMCC_ASSEMBLY_UNSUPPORTED` blockers. The same two values must be passed to preflight, convert and apply; they are bound into the plan digest and apply replans with them, so a caller-edited or omitted choice is never accepted (a valid but different choice returns `PLAN_CHANGED`; a malformed option value returns a structured validation error). Preflight's `planReadiness.nextSteps` repeats the exact startup choice to retain. The managed destination is `Startup/stm32tk_startup_gcc.S`; the original ARMCC startup is never modified or deleted. Review `analysis.startup` (source path/hash, ordered vector entries and reserved slots, stack/heap bytes, reset pattern, generated path/digest, warnings, diagnostics). Supported sources are normalized cortex-m3, cortex-m4 and cortex-m7 conventional files; unknown instructions, custom reset/handler code, multiple vector tables, vector expressions, unsupported cores/layouts and undeclared handlers remain blockers. The generated GCC runtime is not ARMCC, ABI or Microlib behavioral equivalence, and a `MIGRATION_STARTUP_TARGET_COLLISION` is never overwritten.
5. **Explicit multi-RAM placement.** Read `analysis.memoryLayout` on every preflight. `status=implicit` means exactly one non-writable Flash and one readable/writable RAM were resolved; no option is needed and the historical manifest bytes/model hash are preserved. `status=requires-selection` appears with an ordinary `MEMORY_LAYOUT_REQUIRED` blocker (other blockers are still returned): show `candidates.flash` and `candidates.ram` with their actual names, origins, lengths and attributes, and ask the user to choose. The explicit value is a JSON object with exactly `flash`, `data`, `bss`, `heap`, `stack` naming existing regions (MCP `memoryLayout`, CLI `--memory-layout`). Pass a real object to MCP, not a JSON string: the registered `memoryLayout` schema is `dict[str, str]`, so the MCP framework rejects non-object values and objects whose role values are not strings with a `ToolError` before Toolkit runs (for example `string_type` validation at `memoryLayout.flash`); those are not Toolkit `MEMORY_LAYOUT_INVALID` results. Only schema-valid objects reach Toolkit: unknown/incomplete roles and empty string values fail before inspection with structured `MEMORY_LAYOUT_INVALID` field/rule/remediation, while logical region/access validation (whether each named region actually exists and has the required permissions) runs after reading the actual declared regions and returns the same structured error at that point. The CLI `--memory-layout` takes a JSON object string: malformed or duplicate-key JSON and missing/unknown/non-string/empty role values use the same Toolkit `MEMORY_LAYOUT_INVALID`, while a repeated `--memory-layout` option is the existing sanitized parser error. Use only names actually returned in `data.analysis.memoryLayout.candidates`, for example `memoryLayout={"flash": "<candidate flash region name>", "data": "<candidate RAM region name>", "bss": "<candidate RAM region name>", "heap": "<candidate RAM region name>", "stack": "<candidate RAM region name>"}`; the quoted placeholders are not real choices. Flash must be readable, executable and non-writable; the other four must be readable and writable. Never choose a writable executable RAM as Flash, never infer CCM/DMA accessibility, and never invent an external region. An all-main-RAM mapping is valid and leaves other RAM intentionally unused. The same exact mapping must be passed to preflight, plan and apply; omission versus an explicit mapping is a different reviewed request. `status=explicit` in the PLAN response binds that mapping into `data.plan_id`; the PLAN field `data.memory_layout` also exposes the resolved layout or required candidates (preflight exposes the same decision evidence as `data.analysis.memoryLayout`). A native linker-script project cannot also declare `memoryLayout`.
   External RAM is a separate explicit input accepted by the same three calls: MCP `extraRegions` (a real array of objects, registered as `list[dict[str, Any]]`) and CLI `--extra-regions '<json array>'`. Each entry has exactly `name`, `origin`, `length` and `attributes`; only `rw-`/`rwx` writable RAM is allowed, names are 1-64 character ASCII linker identifiers, origin/length are exact JSON integers describing a non-empty half-open range, at most 32 entries are accepted, and entries may not overlap the declared base or each other. Never guess a capacity or infer one from a device/address/board; ask the owner for the exact origin and byte length. Extra RAM adds RAM candidates only, never Flash. Managed `.data`/`.bss`/`.heap`/`.stack` are not placed there implicitly: if the only writable region is the extra RAM, preflight still returns `MEMORY_LAYOUT_REQUIRED`, and an explicit `memoryLayout` must name it. Preflight exposes the request as `data.analysis.extraRegions`, PLAN as `data.extra_regions` and binds it into `data.plan_id`, and the conversion report records `extraRegions`; the proposed manifest keeps the inspected Keil `memory.regions` unchanged and adds `memory.extraRegions`. Omission and an empty array are the same no-extra request; omitting, shortening or changing any entry on PLAN/APPLY returns a structured validation error (including `EXTRA_REGIONS_INVALID`, or `MEMORY_LAYOUT_INVALID` when a retained explicit layout still names the omitted region) or `PLAN_CHANGED` without writing. The frozen/installed 1.3.0 runtime also lacks this source-only patch, so verify the bound server's actual tool inventory and input schema rather than trusting a version number. The CLI JSON path rejects duplicate keys, deep nesting, oversize input and repeated options before inspection; the MCP framework rejects non-array/non-object values before Toolkit runs, while schema-valid but semantically invalid values return `EXTRA_REGIONS_INVALID` field/rule/remediation. Fixed sections remain `NOLOAD` and are not promised initialized; the owner must initialize external memory before access, and an external stack can require earlier bootstrap than `SystemInit`. A native linker script remains user-owned and is not rewritten.
6. **Resolve blockers, not rules.** Report encoding, assembly, scoped compiler option, scatter/memory, and manifest conflicts with their portable paths and safe next steps, using the returned `remediation` category: `needs-user-input` means a real supported selection or reviewed preparation exists; `unsupported` means no automatic fix exists and the evidence must be handled as a project-owned change. Toolkit never silently transcodes non-UTF-8 input, blindly replaces ARMCC startup code, edits a conflicting manifest, deletes untracked files, or weakens a rule to make preflight pass. The startup opt-in above does not translate arbitrary assembly: unrelated `.s` files remain `ARMCC_ASSEMBLY_UNSUPPORTED`. For a source-encoding blocker, the supported preparation route is the separate `normalize-source-comments` companion skill: it previews explicitly declared per-file charsets and copies only reviewed comment-only UTF-8 files to a new external directory. It never edits the original project, guesses a charset, or resolves startup, scoped-option, scatter/memory, Git/apply, or baseline blockers. When the strict preview reports undecodable bytes, or private-use/C1-control/U+FFFD/noncharacter code points, an explicit user request to replace those units with a literal `?`, together with the declared charset, authorizes a read-only replacement preview (`preview --replace-invalid-with '?'`). A strict `DECODE_ERROR` has not yet classified the bytes as comment content; the preview does, and it can block the file. It replaces only lexically proven comment content, records each original byte range and reason, and still blocks non-comment spans, incomplete constructs, DBCS/backslash ambiguities and replacement-created trigraphs. Each accepted lossy file then requires its own explicit `copy --confirm-file '<relative path>'` reflecting the reviewed per-file choice; never loop over `lossyFiles` to manufacture confirmations, and if a lossy file is declined, re-preview the narrowed selection instead of editing the plan or copying unapproved files. Confirmation is per-file review evidence, never bulk approval and never permission to edit originals.
7. **Git is an owner decision.** A missing Git repository, unborn HEAD, or dirty/untracked work blocks only planning/apply, not analysis. Explain the exact prerequisite and let the project owner decide whether to establish a clean committed baseline. Never run `git init`, commit, stash, clean, or rewrite Git state on the user's behalf.
8. **Read-only plan.** When preflight's Git/root prerequisites permit a PLAN, call `stm32_keil_convert(uvprojx="<same path>", targetName="<same target>", startupStrategy="<same value or omitted>", startupSource="<same value or omitted>", memoryLayout=<same reviewed object, or omit the argument>, extraRegions=<same reviewed array, or omit the argument>)` with no `planId` and no `authorized`, even when technical blockers remain. A blocker-free preflight with `planReadiness.ready=true` is required only for a plan that could later be APPLYed, not for requesting this read-only diagnostic plan. This returns the deterministic, Git-bound `keil-conversion-plan` (a PLAN response); a diagnostic plan still carries `data.blockers`, and its `plan_id` is never applicable. Attribute fields to the response that actually returned them: preflight-only `data.analysis.blockerSummary`, blocker `remediation`, `data.analysis.sourceChanges`, `data.planReadiness` and `data.applyReadiness` belong to the preflight payload. A PLAN exposes `data.plan_id`, `data.blockers`, `data.patches[]`, and `data.startup`/`data.floatAbi`/`data.memory_layout`/`data.extra_regions`/`data.include_merges` only when actually returned; it does not carry the enriched preflight keys. Do not claim those keys exist in the PLAN or invent missing fields; label the source response when reporting both. Show its `data.plan_id`, every blocker, `data.startup` when present, and the exact changed paths and diffs from `data.patches[].unified_diff`. For the startup route, verify that only the selected ARMCC source is replaced in `build.assemblySources`, that the new `Startup/stm32tk_startup_gcc.S` patch accompanies the normal manifest/source patches (it is the only generated assembly patch, not the only output file), and that `memory.stackSize`/`memory.heapSize` plus `generation.runtimeInitialization="cmsis-gcc-v1"` match the evidence. When `data.include_merges` is present, compare it with the project's actual group/file scopes: confirm every `added` directory appears exactly once at the end of `build.includePaths` in the manifest patch, that the original target directory order is unchanged, that a repeated or already-exposed physical directory is `already-present`, and that the returned `inventory_sha256`/`inventory_files` are the tool's evidence. For the supported common-syntax rules, confirm the exact rule IDs in both views: preflight reports camelCase `data.analysis.sourceChanges[].ruleIds`, while each PLAN source patch exposes snake_case `data.patches[].rule_ids` (for example `ARMCC_NAKED_ASM_FUNCTION`, `ARMCC_ALIGN_ATTRIBUTE`, `ARMCC_ABSOLUTE_PLACEMENT`, `ARMCC_NO_SEMIHOSTING_PRAGMA`), that a rewritten naked wrapper is plain `naked` basic asm with the instruction immediately followed by `bx lr` and no C stack switch, and that a no-semihosting rewrite adds exactly `build.newlibSpecs=["nosys.specs"]` to the manifest patch while the managed CMake link line later emits `--specs=nosys.specs` once (no implicit `nano.specs`). A fixed address outside every declared memory region is `MIGRATION_FIXED_SECTION_OUTSIDE_MEMORY` with `needs-user-input` remediation and `requiredInputs=["extraRegions"]`; report it, ask the owner for the exact origin/byte length, and never invent or guess external SRAM. Never edit the plan, patch, plan ID, or managed hashes, and never delete a scope, define, or misc control merely to force migration.
9. **Stop on blockers.** If `data.blockers` is non-empty, report them and stop progression toward APPLY; never apply a blocked plan. This does not forbid a read-only diagnostic PLAN when Git/root prerequisites permit: it may still be produced, contains the blockers, and its planId is not applicable.
10. **Authorize.** An explicit user instruction that covers this intended mutation and scope (for example "plan and apply only these changes; after reviewing the exact plan, proceed without asking again") remains reusable after you review the actual plan, provided every reviewed change stays inside that instruction. The user does not need to have quoted the not-yet-existing `data.plan_id`; the APPLY request carries the concrete reviewed `plan_id`. Re-review a changed plan, input, option or scope; ask only when the newly reviewed change exceeds or conflicts with the existing authorization, not merely because a fresh plan ID exists within the already authorized task. Never infer mutation authority from inspection, preflight or a read-only PLAN-only request. Keep the exact `planId`/parameter replay and `authorized=true` guards.
11. **Apply.** Only when the user's authorization covers the reviewed mutation (an existing instruction reused within its scope, or newly given), call `stm32_keil_convert(uvprojx="<same path>", targetName="<same target>", startupStrategy="<same value or omitted>", startupSource="<same value or omitted>", memoryLayout=<same reviewed object, or omit the argument>, extraRegions=<same reviewed array, or omit the argument>, planId="<exact data.plan_id>", authorized=true)`. The PLAN response field is `data.plan_id`; the APPLY request argument is `planId`. The core replans with the request startup options and rechecks the digest, Git, input-drift, and authorization guards before its first write. If the startup evidence, destination collision state or options differ, it returns `PLAN_CHANGED` or a stable `MIGRATION_*` failure and writes nothing.
12. **Return the result.** Report the `keil-conversion-apply` result: the conversion report path, the schema-3 `.stm32-project.json` path, patched source paths, created paths (including `Startup/stm32tk_startup_gcc.S` when generated), and any warnings. If the result is a failure (`AUTHORIZATION_REQUIRED`, `PLAN_CHANGED`, `MIGRATION_*`), report the exact code and details and stop. After apply, configure and build through their own read-only plan and explicit authorization steps.

## Post-migration configure: owner NOLOAD linker fragment

After the conversion is applied, a user-owned writable-RAM `NOLOAD` section fragment may be wired into the managed linker through the ordinary configure workflow. This is current-source/candidate behavior: the published v1.2.0 runtime (48 tools) and the frozen/installed 1.3.0 do not contain this source-only patch. Tool inventory and input schema are unchanged by this patch, so they **cannot** distinguish an unpatched older 1.3.0 from a patched runtime; do not use tool counts, versions or schema presence as proof. Require a runtime verified as built from this patch (installation/upgrade needs separate authorization), then confirm support with a read-only configure PLAN against a reviewed manifest: `data.inputs[]` must include the fragment `path`/`sha256`, the `linker/stm32tk.ld` `unified_diff` must contain the fragment sections, and `data.blockers` must be as expected. If the PLAN lacks that evidence or fails, stop; do not apply. **No new MCP tool or migration parameter exists**: edit the reviewed `.stm32-project.json` by adding only `"linkerFragment": "linker/user.ld"` to the existing `generation` object (keep `cubeMxIoc`, `nativeLinkerScript`, `managedManifest`, `generatedDirectories`, `userDirectories` and any `runtimeInitialization` unchanged) and create that user-owned file, then use the existing `stm32_project_configure` or CLI `project configure`.

1. `stm32_project_configure()` with no `planId` and `authorized=false` is the read-only PLAN. Review `data.plan_id`, `data.model_sha256`, `data.inputs[]` (the fragment `path`/`sha256` must be present), `data.files[]` (especially the `linker/stm32tk.ld` `status`/`unified_diff`), `data.blockers[]`, and `data.managed_manifest_path`. CLI equivalent: `project configure --project <abs> --dry-run --json` (global `--project-root <abs>` before the subcommand is also valid; use the same project root for PLAN and APPLY). Fragment-layer failures return `ok=false`, `code=LINKER_FRAGMENT_INVALID`, with `details.path`/`field`/`rule`/`remediation` (and `line`/`column` when applicable). Earlier failures keep their existing contracts: a null/empty/non-string value is `PROJECT_SCHEMA_INVALID`, and manifest path containment (`rule=pathWithinProjectRoot`) can also fail before fragment semantics. Read the actual `code`/`details`; do not assume one precedence. Fix the fragment, not the managed files or digests.
2. Apply step 10's authorization rule to this exact reviewed fragment plan, then call `stm32_project_configure(planId="<data.plan_id>", authorized=true)` (CLI `project configure --project <abs> --apply --plan-id <data.plan_id> --authorized --json`). APPLY reports the existing camelCase `planId`, `modelSha256`, `createdPaths`, `updatedPaths`, `unchangedPaths`, `preservedPaths`, `warnings`, `managedManifestPath`, `managedManifestSha256`, `templateVersion`; it revalidates the fragment bytes and writes nothing on a changed/deleted path.
3. The fragment is not `extraRegions`, `memoryLayout`, `fixedSections` or `nativeLinkerScript`. It may only contribute custom writable-RAM `NOLOAD` output sections whose selectors stay in their own family and whose region names already exist in the canonical map (multiple RAMs still require the explicit layout). Managed/standard families are reserved by broad name prefixes: any selector under `.text*`, `.rodata*`, `.data*` or `.bss*` (including names such as `.data_ext` or `.bss_ccm`) is rejected, as are small-data, TLS, dynamic metadata, constructors/unwind, heap/stack and `.stm32tk.abs.*`. Valid custom names such as `.sram2` or `.ccm` are accepted only with selectors in their own output-section family; do not relax the parser to admit a reserved prefix. Sections render after fixed sections and before `.data`; they are never copied or zeroed, so initialized objects must not rely on initializers there and external RAM must be initialized before access. A fragment cannot coexist with a native linker script.
4. Fragment edits (including comments), deletion, path changes and option removal invalidate the configuration and build evidence. Build refuses before spawning the compiler. A deleted/unreadable fragment normally fails model loading first: `BUILD_PROJECT_INVALID` with `details.rule=missing` (or the actual model-layer rule) and the fragment remediation, not one of the provenance-only rules. Option removal, missing managed provenance, changed path/digest and changed model hash report `BUILD_PROJECT_INVALID` with `details.rule` `linkerFragmentRemoved`, `linkerFragmentMissing`, `linkerFragmentChanged` or `modelChanged`. Read the actual code/rule and remediation, then rerun configure PLAN/APPLY and rebuild (use `clean` when required). Never edit `linker/stm32tk.ld`, `.stm32-toolkit/generated-files.json` or build receipts to compensate. The generated CMake only gains `LINK_DEPENDS` on the merged linker for this route; direct CMake/Ninja use does not re-parse fragment changes, so reconfigure through Toolkit first. Omission preserves the historical model hash and generated bytes.

## Post-migration configure: explicit PyOCD debug pair

An ordinary conversion writes `"debug": {}` and remains a valid build-only project. Preflight reports this planned post-migration state additively as `data.debugConfiguration` using the shared shape: `backend`/`target` null, `status=needs-user-input`, `missingFields`, `diagnostics` (`code`/`field`/`rule`/`message`/`remediation`), `targetSupport=not-checked`, `hardwareVerified=false`, `nextSteps`, plus `phase=post-migration` and `blocking=false`. It is **not** a technical blocker, does not change `analysis.blockers` or `planReadiness`, adds no Git dependency and invents no plan ID; ordinary conversion PLAN/APPLY still require their existing Git baseline, plan ID and explicit authorization. Never treat this guidance as a migration failure or add it to the blockers list.

After the conversion is applied, record a debug pair with the existing configure workflow — no new MCP tool and no migration parameter:

1. PLAN with the same project and pair: MCP `stm32_project_configure(debugBackend="pyocd", debugTarget="<pyocd-target>")`, CLI `stm32-toolkit project configure --project <abs> --debug-backend pyocd --debug-target <pyocd-target> --dry-run --json`. Read `data.plan_id`, `data.debug_configuration`, `data.manifest_edit` (`path`, `status`, `before_sha256`/`after_sha256`, `before_size`/`after_size`, full `unified_diff`), `data.inputs[]`, `data.files[]` and `data.blockers[]`. Confirm only `debug.backend`/`debug.target` change and `svd`, `svdDevice`, `readableRegions`, `memory`, `generation` and other fields are preserved. Both values are required; raw values are never trimmed, case-folded, coerced or auto-mapped from the Keil device, and an invalid/partial pair returns `DEBUG_CONFIGURATION_INVALID` with complete diagnostics before any write.
2. Apply step 10's authorization rule to this exact reviewed plan, then APPLY with the same project and pair plus `planId=<exact data.plan_id>` and `authorized=true`: MCP `stm32_project_configure(debugBackend="pyocd", debugTarget="<same>", planId="<exact data.plan_id>", authorized=true)`, CLI `stm32-toolkit project configure --project <same abs> --debug-backend pyocd --debug-target <same> --apply --json --plan-id <data.plan_id> --authorized`. Omitted/changed pairs and input drift are refused with `PLAN_CHANGED`/a structured failure without writing.
3. A configured pair is metadata only. It does not discover/install/verify a PyOCD target, prove the physical device, create a debug session or fill `.vscode/launch.json`; a real handoff is separate and explicitly authorized. Existing build/firmware identity becomes stale after the manifest edit — rebuild with `clean` when needed and never hand-repair hashes or receipts.

This configure pair is current-source/candidate behavior and is absent from the frozen/installed 1.3.0; installation or upgrade requires separate authorization.

## Rules

- `stm32_keil_inspect`, `stm32_keil_preflight`, and the plan call are read-only; verify the plan before any mutation.
- `stm32_keil_preflight` already exists in the frozen v1.3.0 package, with `analysis.blockers`, the blocker summary, `planReadiness`/`applyReadiness`, and the `startupStrategy`/`startupSource`/`memoryLayout` options. The current v1.3.1 additions are per-blocker `remediation`/`blockerSummary.byRemediation`, `extraRegions` (`analysis.extraRegions`), and the other additive fields named above. The published v1.2.0 runtime (48 tools) does not expose `stm32_keil_preflight` or any of these options at all. Confirm the bound server's actual tool inventory and input schema before promising a specific field or option, and never present an unreleased option as available on an installed runtime that lacks it; conversely, do not describe the whole preflight tool or its basic blocker payload as absent from 1.3.0, and do not infer server staleness from a version string or inventory count. Compare `stm32_doctor` `data.runtime.toolkitVersion`/`data.publicInventory` with the actual client tools; a launcher version alone is not binding proof. After an upgrade restart VS Code once and re-verify.
- Capability or entry-point availability does not establish migration readiness. Only the current preflight/plan evidence does.
- Within this migration workflow, the apply call is the only project mutation. Pass exactly the reviewed `data.plan_id` as the APPLY request's `planId`, with the exact same project/target selection and the exact same `startupStrategy`/`startupSource` values (or both omitted). The exact same `memoryLayout` object and `extraRegions` array are retained on plan and apply; omission and an explicit all-main-RAM mapping are different reviewed choices, and a changed or omitted request returns `PLAN_CHANGED` or a structured validation error (for example `MEMORY_LAYOUT_INVALID` when the retained explicit layout names a region that the omitted extra request no longer declares); do not promise a single precedence. External RAM remains owner-supplied: never infer a capacity, never treat it as Flash, and never claim it is initialized or hardware-qualified. The separate `normalize-source-comments` helper may write new converted copies outside the project after explicit review; it is not a migration apply and never edits originals. A replacement plan additionally requires one explicit `--confirm-file` per reviewed and accepted lossy file, tied to the reviewed plan ID; confirmations reflect reviewed per-file choices rather than an automatic loop over `lossyFiles`, a declined file requires a narrowed re-preview, and a missing, duplicate, unknown or non-lossy confirmation fails before any output directory is created.
- The startup route is a bounded, reviewed adaptation: it accepts only the conventional Cortex-M3/M4/M7 CMSIS grammar and never executes or copies unknown ARMCC logic. Do not advertise arbitrary ARMASM translation, do not claim ARMCC/Microlib binary or ABI equivalence, and do not treat generated vectors or runtime initialization as hardware-qualified.
- Float ABI evidence is not binary verification. Numeric `uFloatingPoint` values do not declare a calling convention; literal `soft`/`softfp`/`hard` is only project intent; the default `hard` candidate is inferred and unverified for ARMCC + Cortex-M4 + FPU2 with `ArmAdsMisc/RvdsVP` absent/empty or the historical value `2`; other selectors and unsupported compiler/CPU/FPU tuples remain blocked. Report `origin` (`inferred`/`declared`/`blocked`/`not-applicable`), `ruleId`, and `baselineVerified=false` exactly, preserve misc-control and ABI blockers, and tell the user the original compiler command lines, objects and libraries still need review. There is no ABI override flag; never claim `hard` is proven original behavior.
- The common-syntax rules are deliberately narrow and never infer missing evidence. The new function/declaration rewrites are C-only (the historical numeric `__at` placement form remains for C++), while the exact standalone no-semihosting pragma is supported for both C and C++. The MSP setter is emitted as GNU `naked` basic asm (never an ordinary C `__set_MSP` wrapper) so the original no-prologue behavior and the caller's stack pointer assignment are preserved; unknown assembly, prototypes, alignment bounds, attribute combinations, or macro evidence stay blockers. Removing the no-semihosting pragma does not add I/O stubs, does not imply runtime I/O equivalence, and `nosys.specs` is an explicit manifest field rather than a generic linker knob. Successful syntax conversion is not behavioral equivalence; compiler/ELF checks in the slice are offline evidence only.
- Scoped include-only migration is additive only: validated directories become target include search paths and no other scope semantics move. It does not promise per-file macro semantics, preprocessing equivalence for arbitrary code, or that a header found for one scope is correct for another. The plan binds the directory inventory digest, so apply replans and refuses (`MIGRATION_PLAN_INVALID`, rule `freshPlan`) when a Git-ignored header changed or a new colliding file appeared after review.
- Review `data.startup.diagnostics` and warnings before authorizing. A destination collision, unsupported core/grammar, size-bound failure or changed option set is a stop condition, not a reason to overwrite files or edit the plan.
- Do not parse `.uvprojx` XML, rewrite project source files, render templates, or run compilers yourself. The companion helper's copy-only external output is not a project rewrite.
- A historical AXF can be imported as ELF by the separate source-only external-firmware route when the bound server exposes `stm32_firmware_import`/`stm32_firmware_admit`/`stm32_flash_imported`. That route does not migrate sources, create a managed project, compare migration baselines, or prove the AXF matches the current project; do not describe it as migration progress or as a substitute for preflight/plan/apply.
- Never claim success; report the returned `OperationResult` exactly as received and finish immediately.
