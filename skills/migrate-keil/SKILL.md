# Migrate Keil Project

## Workflow

1. **Context and binding first.** Call `stm32_project_context` (no arguments). Read `capabilityDetails`, not only the legacy booleans: `status=available` means the entry point applies to this project, `blocked` means a named prerequisite is missing, and `not-evaluated` means context did not check it. `hardwareDiscovery=not-performed` means no probe was queried. Context never scans all sources or proves migration readiness. Keep `data.project.root` authoritative. If this workflow needs v1.3.2-only fields, compare `stm32_doctor` `data.runtime.toolkitVersion` and `data.publicInventory` with the actual tool list/input schemas the client exposes; a CLI/launcher version does not prove the bound server's version, and a v1.3.1 implementation may legitimately omit the new v1.3.2 diagnostics. After an upgrade restart VS Code once and verify again. Missing tools/fields or a different root means preserve the full result and stop the dependent operation.
2. **Select and inspect.** Use `data.project.files` to identify the project-root-relative `.uvprojx` (context does not list target names). For multiple project candidates, ask the user to choose one. If the exact target is unknown, call `stm32_keil_inspect(uvprojx="<selected relative path>", includeBaseline=true)` and omit `targetName`; on `KEIL_TARGET_SELECTION_REQUIRED`, present `details.targets` and let the user choose, then inspect again with that exact `targetName`. A successful result carries `data.inspection.target_name`; preserve that exact value, plus the same `uvprojx`, for every later call. Never guess a target. `baseline.available` only means a historical AXF or MAP was found and parsed; it does not prove a current build, toolchain, source identity, or authorized baseline.
3. **Preflight without Git.** Call `stm32_keil_preflight(uvprojx="<same path>", targetName="<same target>")`. Preflight is read-only and requires no Git. It returns typed `analysis.blockers` separately from `planReadiness` (technical readiness for obtaining a delivery plan) and `applyReadiness` (always false pending a reviewed, authorized plan). Git is optional traceability: `data.git` may report a missing repository, unborn HEAD, non-toplevel root or dirty worktree as truthful evidence, but those facts are never planReadiness prerequisites and never a reason to run `git init`, commit, stash, clean or ignore files. `planReadiness.requiredInputs` names the one input preflight does not evaluate: an absolute new output directory outside the source that must be absent or verified empty. A successful call means analysis completed; it does **not** mean the project is ready to apply, and it never returns an applicable plan ID. Public conversion has no diagnostic-plan fallback: any technical blocker makes the delivery PLAN fail with `DELIVERY_BLOCKED` plus complete blocker details/codes, while preflight retains every original blocker and remediation. Report every blocker and every required input. Each blocker adds `remediation` with `category` (`needs-user-input` or `unsupported`), a concise `summary`, an optional `tool` naming a real MCP tool, an optional `skill` naming a companion Skill (the two are never conflated), and `requiredInputs`; `blockerSummary.byRemediation` counts the same classifications while the original code/rule_id/path/line/column/evidence/message fields stay unchanged. When supported source rewrites are proposed, `analysis.sourceChanges` is an additive concise list of `{path, ruleIds, beforeSha256, afterSha256}` from the same patch evidence; the delivery PLAN exposes every final output in `data.outputs[]` and every reviewed source/manifest patch in `data.sourcePatches[]`. Use these only to distinguish proposed supported changes from blockers — they grant no authorization. Supported common syntax is narrow, and its new function/declaration rules apply only to C sources (the historical numeric `__at` placement form remains for C++), while the exact standalone no-semihosting pragma is supported for both C and C++: an exact `__asm void` wrapper (zero-argument WFI/CPSID I/CPSIE I, or a known 32-bit/`unsigned int`/`unsigned long` MSP setter) whose body is exactly the instruction plus `BX LR`/`BX R14`, rewritten to a GNU `naked` basic-asm function; bounded `__align(n)` (positive power of two at most 4096) on one plain object, composable with a supported fixed address only when that resolved address is a multiple of `n`; a single uninitialized scalar/array absolute placement whose bounded expression resolves from target defines and contained quoted guarded headers; and only the exact standalone `#pragma import(__use_no_semihosting)` (removed, with an explicit `build.newlibSpecs=["nosys.specs"]` in the manifest proposal). Unknown/conditional/redefined/`#undef`/function-like macros, extra instructions or prototypes, pointers, initializers, `extern`/`typedef`, zero-length arrays, mixed/unknown attributes, C++ new function/declaration forms, and unsupported ARMCC pragmas retain blockers; other generic pragmas keep their existing behavior. Read the blocker message before treating a source as unsupported: the align/placement diagnostics distinguish unsupported declaration grammar from an unresolved address expression or array bound and name the bounded project-relative quoted include (for example `quoted include "Inc/malloc.h" is not UTF-8`). A recognised `__asm void` wrapper without an explicit return (such as `{ WFI; }`) remains blocked: the ARM Compiler armcc User Guide section 7.30 permits fall-through into the next embedded assembly function, so obtain a Keil disassembly/control-flow baseline; never invent `BX LR` or map it to a CMSIS intrinsic. Wrappers with an explicit `BX LR`/`BX R14` keep the supported rewrite. These diagnostics are local unreleased source behavior; the installed 1.3.2 binary does not include them. Only inputs the current preflight actually accepts may be recommended: `memoryLayout` and `extraRegions` here, and the separate `startupStrategy`/`startupSource` opt-in below. There is no framework, FPU, or ABI override parameter, no blocker is auto-fixable, and unknown codes remain unsupported. Read `analysis.floatAbi` on every preflight (PLAN returns the same object as `data.floatAbi`; the conversion report uses `floatAbi`): numeric `uFloatingPoint` values are not ABI evidence, literal `soft`/`softfp`/`hard` is a project declaration only, and default hard linkage is inferred only for ARMCC + Cortex-M4 + FPU2 when the selected target's `ArmAdsMisc/RvdsVP` is absent/empty or the historical value `2`. Any other nonempty selector, compiler/CPU/FPU tuple, or unknown numeric value stays blocked, even when a literal ABI is declared. `baselineVerified` is always false: inspect the actual compiler command lines, objects and libraries, and never edit evidence, selectors, or digests to clear a blocker. Blocked float-ABI or hardware-selection evidence stops both delivery planning and progression toward APPLY: resolve it before requesting the PLAN. When a group or file scope carries only `IncludePath` and the analysis produced merge evidence, preflight also returns additive `analysis.includeMerges`: one entry per scope/owner and normalized directory with `decision` `added` or `already-present` (added entries also carry `inventorySha256`/`inventoryFiles`; the PLAN `include_merges` entries use the same fields in snake_case, `inventory_sha256`/`inventory_files`). Only scopes whose compiled sources are included C/C++ contribute; listed headers and precompiled libraries do not execute a compiler and are ignored for this decision (so a C/C++ group that also lists headers still merges), an excluded file scope, a header/library-only group or file, or a group with no included source is ignored, while a scope that also has defines, misc controls, included assembly, or an unknown compiled language stays a single `ARMCC_OPTION_UNSUPPORTED` blocker without a partial merge. Any `MIGRATION_INCLUDE_*` blocker (missing, not-directory, escaping, unreadable, unsupported redirect, aggregate traversal/hash limit, or one case-insensitive include-relative key resolving to different files in two search roots) rejects the whole include analysis, so no partial merge is reported and the proposal keeps the original target include list. Overlapping search roots are allowed when they expose the same physical files (for example a target `USER` directory plus a scoped `USER/IWDG` directory); only a key that resolves to distinct files is ambiguous.
4. **Optional CMSIS startup review.** A conventional ST/CMSIS Cortex-M ARMCC startup is supported only through the explicit opt-in `startupStrategy="generate-cmsis-gcc"` (CLI `--startup-strategy generate-cmsis-gcc`). Add `startupSource="<exact project-relative included ARMCC .s path>"` (CLI `--startup-source`) whenever more than one included non-empty assembly source exists; omitting it then returns `MIGRATION_STARTUP_SELECTION_REQUIRED` with `details.candidates`. Omit both options to retain the existing `ARMCC_ASSEMBLY_UNSUPPORTED` blockers. The same two values must be passed to preflight, convert and apply; they are bound into the plan digest and apply replans with them, so a caller-edited or omitted choice is never accepted (a valid but different choice returns `PLAN_CHANGED`; a malformed option value returns a structured validation error). Preflight's `planReadiness.nextSteps` repeats the exact startup choice to retain. The managed destination is `Startup/stm32tk_startup_gcc.S`; the original ARMCC startup is never modified or deleted. Review `analysis.startup` (source path/hash, ordered vector entries and reserved slots, stack/heap bytes, reset pattern, generated path/digest, warnings, diagnostics). Supported sources are normalized cortex-m3, cortex-m4 and cortex-m7 conventional files; unknown instructions, custom reset/handler code, multiple vector tables, vector expressions, unsupported cores/layouts and undeclared handlers remain blockers. The generated GCC runtime is not ARMCC, ABI or Microlib behavioral equivalence, and a `MIGRATION_STARTUP_TARGET_COLLISION` is never overwritten.
5. **Explicit multi-RAM placement.** Read `analysis.memoryLayout` on every preflight. `status=implicit` means exactly one non-writable Flash and one readable/writable RAM were resolved; no option is needed and the historical manifest bytes/model hash are preserved. `status=requires-selection` appears with an ordinary `MEMORY_LAYOUT_REQUIRED` blocker (other blockers are still returned): show `candidates.flash` and `candidates.ram` with their actual names, origins, lengths and attributes, and ask the user to choose. The explicit value is a JSON object with exactly `flash`, `data`, `bss`, `heap`, `stack` naming existing regions (MCP `memoryLayout`, CLI `--memory-layout`). Pass a real object to MCP, not a JSON string: the registered `memoryLayout` schema is `dict[str, str]`, so the MCP framework rejects non-object values and objects whose role values are not strings with a `ToolError` before Toolkit runs (for example `string_type` validation at `memoryLayout.flash`); those are not Toolkit `MEMORY_LAYOUT_INVALID` results. Only schema-valid objects reach Toolkit: unknown/incomplete roles and empty string values fail before inspection with structured `MEMORY_LAYOUT_INVALID` field/rule/remediation, while logical region/access validation (whether each named region actually exists and has the required permissions) runs after reading the actual declared regions and returns the same structured error at that point. The CLI `--memory-layout` takes a JSON object string: malformed or duplicate-key JSON and missing/unknown/non-string/empty role values use the same Toolkit `MEMORY_LAYOUT_INVALID`, while a repeated `--memory-layout` option is the existing sanitized parser error. Use only names actually returned in `data.analysis.memoryLayout.candidates`, for example `memoryLayout={"flash": "<candidate flash region name>", "data": "<candidate RAM region name>", "bss": "<candidate RAM region name>", "heap": "<candidate RAM region name>", "stack": "<candidate RAM region name>"}`; the quoted placeholders are not real choices. Flash must be readable, executable and non-writable; the other four must be readable and writable. Never choose a writable executable RAM as Flash, never infer CCM/DMA accessibility, and never invent an external region. An all-main-RAM mapping is valid and leaves other RAM intentionally unused. The same exact mapping must be passed to preflight, plan and apply; omission versus an explicit mapping is a different reviewed request. The delivery PLAN echoes the reviewed choice as `data.options.memoryLayout` and binds it into `data.planId`; preflight exposes the same decision evidence as `data.analysis.memoryLayout`, and the plan preview does not repeat that resolution object. A native linker-script project cannot also declare `memoryLayout`.
   External RAM is a separate explicit input accepted by the same three calls: MCP `extraRegions` (a real array of objects, registered as `list[dict[str, Any]]`) and CLI `--extra-regions '<json array>'`. Each entry has exactly `name`, `origin`, `length` and `attributes`; only `rw-`/`rwx` writable RAM is allowed, names are 1-64 character ASCII linker identifiers, origin/length are exact JSON integers describing a non-empty half-open range, at most 32 entries are accepted, and entries may not overlap the declared base or each other. Never guess a capacity or infer one from a device/address/board; ask the owner for the exact origin and byte length. Extra RAM adds RAM candidates only, never Flash. Managed `.data`/`.bss`/`.heap`/`.stack` are not placed there implicitly: if the only writable region is the extra RAM, preflight still returns `MEMORY_LAYOUT_REQUIRED`, and an explicit `memoryLayout` must name it. Preflight exposes the request as `data.analysis.extraRegions`, PLAN as `data.options.extraRegions` bound into `data.planId`, and the conversion report records `extraRegions`; the proposed manifest keeps the inspected Keil `memory.regions` unchanged and adds `memory.extraRegions`. Omission and an empty array are the same no-extra request; omitting, shortening or changing any entry on PLAN/APPLY returns a structured validation error (including `EXTRA_REGIONS_INVALID`, or `MEMORY_LAYOUT_INVALID` when a retained explicit layout still names the omitted region) or `PLAN_CHANGED` without writing. The frozen/installed 1.3.0 runtime also lacks this source-only patch, so verify the bound server's actual tool inventory and input schema rather than trusting a version number. The CLI JSON path rejects duplicate keys, deep nesting, oversize input and repeated options before inspection; the MCP framework rejects non-array/non-object values before Toolkit runs, while schema-valid but semantically invalid values return `EXTRA_REGIONS_INVALID` field/rule/remediation. Fixed sections remain `NOLOAD` and are not promised initialized; the owner must initialize external memory before access, and an external stack can require earlier bootstrap than `SystemInit`. A native linker script remains user-owned and is not rewritten.
6. **Resolve blockers, not rules.** Report encoding, assembly, scoped compiler option, scatter/memory, and manifest conflicts with their portable paths and safe next steps, using the returned `remediation` category: `needs-user-input` means a real supported selection or reviewed preparation exists; `unsupported` means no automatic fix exists and the evidence must be handled as a project-owned change. Toolkit never silently transcodes non-UTF-8 input, blindly replaces ARMCC startup code, edits a conflicting manifest, deletes untracked files, or weakens a rule to make preflight pass. The startup opt-in above does not translate arbitrary assembly: unrelated `.s` files remain `ARMCC_ASSEMBLY_UNSUPPORTED`. For a source-encoding blocker, the supported preparation route is the separate `normalize-source-comments` companion skill: it previews explicitly declared per-file charsets and copies only reviewed comment-only UTF-8 files to a new external directory. It never edits the original project, guesses a charset, or resolves startup, scoped-option, scatter/memory, Git/apply, or baseline blockers. The same route applies when an align/placement blocker names a quoted include that is not UTF-8: preview that header's declared charset and, only for a reviewed comment-only change, prepare a strict copy outside the project, then rerun inspect and preflight. A missing, unreadable, redirected, or ambiguous dependency is not an encoding problem: collect read-only path and scoped-include evidence first; a reviewed include-path correction is project-owned, but never transcode or blindly widen search paths to silence the blocker. When the strict preview reports undecodable bytes, or private-use/C1-control/U+FFFD/noncharacter code points, an explicit user request to replace those units with a literal `?`, together with the declared charset, authorizes a read-only replacement preview (`preview --replace-invalid-with '?'`). A strict `DECODE_ERROR` has not yet classified the bytes as comment content; the preview does, and it can block the file. It replaces only lexically proven comment content, records each original byte range and reason, and still blocks non-comment spans, incomplete constructs, DBCS/backslash ambiguities and replacement-created trigraphs. Each accepted lossy file then requires its own explicit `copy --confirm-file '<relative path>'` reflecting the reviewed per-file choice; never loop over `lossyFiles` to manufacture confirmations, and if a lossy file is declined, re-preview the narrowed selection instead of editing the plan or copying unapproved files. Confirmation is per-file review evidence, never bulk approval and never permission to edit originals.
7. **Git is optional traceability.** Migration planning and apply never require a Git repository, a committed HEAD, a clean worktree, or the project root to be a Git toplevel. A missing repository, unborn HEAD, nested root, or dirty/untracked files is optional evidence only. Never run `git init`, commit, stash, clean, or rewrite Git state on the user's behalf, and never present Git as a migration prerequisite.
8. **Choose a new destination.** The Keil source is read-only. Ask the owner for one absolute path outside it that is absent or verified empty; never invent a path, reuse the source, or fall back to an in-place conversion. This destination is a required input for both the read-only PLAN and the authorized apply; omitting it returns `DELIVERY_DESTINATION_REQUIRED` with a concrete example and the rationale that the source is read-only and the deliverable is an independent GCC project. Preflight reports its state as `not-evaluated`.
9. **Read-only delivery plan.** When `planReadiness.ready=true` and no technical blockers remain, call `stm32_keil_convert(destination="<absolute new output>", uvprojx="<same path>", targetName="<same target>", startupStrategy="<same value or omitted>", startupSource="<same value or omitted>", memoryLayout=<same reviewed object, or omit the argument>, extraRegions=<same reviewed array, or omit the argument>)` with no `planId` and no `authorized`. This is the deterministic `keil-conversion-plan` response. Review `data.planId` (not `data.plan_id`), `data.sourceSnapshotSha256`, `data.destination`/`data.destinationState`, `data.options`, `data.outputs[]` (`kind`, `path`, `beforeSha256`, `sha256`, `unifiedDiff`, `collision`) and `data.sourcePatches[]`. The preview states `configured=false`, `built=false` and `flashed=false`: it is neither build nor flash evidence. For the startup route, confirm `data.options.startupOptions` retains the reviewed strategy/source, that `Startup/stm32tk_startup_gcc.S` appears as a generated output, and that the manifest patch records the expected stack/heap and `generation.runtimeInitialization="cmsis-gcc-v1"`. For include-only scopes, compare `data.includeMerges` when returned with the actual group/file scopes. For supported common-syntax rules, use the exact `ruleIds` in preflight's `analysis.sourceChanges` and each output/source patch's unified diff; never edit the plan, output, patch, planId or managed hashes, and never delete a scope, define or misc control merely to force migration. A fixed address outside every declared memory region is `MIGRATION_FIXED_SECTION_OUTSIDE_MEMORY` with `needs-user-input` remediation and `requiredInputs=["extraRegions"]`; ask the owner for the exact origin/byte length and never guess external SRAM.
10. **Stop on blockers.** Technical blockers make this PLAN fail with `DELIVERY_BLOCKED` and complete `details.blockerCodes`/`details.blockers`; report them and stop. Never apply a blocked plan and never claim a diagnostic delivery plan.
11. **Authorize.** An explicit user instruction that covers this intended mutation and scope (for example "plan and apply only these changes; after reviewing the exact plan, proceed without asking again") remains reusable after you review the actual plan, provided every reviewed change stays inside that instruction. The user does not need to have quoted the not-yet-existing `data.planId`; the APPLY request carries the concrete reviewed `data.planId`. Re-review a changed plan, destination, input, option or scope; ask only when the newly reviewed change exceeds or conflicts with the existing authorization, not merely because a fresh plan ID exists within the already authorized task. Never infer mutation authority from inspection, preflight or a read-only PLAN-only request. Keep the exact `planId`/destination/parameter replay and `authorized=true` guards.
12. **Apply.** Only when the user's authorization covers the reviewed mutation (an existing instruction reused within its scope, or newly given), call `stm32_keil_convert(destination="<same absolute new output>", uvprojx="<same path>", targetName="<same target>", startupStrategy="<same value or omitted>", startupSource="<same value or omitted>", memoryLayout=<same reviewed object, or omit the argument>, extraRegions=<same reviewed array, or omit the argument>, planId="<exact data.planId>", authorized=true)`. The PLAN response field is `data.planId`; the APPLY request argument is `planId`. The core replans the delivery, verifies the source snapshot, destination state, options and exact planId, stages only in an owned sibling, and publishes one complete output directory. A changed destination/option/source snapshot returns `PLAN_CHANGED` or `DELIVERY_*` and writes nothing; a nonempty destination is never overwritten.
13. **Return the result and hand off the root.** Report the `keil-conversion-apply` result: the exact `data.outputRoot`, `data.contentId`, `data.reportPath`, the delivered `.stm32-project.json`, changed/generated output paths, and warnings. Confirm `configured=true`, `built=false` and `flashed=false`; apply generated configuration but did not build or flash. If the result is a failure (`AUTHORIZATION_REQUIRED`, `PLAN_CHANGED`, `DELIVERY_*`), report the exact code and details and stop. Then give the exact next actions: bind `data.outputRoot` as the VS Code workspace and as the MCP server's project root, rerun `stm32_project_context` there, run the confirmed configure PLAN/APPLY for an explicit debug backend/target and verified Toolkit/GCC executable paths when missing, then use the normal authorized GCC build and managed flash route. Git is optional for the delivered project; never mutate the server's project-root binding behind the user's back, fabricate paths, or select a probe automatically.

## Post-migration configure: owner NOLOAD linker fragment

After the conversion is applied, a user-owned writable-RAM `NOLOAD` section fragment may be wired into the managed linker through the ordinary configure workflow. This is current v1.3.2 behavior and is also present in the published v1.3.1 package: the published v1.2.0 runtime (48 tools) and the frozen/installed 1.3.0 do not contain this source-only patch. Tool inventory and input schema are unchanged by this patch, so they **cannot** distinguish an unpatched older 1.3.0 from a patched runtime; do not use tool counts, versions or schema presence as proof. Require a runtime verified as built from this patch (installation/upgrade needs separate authorization), then confirm support with a read-only configure PLAN against a reviewed manifest: `data.inputs[]` must include the fragment `path`/`sha256`, the `linker/stm32tk.ld` `unified_diff` must contain the fragment sections, and `data.blockers` must be as expected. If the PLAN lacks that evidence or fails, stop; do not apply. **No new MCP tool or migration parameter exists**: edit the reviewed `.stm32-project.json` by adding only `"linkerFragment": "linker/user.ld"` to the existing `generation` object (keep `cubeMxIoc`, `nativeLinkerScript`, `managedManifest`, `generatedDirectories`, `userDirectories` and any `runtimeInitialization` unchanged) and create that user-owned file, then use the existing `stm32_project_configure` or CLI `project configure`.

1. `stm32_project_configure()` with no `planId` and `authorized=false` is the read-only PLAN. Review `data.plan_id`, `data.model_sha256`, `data.inputs[]` (the fragment `path`/`sha256` must be present), `data.files[]` (especially the `linker/stm32tk.ld` `status`/`unified_diff`), `data.blockers[]`, and `data.managed_manifest_path`. CLI equivalent: `project configure --project <abs> --dry-run --json` (global `--project-root <abs>` before the subcommand is also valid; use the same project root for PLAN and APPLY). Fragment-layer failures return `ok=false`, `code=LINKER_FRAGMENT_INVALID`, with `details.path`/`field`/`rule`/`remediation` (and `line`/`column` when applicable). Earlier failures keep their existing contracts: a null/empty/non-string value is `PROJECT_SCHEMA_INVALID`, and manifest path containment (`rule=pathWithinProjectRoot`) can also fail before fragment semantics. Read the actual `code`/`details`; do not assume one precedence. Fix the fragment, not the managed files or digests.
2. Apply step 10's authorization rule to this exact reviewed fragment plan, then call `stm32_project_configure(planId="<data.plan_id>", authorized=true)` (CLI `project configure --project <abs> --apply --plan-id <data.plan_id> --authorized --json`). APPLY reports the existing camelCase `planId`, `modelSha256`, `createdPaths`, `updatedPaths`, `unchangedPaths`, `preservedPaths`, `warnings`, `managedManifestPath`, `managedManifestSha256`, `templateVersion`; it revalidates the fragment bytes and writes nothing on a changed/deleted path.
3. The fragment is not `extraRegions`, `memoryLayout`, `fixedSections` or `nativeLinkerScript`. It may only contribute custom writable-RAM `NOLOAD` output sections whose selectors stay in their own family and whose region names already exist in the canonical map (multiple RAMs still require the explicit layout). Managed/standard families are reserved by broad name prefixes: any selector under `.text*`, `.rodata*`, `.data*` or `.bss*` (including names such as `.data_ext` or `.bss_ccm`) is rejected, as are small-data, TLS, dynamic metadata, constructors/unwind, heap/stack and `.stm32tk.abs.*`. Valid custom names such as `.sram2` or `.ccm` are accepted only with selectors in their own output-section family; do not relax the parser to admit a reserved prefix. Sections render after fixed sections and before `.data`; they are never copied or zeroed, so initialized objects must not rely on initializers there and external RAM must be initialized before access. A fragment cannot coexist with a native linker script.
4. Fragment edits (including comments), deletion, path changes and option removal invalidate the configuration and build evidence. Build refuses before spawning the compiler. A deleted/unreadable fragment normally fails model loading first: `BUILD_PROJECT_INVALID` with `details.rule=missing` (or the actual model-layer rule) and the fragment remediation, not one of the provenance-only rules. Option removal, missing managed provenance, changed path/digest and changed model hash report `BUILD_PROJECT_INVALID` with `details.rule` `linkerFragmentRemoved`, `linkerFragmentMissing`, `linkerFragmentChanged` or `modelChanged`. Read the actual code/rule and remediation, then rerun configure PLAN/APPLY and rebuild (use `clean` when required). Never edit `linker/stm32tk.ld`, `.stm32-toolkit/generated-files.json` or build receipts to compensate. The generated CMake only gains `LINK_DEPENDS` on the merged linker for this route; direct CMake/Ninja use does not re-parse fragment changes, so reconfigure through Toolkit first. Omission preserves the historical model hash and generated bytes.

## Post-migration configure: explicit PyOCD debug pair

An ordinary conversion writes `"debug": {}` and remains a valid build-only project. Preflight reports this planned post-migration state additively as `data.debugConfiguration` using the shared shape: `backend`/`target` null, `status=needs-user-input`, `missingFields`, `diagnostics` (`code`/`field`/`rule`/`message`/`remediation`), `targetSupport=not-checked`, `hardwareVerified=false`, `nextSteps`, plus `phase=post-migration` and `blocking=false`. It is **not** a technical blocker, does not change `analysis.blockers` or `planReadiness`, adds no Git dependency and invents no plan ID; ordinary conversion PLAN/APPLY still require the reviewed plan ID, the same explicit destination/options and explicit authorization, and they do not require Git. Never treat this guidance as a migration failure or add it to the blockers list.

After the conversion is applied, record a debug pair with the existing configure workflow — no new MCP tool and no migration parameter:

1. PLAN with the same project and pair: MCP `stm32_project_configure(debugBackend="pyocd", debugTarget="<pyocd-target>")`, CLI `stm32-toolkit project configure --project <abs> --debug-backend pyocd --debug-target <pyocd-target> --dry-run --json`. Read `data.plan_id`, `data.debug_configuration`, `data.manifest_edit` (`path`, `status`, `before_sha256`/`after_sha256`, `before_size`/`after_size`, full `unified_diff`), `data.inputs[]`, `data.files[]` and `data.blockers[]`. Confirm only `debug.backend`/`debug.target` change and `svd`, `svdDevice`, `readableRegions`, `memory`, `generation` and other fields are preserved. Both values are required; raw values are never trimmed, case-folded, coerced or auto-mapped from the Keil device, and an invalid/partial pair returns `DEBUG_CONFIGURATION_INVALID` with complete diagnostics before any write.
2. Apply step 10's authorization rule to this exact reviewed plan, then APPLY with the same project and pair plus `planId=<exact data.plan_id>` and `authorized=true`: MCP `stm32_project_configure(debugBackend="pyocd", debugTarget="<same>", planId="<exact data.plan_id>", authorized=true)`, CLI `stm32-toolkit project configure --project <same abs> --debug-backend pyocd --debug-target <same> --apply --json --plan-id <data.plan_id> --authorized`. Omitted/changed pairs and input drift are refused with `PLAN_CHANGED`/a structured failure without writing.
3. A configured pair is metadata only. It does not discover/install/verify a PyOCD target, prove the physical device, create a debug session or fill `.vscode/launch.json`; a real handoff is separate and explicitly authorized. Existing build/firmware identity becomes stale after the manifest edit — rebuild with `clean` when needed and never hand-repair hashes or receipts.

This configure pair is current v1.3.2 behavior and is also present in the published v1.3.1 package; it is absent from the frozen/installed 1.3.0, and installation or upgrade requires separate authorization.

## Rules

- `stm32_keil_inspect`, `stm32_keil_preflight`, and the plan call are read-only; verify the plan before any mutation.
- `stm32_keil_preflight` already exists in the frozen v1.3.0 package, with `analysis.blockers`, the blocker summary, `planReadiness`/`applyReadiness`, and the `startupStrategy`/`startupSource`/`memoryLayout` options. The published v1.3.1 additions are per-blocker `remediation`/`blockerSummary.byRemediation`, `extraRegions` (`analysis.extraRegions`), and the other additive fields named above; v1.3.2 adds the separated pyOCD evidence and VS Code guidance fields described in the configure Skill, which a v1.3.1 implementation may legitimately omit. The published v1.2.0 runtime (48 tools) does not expose `stm32_keil_preflight` or any of these options at all. Confirm the bound server's actual tool inventory and input schema before promising a specific field or option, and never present an unreleased option as available on an installed runtime that lacks it; conversely, do not describe the whole preflight tool or its basic blocker payload as absent from 1.3.0, and do not infer server staleness from a version string or inventory count. Compare `stm32_doctor` `data.runtime.toolkitVersion`/`data.publicInventory` with the actual client tools; a launcher version alone is not binding proof. After an upgrade restart VS Code once and re-verify.
- The destination-based independent delivery contract in this Skill is **current local unpublished source behavior**, not part of the published v1.3.2 package. An installed v1.3.2/v1.3.1 runtime still exposes the historical in-place `keil convert` without `--destination`; verify the bound server's actual input schema before promising `destination`, `data.planId`, `data.outputs[]`, `data.sourcePatches[]` or `outputRoot`. Never present unpublished behavior as available on an installed runtime, and never install or upgrade without separate authorization.
- Capability or entry-point availability does not establish migration readiness. Only the current preflight/plan evidence does.
- Within this migration workflow, the apply call is the only mutation, and it writes only into the explicit new destination. The Keil source tree is never edited. Pass exactly the reviewed `data.planId` as the APPLY request's `planId`, with the exact same destination, project/target selection and the exact same `startupStrategy`/`startupSource` values (or both omitted). The exact same `memoryLayout` object and `extraRegions` array are retained on plan and apply; omission and an explicit all-main-RAM mapping are different reviewed choices, and a changed or omitted request returns `PLAN_CHANGED` or a structured validation error (for example `MEMORY_LAYOUT_INVALID` when the retained explicit layout names a region that the omitted extra request no longer declares); do not promise a single precedence. External RAM remains owner-supplied: never infer a capacity, never treat it as Flash, and never claim it is initialized or hardware-qualified. The separate `normalize-source-comments` helper may write new converted copies outside the project after explicit review; it is not a migration apply and never edits originals. A replacement plan additionally requires one explicit `--confirm-file` per reviewed and accepted lossy file, tied to the reviewed plan ID; confirmations reflect reviewed per-file choices rather than an automatic loop over `lossyFiles`, a declined file requires a narrowed re-preview, and a missing, duplicate, unknown or non-lossy confirmation fails before any output directory is created.
- The startup route is a bounded, reviewed adaptation: it accepts only the conventional Cortex-M3/M4/M7 CMSIS grammar and never executes or copies unknown ARMCC logic. Do not advertise arbitrary ARMASM translation, do not claim ARMCC/Microlib binary or ABI equivalence, and do not treat generated vectors or runtime initialization as hardware-qualified.
- Float ABI evidence is not binary verification. Numeric `uFloatingPoint` values do not declare a calling convention; literal `soft`/`softfp`/`hard` is only project intent; the default `hard` candidate is inferred and unverified for ARMCC + Cortex-M4 + FPU2 with `ArmAdsMisc/RvdsVP` absent/empty or the historical value `2`; other selectors and unsupported compiler/CPU/FPU tuples remain blocked. Report `origin` (`inferred`/`declared`/`blocked`/`not-applicable`), `ruleId`, and `baselineVerified=false` exactly, preserve misc-control and ABI blockers, and tell the user the original compiler command lines, objects and libraries still need review. There is no ABI override flag; never claim `hard` is proven original behavior.
- The common-syntax rules are deliberately narrow and never infer missing evidence. The new function/declaration rewrites are C-only (the historical numeric `__at` placement form remains for C++), while the exact standalone no-semihosting pragma is supported for both C and C++. The MSP setter is emitted as GNU `naked` basic asm (never an ordinary C `__set_MSP` wrapper) so the original no-prologue behavior and the caller's stack pointer assignment are preserved; unknown assembly, prototypes, alignment bounds, attribute combinations, or macro evidence stay blockers. A missing explicit return is never repaired automatically: the blocker explains the possible fall-through (ARM Compiler armcc User Guide section 7.30, https://documentation-service.arm.com/static/5eb946b50f1c1e0dae6ee21e) and asks for a Keil disassembly/control-flow baseline. A blocker caused by an unusable quoted header carries its own remediation (encoding preparation or path evidence); follow that rather than editing the rule. Removing the no-semihosting pragma does not add I/O stubs, does not imply runtime I/O equivalence, and `nosys.specs` is an explicit manifest field rather than a generic linker knob. Successful syntax conversion is not behavioral equivalence; compiler/ELF checks in the slice are offline evidence only.
- Scoped include-only migration is additive only: validated directories become target include search paths and no other scope semantics move. It does not promise per-file macro semantics, preprocessing equivalence for arbitrary code, or that a header found for one scope is correct for another. The plan binds the complete source inventory digest, so apply replans and refuses (`DELIVERY_SOURCE_CHANGED`/`PLAN_CHANGED`) when any inspected input changed or a new colliding file appeared after review.
- Review `analysis.startup.diagnostics` and warnings before authorizing. A destination collision, nonempty destination, unsupported core/grammar, size-bound failure or changed option set is a stop condition, not a reason to overwrite files or edit the plan. Public delivery publishes one complete directory or nothing; a retained staging directory means apply failed and must be reported, never adopted.
- Do not parse `.uvprojx` XML, rewrite project source files, render templates, or run compilers yourself. The companion helper's copy-only external output is not a project rewrite.
- A historical AXF can be imported as ELF by the separate source-only external-firmware route when the bound server exposes `stm32_firmware_import`/`stm32_firmware_admit`/`stm32_flash_imported`. That route does not migrate sources, create a managed project, compare migration baselines, or prove the AXF matches the current project; do not describe it as migration progress or as a substitute for preflight/plan/apply.
- Never claim success; report the returned `OperationResult` exactly as received and finish immediately.
