# Build Firmware

## Workflow

1. **Context first.** Call `stm32_project_context` (no arguments). Read `capabilityDetails.build`: `available` means build evidence is complete; `blocked` means the stated prerequisite is missing; `not-evaluated` means context did not check it. If the status is `blocked`, report the evidence and next step and stop. Never stop solely because a legacy hardware boolean is `false`: those booleans are conservative compatibility fields, hardware state is unprobed, and `capabilityDetails` may identify a known blocker (for example unsupported snapshot firmware provenance). Neither a false boolean nor unprobed hardware state prevents an otherwise valid build.
2. **Doctor and binding.** Call `stm32_doctor` (no arguments). `ok=true` only means the report was collected, not that the environment is ready: a missing, unknown, unavailable or incomplete observation is evidence, not a collection failure. Show the evidence for every probed tool, and distinguish `ok` (the version-probe command completed successfully; `version` may still be null, so inspect it separately and never infer a version from `status` alone), `unknown` (located but no readable static/version evidence), `missing`, and `timeout`/`error`/`nonzero`. For this build route, require observed ARM GCC, CMake and Ninja evidence from `data.tools`; ARM GDB pertains to debugging, and missing or unknown optional CubeMX, VS Code `code`, PyOCD or extension evidence does not by itself gate a build. Do not turn doctor into a separate readiness gate or stop a build solely because an unrelated optional tool is absent. CubeMX/VS Code versions come from static metadata; `unknown` is not a verified version. Current doctor enumerates extensions by default; `installed=null` with `status`/`code` means skipped, unavailable or incomplete observation, never `installed=false`, and `--skip-vscode-extensions`/MCP `probeVscodeExtensions=false` is an explicit opt-out. `probeCore.registry` describes the Probe lease directory; `missing` does not mean PyOCD has no targets and does not change its `safe` result. Read `data.runtime.toolkitVersion` and `data.publicInventory` together with the actual tool list/input schemas the client exposes; a CLI or launcher version does not prove the bound server's version, and an inventory count is not registration proof. After an upgrade restart VS Code once and verify again. If expected tools or fields are missing, preserve the full result and stop the dependent operation.
3. **State the invocation.** State the chosen values: preset (`arm-debug` unless the user specified `arm-release`), `clean` (`false` unless the user requested a clean build), `timeoutSeconds` (300 unless the user specified another value), and the toolchain evidence for this build invocation. State them explicitly; do not require the user to recite them.
4. **Authorize.** An explicit request to build now authorizes those ordinary documented defaults, or the preset/clean/timeout constraints the user actually supplied. State the chosen values but do not ask for repeated confirmation merely because the user did not recite a timeout or the other defaults. Honor every provided constraint; clarify first only when the requested build would exceed the existing authorization. Requests for status, diagnostics, a dry run, or read-only inspection are not build authorization. A broader explicit scoped authorization follows the same review-and-scope reuse rule. `stm32_build` is not a dry run; it never runs without `authorized=true`.
5. **Build.** Once authorization covers the chosen invocation, call `stm32_build` with the preset, clean value, and timeout stated in step 3 plus `authorized=true`. Do not substitute a default for an approved clean build, and do not add automatic retries, clean/rebuild steps or route switches.
6. **Report evidence.** From the returned `build` result, report: the build ID, identity `schemaVersion`, provenance (`sourceBaseline`), Git HEAD and dirty state, ELF and MAP SHA-256 hashes, memory usage per region, `identity.memorySummary` (basis, region rows, and warnings), warnings, and the portable artifact paths (`buildLogPath`, `buildResultPath`, `identityPath`). A schema-1 identity has a 40-character `gitHead` and boolean `gitDirty`. A schema-2 identity means Git was unavailable: `sourceBaseline` is `input-snapshot-v1`, `gitHead` and `gitDirty` are JSON `null`, and `gitEvidence` is bounded to `{status:"unavailable", code:"BUILD_GIT_INVALID", rule:"head"}` (the `rule` value is either `head` or `status`). Never report null as clean and never invent a commit. If the result is a failure (`AUTHORIZATION_REQUIRED`, `BUILD_*`, `RAM_OVERFLOW`, `FLASH_OVERFLOW`, ...), report the exact code and details and stop.
7. **Stale outputs.** Retain the complete `BUILD_OUTPUT_STALE` response before any other operation: the next build overwrites the current log and result. This is a failure response, so its artifact paths are `details.logPath`, `details.resultPath`, and `details.identityPath`; the successful `data.buildLogPath`/`data.buildResultPath` keys do not exist here. Read `details.reason` (`output-unavailable`, `prior-evidence-unavailable`, `prior-build-not-successful`, `input-snapshot-mismatch`, or `prior-evidence-mismatch`), and the fixed `evidenceField`/`evidenceSource` when present. Never echo or infer an old recorded value from a digest mismatch. If `remediation.action=clean-rebuild` and the user has not already authorized that exact clean build, ask for authorization using the proposed preset, `clean=true`, and timeout. Only then call `stm32_build` on the same bound server/project with the same preset and timeout plus `authorized=true`; the proposed MCP parameters omit `authorized` because advice is not authorization. `remediation.cli.arguments` is only the command tail, not a standalone invocation: prefix the caller-verified executable, then the required `remediation.cli.projectRoot` option (`--project-root`) with the same binding's verified **absolute** project root, in `remediation.cli.workingDirectory=project-root`; an explicit absolute root is required even when the current directory is the project root, and the bare tokens are rejected. The executable label is symbolic, not a real path, and the advice embeds no absolute root or shell command. If `clean` was already requested or an output is unavailable (`inspect-build-log`), do not repeat a clean build: inspect the build log and configuration first. Never edit receipts, identity documents, managed hashes, or the ELF/MAP to simulate freshness. If `BUILD_PROJECT_INVALID` reports managed-file drift or an invalid managed configuration, use the supported configure/fragment repair path; clean builds and hash edits are not repairs. A failed or stale managed build does not authorize flash, debug, Monitor, Target tests, or an automatic switch to the imported firmware route. These diagnostic fields are current v1.3.2 source behavior and are also present in the published v1.3.1 package; the earlier frozen/installed 1.3.0 does not contain them until an authorized install.

## Rules

- Never run CMake, Ninja, or a compiler directly; the Toolkit build is the only build path.
- Never fabricate success: a failed build returns no fresh identity, and the previous ELF is stale.
- `--clean`/`clean=true` maps only to CMake `--clean-first` in the build stage: CMake invokes its `clean` target before rebuilding, so generated build outputs may be removed. It is not a recursive deletion of the entire build directory, cache, receipts, or identity, and it does not guarantee fresh outputs or fix the underlying cause. Do not describe it as a guaranteed repair or loop it after an inspect-build-log result.
- Git is optional provenance for a build, never an eligibility gate. Missing Git, an unborn HEAD, or a dirty/untracked worktree is identity evidence, not a build failure; never run `git init`, commit, stash, clean, or otherwise change Git state to make a build pass, and never present Git as a build prerequisite. A project delivered by `keil convert` is built from its new `outputRoot`; no Git repository is required there.
- A schema-2 snapshot identity is build-only evidence on this unpublished source branch. Do not claim flash, debug, Target tests, Monitor or acceptance readiness for it: managed firmware admission here still returns `FIRMWARE_PROVENANCE_UNSUPPORTED` before any probe effect, and wrappers may map it (acceptance recovery maps it to `ACCEPTANCE_ATTEMPT_OUTPUT_INVALID`). The separate managed-snapshot admission slice has been verified on its own branch but is not integrated here; do not duplicate or assume it. Never fabricate a Git commit or treat null as clean.
- Distinguish unavailable, blocked, and not-evaluated evidence. A missing managed manifest or drifted managed file is blocked. Hardware state is normally unprobed; detailed capabilities can identify a known blocker such as unsupported snapshot firmware provenance. Neither unprobed hardware nor a false legacy hardware boolean prevents an otherwise valid build. Probe discovery (`stm32_probe_list`) remains independent of firmware provenance.
- A manifest with an explicit `memory.layout` places `.data`/`.bss`/`.heap`/`.stack` in their reviewed regions and keeps the `.data` load address in the selected Flash. A managed manifest with multiple Flash/RAM candidates and no layout is refused by configure with `MEMORY_LAYOUT_REQUIRED`; do not hand-edit the generated linker or choose regions in the build step. A native linker-script project keeps its own placement. Region overflow, overlap and too-small regions are linker failures. A successful link is offline placement evidence, not proof of CCM/external-memory or board runtime behavior.
- **`MEMORY_LOW_MARGIN` is nonblocking static evidence.** A successful current build always includes `identity.memorySummary` (`basis="elf-map-static-v1"`, deterministic `regions`, `warnings`) for both identity schemas. Each declared region, including an unused small `extraRegions` entry, warns when `free < 1024` **or** `free * 20 < length`. Each criterion is strict on its own: equality disables only that criterion, so a 128 KiB region with `free == 1024` still warns on the 5% ratio. `belowBytes`/`belowPercent` record which criteria matched. Report `region`, `freeBytes`, `lengthBytes` and those flags from the same summary as the readable `warnings`. `free` is interval-union static free space, not the largest contiguous free block, runtime stack/heap peak, or initialization proof. Do not edit the identity, warnings, ELF or MAP to suppress a warning, and do not change the memory layout automatically. An older identity may omit `memorySummary`; that absence preserves legacy behavior but is not positive margin evidence. The summary participates in `buildId`, and current admission recomputes it from ELF/MAP/model while older runtimes may reject the new field, so new receipts require a matching runtime.
- For a manifest carrying `generation.runtimeInitialization="cmsis-gcc-v1"`, the generated linker preserves the recorded `memory.stackSize`/`memory.heapSize` exact values and retains the constructor arrays consumed by the generated startup. Do not substitute the default 4 KiB heap/1 KiB stack, edit the generated `.S`, or describe a successful link/build as ARMCC or Microlib equivalence. Linker allocation is not runtime stack/heap high-water evidence.
- A managed build identity is not a prerequisite for the separate source-only external-firmware route (`stm32_firmware_import`/`stm32_firmware_admit`/`stm32_flash_imported`) that an unmanaged project may use when the bound server exposes those tools. That route requires an explicit user selection and its own inputs/authorization; a failed or schema-2 managed build never switches to it automatically. Never fabricate `.stm32-project.json`, a `buildId`, a Git commit, or a managed receipt to make that route look managed, and never present the imported receipt as a current build identity or as a remedy for debug, Monitor, Target tests, or recovery.
- Read and retain the returned `OperationResult` envelope (`ok`, `code`, `message`, `data`, `details`), including `ok=false` errors and details, before giving a concise summary of the relevant fields; never discard errors or diagnostics, and finish immediately.
