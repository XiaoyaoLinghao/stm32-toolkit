# Build Firmware

## Workflow

1. **Context first.** Call `stm32_project_context` (no arguments). Read `capabilityDetails.build`: `available` means build evidence is complete; `blocked` means the stated prerequisite is missing; `not-evaluated` means context did not check it. If the status is `blocked`, report the evidence and next step and stop. Never stop solely because a legacy hardware boolean is `false`: those booleans are conservative compatibility fields, hardware state is unprobed, and `capabilityDetails` may identify a known blocker (for example unsupported snapshot firmware provenance). Neither a false boolean nor unprobed hardware state prevents an otherwise valid build.
2. **Doctor and binding.** Call `stm32_doctor` (no arguments). Show the toolchain evidence: ARM GCC, ARM GDB, CMake, and Ninja availability. Report missing tools and stop when the toolchain is not healthy. CubeMX/VS Code versions come from static metadata; `unknown` is not a verified version. VS Code extensions marked `not-probed` were not enumerated. `probeCore.registry` describes the Probe lease directory; `missing` does not mean PyOCD has no targets and does not change its `safe` result. Read `data.runtime.toolkitVersion` and `data.publicInventory` together with the actual tool list/input schemas the client exposes; a CLI or launcher version does not prove the bound server's version, and an inventory count is not registration proof. After an upgrade restart VS Code once and verify again. If expected tools or fields are missing, preserve the full result and stop the dependent operation.
3. **State the invocation.** Show the preset (`arm-debug` or `arm-release`), `clean` (only when the user asked for a clean build), the timeout, and the toolchain evidence for this exact build invocation.
4. **Authorize.** Ask the user for explicit authorization for this build invocation. `stm32_build` is not a dry run; it never runs without `authorized=true`.
5. **Build.** After explicit authorization, call `stm32_build` with the exact preset, clean value, and timeout shown in step 3 and approved in step 4, plus `authorized=true`. Do not substitute a default for an approved clean build.
6. **Report evidence.** From the returned `build` result, report: the build ID, identity `schemaVersion`, provenance (`sourceBaseline`), Git HEAD and dirty state, ELF and MAP SHA-256 hashes, memory usage per region, warnings, and the portable artifact paths (`buildLogPath`, `buildResultPath`, `identityPath`). A schema-1 identity has a 40-character `gitHead` and boolean `gitDirty`. A schema-2 identity means Git was unavailable: `sourceBaseline` is `input-snapshot-v1`, `gitHead` and `gitDirty` are JSON `null`, and `gitEvidence` is bounded to `{status:"unavailable", code:"BUILD_GIT_INVALID", rule:"head"}` (the `rule` value is either `head` or `status`). Never report null as clean and never invent a commit. If the result is a failure (`AUTHORIZATION_REQUIRED`, `BUILD_*`, `RAM_OVERFLOW`, `FLASH_OVERFLOW`, ...), report the exact code and details and stop.
7. **Stale outputs.** Retain the complete `BUILD_OUTPUT_STALE` response before any other operation: the next build overwrites the current log and result. Read `details.reason` (`output-unavailable`, `prior-evidence-unavailable`, `prior-build-not-successful`, `input-snapshot-mismatch`, or `prior-evidence-mismatch`), and the fixed `evidenceField`/`evidenceSource` when present. Never echo or infer an old recorded value from a digest mismatch. If `remediation.action=clean-rebuild` and the user has not already authorized that exact clean build, ask for authorization using the proposed preset, `clean=true`, and timeout. Only then call `stm32_build` on the same bound server/project with the same preset and timeout plus `authorized=true`; the proposed MCP parameters omit `authorized` because advice is not authorization. `remediation.cli.arguments` is only the command tail, not a standalone invocation: prefix the caller-verified executable, then the required `remediation.cli.projectRoot` option (`--project-root`) with the same binding's verified **absolute** project root, in `remediation.cli.workingDirectory=project-root`; an explicit absolute root is required even when the current directory is the project root, and the bare tokens are rejected. The executable label is symbolic, not a real path, and the advice embeds no absolute root or shell command. If `clean` was already requested or an output is unavailable (`inspect-build-log`), do not repeat a clean build: inspect the build log and configuration first. Never edit receipts, identity documents, managed hashes, or the ELF/MAP to simulate freshness. If `BUILD_PROJECT_INVALID` reports managed-file drift or an invalid managed configuration, use the supported configure/fragment repair path; clean builds and hash edits are not repairs. A failed or stale managed build does not authorize flash, debug, Monitor, Target tests, or an automatic switch to the imported firmware route. These diagnostic fields are current-source behavior; frozen/installed 1.3.0 does not contain them until an authorized install.

## Rules

- Never run CMake, Ninja, or a compiler directly; the Toolkit build is the only build path.
- Never fabricate success: a failed build returns no fresh identity, and the previous ELF is stale.
- `--clean`/`clean=true` maps only to CMake `--clean-first` in the build stage. It does not delete the build directory, cache, receipts, or identity, and it does not guarantee fresh outputs. Do not describe it as a guaranteed repair or loop it after an inspect-build-log result.
- Git failure alone is not a build failure, but never run `git init`, commit, stash, or otherwise change Git state to make a build pass.
- A schema-2 snapshot identity is build-only evidence. Do not suggest flash, debug, Target tests, Monitor or acceptance for it; shared firmware admission returns `FIRMWARE_PROVENANCE_UNSUPPORTED` before any probe effect, and wrappers may map it (acceptance recovery maps it to `ACCEPTANCE_ATTEMPT_OUTPUT_INVALID`). To use hardware, restore a Git repository with a committed HEAD and rebuild.
- Distinguish unavailable, blocked, and not-evaluated evidence. A missing managed manifest or drifted managed file is blocked. Hardware state is normally unprobed; detailed capabilities can identify a known blocker such as unsupported snapshot firmware provenance. Neither unprobed hardware nor a false legacy hardware boolean prevents an otherwise valid build. Probe discovery (`stm32_probe_list`) remains independent of firmware provenance.
- A manifest with an explicit `memory.layout` places `.data`/`.bss`/`.heap`/`.stack` in their reviewed regions and keeps the `.data` load address in the selected Flash. A managed manifest with multiple Flash/RAM candidates and no layout is refused by configure with `MEMORY_LAYOUT_REQUIRED`; do not hand-edit the generated linker or choose regions in the build step. A native linker-script project keeps its own placement. Region overflow, overlap and too-small regions are linker failures. A successful link is offline placement evidence, not proof of CCM/external-memory or board runtime behavior.
- For a manifest carrying `generation.runtimeInitialization="cmsis-gcc-v1"`, the generated linker preserves the recorded `memory.stackSize`/`memory.heapSize` exact values and retains the constructor arrays consumed by the generated startup. Do not substitute the default 4 KiB heap/1 KiB stack, edit the generated `.S`, or describe a successful link/build as ARMCC or Microlib equivalence. Linker allocation is not runtime stack/heap high-water evidence.
- A managed build identity is not a prerequisite for the separate source-only external-firmware route (`stm32_firmware_import`/`stm32_firmware_admit`/`stm32_flash_imported`) that an unmanaged project may use when the bound server exposes those tools. That route requires an explicit user selection and its own inputs/authorization; a failed or schema-2 managed build never switches to it automatically. Never fabricate `.stm32-project.json`, a `buildId`, a Git commit, or a managed receipt to make that route look managed, and never present the imported receipt as a current build identity or as a remedy for debug, Monitor, Target tests, or recovery.
- Read and retain the returned `OperationResult` envelope (`ok`, `code`, `message`, `data`, `details`), including `ok=false` errors and details, before giving a concise summary of the relevant fields; never discard errors or diagnostics, and finish immediately.
